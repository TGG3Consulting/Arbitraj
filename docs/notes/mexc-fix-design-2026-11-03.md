# Исправления по разборам MEXC 03.11.2026 — проект решения (решение 118)

Основание: `mexc-audit-2026-11-03.md` (адаптер против официальной документации, дальше — **А**) и
`mexc-core-audit-2026-11-03.md` (ядро при двух биржах, дальше — **Я**). Пункт Я-1 уже исправлен (решение 117).
Решения Тиграна 03.11:
- налог перевода биржа↔биржа — **настройкой**;
- время в пути — **отправка у источника + зачисление у получателя**, уточнение по истории пары (`manual_auto`) остаётся;
- карантин — **по адресу контракта**, ручной чёрный список и настройки «по монете» — по тикеру, как сейчас.

Для каждого пункта: причина → решение → файлы → настройки → прогон (сценарий «до / после»).
Правила проекта: без хардкодов (числа — в настройках), без моков, тесты — на записанных данных, файл ≤ ~200 строк.

## Часть 1. Ядро

### Я-2 🔴 Одна сделка на монету (замок по монете)
- **Причина.** Замок `inner.active: HashSet<Direction>` — по направлению. При DEX дешевле двух бирж `bsc_dex→bingx` и
  `bsc_dex→mexc` идут параллельно, обе берут весь лимит монеты (вложенное растёт только после покупки). Живой случай
  02.11: XPL `mexc→bingx` 21:31:49 и `mexc→bsc_dex` 21:31:58.
- **Решение.** Замок по монете. Ключ — адрес контракта (у монеты без адреса — тикер; такие не торгуются, но ключ
  определён). `active: HashSet<CoinKey>`; `enqueue` пропускает направление, если по монете идёт сделка; `executor::start`
  вставляет ключ монеты (вторая — `Busy`). Тот же ключ — в проверке `deals` при выдаче ID (Я-17).
- **Файлы.** core/inner.rs, executor.rs, candidates.rs (+ все чтения `active`).
- **Прогон.** Тик: оба направления XPL — кандидаты. Первое дошло до `start` → замок XPL. Второе: `enqueue` не ставит
  (замок), а если уже считалось — `start` → `Busy`, расчёт закрыт без покупки. В монете ≤ `money.max_per_coin_usd`.

### Я-3 🔴 Налог перевода биржа↔биржа (настройкой)
- **Причина.** Налоги проверяются только у монет с пулом на DEX; в расчёте вывода с биржи налога перевода нет.
- **Решение.**
  1. Налог перевода монеты = `transfer_pct` из проверки налогов любой DEX-площадки по адресу (`market.coin_check`).
  2. Вывод с биржи A (`costs_withdraw::withdraw_a`): если налог известен — строка `TransferTax` (% от суммы вывода,
     в монете, `in_qty`) — приход на B меньше. Ожидание зачисления (`credit_expect`) берёт тот же налог и для
     получателя-биржи (сейчас только для DEX) — план и ожидание совпадают.
  3. Налог неизвестен: если ни одна сторона не DEX — по настройке **`cex_cex.untaxed_ok`** (Да/Нет, вся система,
     необязательная): «да» — налог 0, «нет» или не задана — направления нет (причина «налог перевода не измерен»).
     Если одна сторона DEX — как сейчас (там проверка обязательна).
  4. Страховка: зачислилось меньше ожидаемого больше допуска (`transfer.credit_shortfall_pct` уже? — если нет, новая
     **`transfer.credit_shortfall_pct`**, %, вся система, необязательная; не задана — без авто-блока) → монета в ручной
     чёрный список `coin.blocked` с причиной «зачислено меньше на N% — похоже на налог перевода», уведомление.
- **Файлы.** core/costs_withdraw.rs, credit_expect.rs, registry.rs (directions: фильтр CEX↔CEX), transfer_credit.rs.
- **Прогон.** BingX→MEXC, монета с пулом и налогом 0% — строка налога 0, как раньше. Монета без пула,
  `cex_cex.untaxed_ok` не задана → направления нет (видно на «Монеты»). Задано «да», реально налог 5% → зачислено на 5%
  меньше → блок монеты и уведомление; больше эта монета не торгуется.

### Я-4 🟠 Время в пути = отправка у источника + зачисление у получателя
- **Решение.** Новая **`profit.transit_credit_s`** (секунды, по площадке-**получателю**, необязательная; не задана — 0,
  как раньше). `transit::seconds`: ручное T = `profit.transit_manual_s[A]` + `profit.transit_credit_s[B]`. Режим
  `manual_auto` по истории пары остаётся. История `transits` обрезается до `profit.transit_auto_after` значений на пару.
  Подписи в интерфейсе: `transit_manual_s` — «отправка с площадки (до появления в сети)», `transit_credit_s` —
  «зачисление на площадке после появления в сети».
- **Прогон.** BingX→кошелёк: manual[bingx]=N, credit[bsc_dex] не задан → T=N (как было). BingX→MEXC: credit[mexc]=M →
  T=N+M. Через N сделок пары `manual_auto` берёт среднее факта.

### Я-5 🟠 Адрес депозита получателя — в предпроверке
- **Решение.** Если B — биржа: `deposit_address(asset, net_b)` в предпроверке; ошибка — отказ до покупки. Адаптеры
  кэшируют адрес в памяти по (монета, сеть) — повторно запросов нет.
- **Прогон.** У MEXC нет адреса XYZ → «нет адреса депозита MEXC — создайте в кабинете» до покупки, денег не тронуто.

### Я-6 🟠 σ по направлению, а не по площадке
- **Решение.** Ключ ряда — (площадка, монета, сторона, **площадка-напарник**). `evaluate` пишет со своим напарником,
  `dirctx` читает σ продажи на B для напарника A.
- **Прогон.** Ряд (mexc, X, продажа, bingx) и (mexc, X, продажа, bsc_dex) — разные; разные объёмы не смешиваются.

### Я-7 🟠 Память котировок DEX: ключ по адресу, несколько объёмов
- **Решение.** Ключ (площадка, **адрес токена**, сторона) → маленькая карта объём → (котировка, время, поколение);
  при записи — удалять записи старше `signal.dex_quote_cache_ms`. Число объёмов на ключ ≤ числа направлений монеты.
- **Прогон.** Тик BingX: BingX→DEX кладёт продажу DEX на Q1; MEXC→DEX — на Q2; следующий тик берёт обе из памяти.

### Я-8 🟠 Разные тикеры одного адреса на разных биржах
- Живая проверка невозможна (MEXC выключен Тиграном 22:21 UTC). **Решение (безопасное):** при сборке справочника, если
  у одного адреса на разных биржах разные тикеры, — монета делится на отдельные записи по тикеру (ключ `адрес|тикер`),
  в журнал одна запись «у адреса … разные тикеры: bingx=…, mexc=…» (раз на изменение). Направления между ними не
  строятся — бот не торгует то, что не может сопоставить. Тикер у каждой площадки (полный разнос) — техдолг.
- **Прогон.** BingX «ABC», MEXC «ABC2», один адрес → две строки, направлений BingX↔MEXC нет, запись в журнале.

### Я-9 🟠 Тик стакана: карта (площадка, тикер) → монета
- **Решение.** Пересборка справочника строит `HashMap<(VenueId, String), Asset>`; `tick.rs` ищет по ней (O(1)).
- **Прогон.** Кадр MEXC «XYZ» → монета MEXC с её адресом; перебора 11 тыс. записей нет.

### Я-10 🟠 Пауза биржи продажи
- **Решение.** `can_open`: для B обязательна `risk.max_errors_in_row` в её области (не задана — «торговля не
  включается»). Остальные `money.*`/`risk.*` — по A, как раньше.

### Я-11 🟠 Балансы одной площадки не получены — пауза этой площадки
- **Решение.** «Балансы не получены» (после `ledger.reconcile_confirm_rounds`) → `venue_paused[площадка]`, а не
  системная пауза. Расхождение монет по учёту — системная пауза, как раньше. Снятие паузы площадки — как сейчас (кнопка).

### Я-12 🟠 Возврат USDT: минимум/максимум вывода
- **Решение.** `return_b`: сумма возврата < `withdraw_min` USDT у B → `Fail::TooSmall` (подбор объёма поднимет объём);
  > `withdraw_max` → `Fail::TooLarge`.

### Я-13 🟠 Возврат «отдельно» при трёх площадках
- **Решение.** После перегона `free[from] -= amount`, `free[to] += amount`; донор — только если после отдачи у него
  не меньше его порога `low_balance_usd`.

### Я-14 🟠 «Перегон» застрявшей монеты
- **Решение.** `targets` — без площадок на паузе; `value_at` — проверки вывода/депозита (минимумы, максимумы) по
  справочнику ядра, комиссия — из справочника ядра (без запроса к бирже).

### Я-16 🟠 / А-🟠6 Хеш перевода: сравнение после нормализации
- **Решение.** Общая функция шлюза `gateway::tx_hash::same(a, b)`: нижний регистр, без `0x`, до `:`. Адаптеры BingX и
  MEXC сравнивают через неё.

### Я-15 🟠 memo/tag адреса депозита
- **Решение.** Адаптеры BingX и MEXC: у адреса депозита сети BSC непустой memo/tag → ошибка «адрес депозита требует
  memo — не поддерживается» (с Я-5 — отказ в предпроверке).

### Я-17 🟠 ID сделки уникален
- **Решение.** При выдаче ID: занят в `deals` → добавить счётчик. С Я-2 одновременных сделок одной монеты нет.

### Я-18 🟠 Карантин по адресу
- **Решение.** `risk.quarantine: HashMap<CoinKey, (тикер, причина)>`; показ — тикер + короткий адрес. Ручной список —
  по тикеру (как сейчас).

### Я-19..23 🟡
- 19: запасное имя сети BSC — только `venue.bsc_network` своей площадки, иначе ошибка.
- 20: карточка CEX↔CEX — у направления без DEX полоса не задаётся и **не ошибка**: стаканы показываются без полосы.
- 21: «Балансы» → вложено по монетам — ключ «тикер (адрес коротко)».
- 22: перегон «в каждой сделке» — выручка минус комиссия продажи в котируемой монете.
- 23: подписи времени в пути — с Я-4.

### Я-24 Нагрузка
Закрывается Я-7, Я-9, А-🟡13 (кэш справочника MEXC для предпроверки, ниже).

## Часть 2. Адаптер MEXC (и общее с BingX)

### А-🔴1 Комиссия по всем сделкам ордера
- **Решение.** `myTrades` с `limit` = **`venue.my_trades_limit`** (по площадке, обязательна для MEXC; в доке max 1000);
  сумма `qty` сделок сверяется с `executedQty` ордера: не сошлось — повтор чтения до `venue.order_final_wait_ms`;
  так и не сошлось — ошибка с фактом (не занижённая комиссия).

### А-🔴2 Ордер не остаётся висеть
- **Решение.** `settle`: ошибка запроса статуса в цикле — не выход, повтор до срока; по сроку — всегда `DELETE`
  (по `orderId`), затем чтение итога (с повторами); OutcomeUnknown — только если итог не прочитан и после отмены.

### А-🔴3 HTTP 418/429 → «превышен лимит»
- **Решение.** HTTP-статус 418/429 (и `code` 429 в теле) — всегда `RateLimited` независимо от тела; 403 — WAF.
  `Retry-After` (секунды) — если транспорт отдаёт заголовок, в текст ошибки и в паузу правила (не меньше Retry-After).

### А-🟠1 Вес tradeFee — комментарий «IP», в README; подсказка в описании `venue.fee_requests_per_sec`.
### А-🟠2 Проверка ключа требует SPOT_DEAL_READ.
### А-🟠3 Успешный HTTP без `orderId`/`id` → OutcomeUnknown (ордер — поиск по своему ID).
### А-🟠4 Итог постановки неизвестен и ордер не найден → `DELETE` по `origClientOrderId`, затем чтение по нему же
(повторы до `venue.order_final_wait_ms`).
### А-🟠5 Вывод: `withdrawOrderId` с меткой попытки (как решение 114); OutcomeUnknown — поиск в истории по
`withdrawOrderId`.
### А-🟠6 Хеш депозита — через `gateway::tx_hash::same` (см. Я-16).
### А-🟠7 `withdrawIntegerMultiple` — читается из `config/getall`; если > 0 — сумма вывода вниз до кратного
(в `CoinNetworkInfo` — поле шага вывода; ядро уже округляет по `withdraw_precision` — добавить шаг).
### А-🟠8 Свежесть стакана по паре: время последнего кадра пары (и при пропуске одинакового снимка); старше
`venue.book_stale_ms` (если такая уже есть у BingX — та же; иначе новая, по площадке) — котировки нет.
### А-🟠9 700003 / 10073 → текст «время запроса вне recvWindow — проверьте часы сервера» (код InvalidCredentials
не годится → `BadResponse` с этим текстом).
### А-🟠10 listenKey: при обрыве WebSocket — переподключение с тем же ключом, пока продление проходит; новый — только
при отказе продления; закрытие ключа — с записью ошибки в журнал.
### А-🟡: 1 recvWindow ≥ 60000 — отказ; 2 коды 30035, 60005 → `InsufficientPermissions` (блок аккаунта — пауза
площадки), 10073/700003 — см. 🟠9; 3 11444 у ордера/вывода → отказ (`OrderRejected`/`WithdrawRejected`), не «неизвестно»;
7 тип ордера проверяется по `orderTypes` пары до отправки; 8 ошибка пробного ордера сохраняет код (RateLimited и др.);
9 количество ордера по умолчанию — отправленное (округлённое); 13 кэш `config/getall` для предпроверки, вывода и адреса
депозита — моложе **`venue.networks_fresh_ms`** (по площадке, необязательная; не задана — запрос каждый раз, как
сейчас); 15 точность котируемой монеты — точное совпадение базового актива пары, не `ends_with`; 16 `code` ≠ 0/200
без `msg` — ошибка.
### Не делаем сейчас (техдолг, записано): А-🟡6 `available` vs `free` (сверить на живом ответе); А-🟡12 подписка на
стаканы при запертых секретах; отмена висящих ордеров при запуске; полный разнос тикера по площадкам (Я-8).
