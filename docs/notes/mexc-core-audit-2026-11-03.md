## 🔴 1. Предпроверка затирает справочник сетей биржи одной монетой

**Где:** `src/core/precheck.rs:30–51`.

```rust
let list = gw.coin_networks_of(&d.asset.ticker).await ...;   // решение 113: ОДНА монета
let list = super::native::map(core, v, list);
...
wr(&core.inner.networks).insert(v.clone(), list);            // заменяет ВЕСЬ справочник биржи
core.request_rebuild();
```

`coin_networks_of` (gateway/contract.rs:82–89; BingX — `config/getall?coin=`, MEXC — весь справочник с фильтром)
отдаёт сети одной монеты. Список пишется на место всего справочника сетей биржи `core.inner.networks[v]`.
До решения 113 сюда приходил полный список, поэтому раньше это не мешало.

**Что произойдёт.** Каждая сделка с биржей (на A или на B) запускает предпроверку, и после неё:
- пересборка справочника (`rebuild.rs:91–113`) видит у этой биржи одну монету. У всех остальных монет присутствие
  на ней — `NoBscNetwork` (presence.rs:38), направления пропадают, строки уходят с «Живого экрана»
  (`spreads.retain`, rebuild.rs:104), эпизоды закрываются (`episode_run::sweep`);
- `subscribe::wanted` (subscribe.rs:30–37) даёт бирже список «1 монета + BNB», и подписка стаканов биржи
  пересобирается на 1–2 монеты. У MEXC это тысячи стаканов, и через `venue.networks_poll_ms` они возвращаются
  обратно. Каждая предпроверка — отписка и повторная подписка всех стаканов биржи;
- у монет, которые торгуются только на этой бирже и на DEX, пропадает DEX-присутствие (`cex_pair`):
  подписка DEX пересобирается заново с поиском пулов (subscribe.rs:42–50 — это «минуты»), пулы в `PoolsLoading`;
- расчёты других кандидатов на этой бирже падают на `dirctx_venue::network` — «сети … нет в справочнике сетей»
  (dirctx.rs:124–131);
- у USDT этой биржи нет записи: `usdt_b` для возврата USDT не найдётся (dirctx.rs:137–141). Если адрес USDT
  давала только эта биржа, `usdt_address` → Err и у всего DEX `NoUsdtAddress`;
- если тикер у бирж разный (п. 8), владелец тикера записи монеты меняется, а с ним и `Asset` направлений.

**Проверить на живых данных:** в журнале сразу после «предпроверка пройдена» / «сделки нет — …» должна
появиться запись `core.subscribe` «Подписка на рыночные данные: 2 монет» (или близкое число) у биржи сделки.
На экране «Монеты» число монет биржи падает до 1 и через `venue.networks_poll_ms` восстанавливается.

**Исправить:** в предпроверке заменять в `networks[v]` только записи этого тикера (удалить старые записи тикера и
добавить свежие), остальной справочник не трогать. Либо вообще не писать в общий справочник, а только
использовать свежий статус для решения. Пересборку толкать, только если статус монеты изменился.

## 🔴 2. Одна монета — несколько сделок одновременно; лимит на монету не держится

**Где:** `src/core/executor.rs:71` (замок по направлению), `candidates.rs:62–90` (расчёты параллельно),
`limits.rs:43–46` (остаток лимита по монете), `ledger.rs:26–36` (вложенное считается по факту покупки).

```rust
if !lk(&core.inner.active).insert(d.clone()) { return Start::Busy; }   // ключ — Direction (монета, A, B)
...
let coin_left = per_coin - ex.per_coin.get(&d.asset)...;               // exposure растёт только после покупки
...
let left = (d.invested - d.proceeds).max(Decimal::ZERO);               // invested заполняет fills::trade
```

С одной биржей у монеты было два направления (A→B и B→A), и прибыльным одновременно бывало только одно.
С BingX, MEXC и DEX у монеты 6 направлений, и самый частый случай — DEX дешевле обеих бирж:
`bsc_dex → bingx` и `bsc_dex → mexc` становятся кандидатами на одном тике.

**Что произойдёт:** оба расчёта идут параллельно (решение 88). Оба видят `exposure.per_coin` = 0 и берут бюджет по
`money.max_per_coin_usd` (45) целиком. Оба проходят предпроверку на одном и том же состоянии пулов и обе
покупают одну монету на DEX. В монете оказывается до 2 × 45 (при N биржах — до N × 45), `money.max_in_transit_usd`
тоже не резервируется. Вторая покупка идёт по пулу, который уже сдвинула первая, а её план считался на пуле до
первой — проскальзывание второй не учтено, и её прибыль завышена. То же на бирже: «BingX дешевле MEXC и DEX» —
две покупки по одному стакану.

**Исправить:** замок на (монета, площадка покупки), а лучше на монету целиком. Либо резервировать `per_coin` и
`in_transit` в `exposure` в момент принятия кандидата (до предпроверки) и снимать резерв при закрытии без покупки.
`enqueue` (candidates.rs:43–46) тогда пропускает направление, если по монете уже идёт сделка.

## 🔴 3. CEX ↔ CEX: монета без проверки налогов торгуется; налог перевода не в расчёте

**Где:** `src/core/rebuild_blacklist.rs:27–33`, `blacklist.rs:66–86`, `costs_withdraw.rs:219–222`,
`credit_expect.rs:121–125`.

```rust
// rebuild_blacklist.rs — проверки налогов берутся только у DEX-присутствий с пулом
.filter(|p| p.info.is_none() && has_pool(&p.excluded))
// blacklist.rs — пустой список проверок → блокировки нет
for c in checks { ... }  Ok(None)
// costs_withdraw.rs — вывод с биржи A: только комиссия вывода
if let Some(info) = &cx.a.info { return Ok(vec![fee_line(info)?]); }
// credit_expect.rs — налог перевода учитывается только когда получатель DEX
if !dex || ... { return Ok(Decimal::ZERO); }
```

**Что произойдёт:**
- монета есть на BingX и MEXC с адресом в BSC, а пула с USDT на DEX нет (или все пулы исключены). Проверок
  налогов нет → `block = None` → направления BingX ↔ MEXC рабочие (registry.rs:98–124). Монета с налогом
  перевода (fee-on-transfer) или «медовая ловушка» торгуется вслепую. Это нарушает «Не торгуем вслепую» и
  CLAUDE.md: «CEX ↔ CEX — те же правила и затраты», в том числе налог токена;
- даже когда налог известен (`transfer_pct` ниже порога `tax.max_transfer_pct`), в расчёте CEX → CEX и CEX → DEX
  его нет: вывод биржи — это перевод токена в сети, налог снимается, а план считает приход = вывод − комиссия.
  Прибыль завышена на `transfer_pct` от объёма. Сверка зачисления (`credit_expect`) при этом налог для DEX
  учитывает, то есть план и ожидание расходятся.

**Исправить:** для направлений, где ни одна сторона не DEX, требовать известную проверку налогов монеты (по адресу
у любой DEX-площадки, даже без пула с USDT — нужен отдельный путь проверки) или явную настройку «CEX ↔ CEX без
проверки налогов: нет». Не задано — направления нет. В `withdraw_a` для биржи-источника добавить строку
`TransferTax` из проверки монеты; неизвестно — `Fail::Stop`. Нужно решение Тиграна: можно ли торговать CEX ↔ CEX
монеты без пула на DEX.

## 🟠 4. Время в пути по площадке-источнику, а не по паре

**Где:** `src/core/transit.rs:87–116` (+ подпись в интерфейсе, п. 23).

```rust
let from = Scope::Venue(d.buy_on.0.clone());
let mode = s.text_in("profit.transit_mode", &from) ...
let manual = s.integer_in("profit.transit_manual_s", &from) ...
```

**Что произойдёт:** `profit.transit_manual_s [bingx]` задавалась под «BingX → кошелёк» (несколько секунд, слова
Тиграна). Теперь это же число берут BingX → MEXC: вывод BingX плюс зачисление MEXC после её подтверждений сети.
`[bsc_dex]` («кошелёк → BingX, почти моментально») — то же для кошелька → MEXC. T занижен → запас
r = k·σ·√T занижен → прибыль завышена. В режиме `manual_auto` история уже по паре (откуда, куда), но первые
`profit.transit_auto_after` сделок идут по числу «под кошелёк». История `transits` растёт без ограничения
(transit.rs:66–69): в память и в базу пишется весь ряд.

**Исправить:** область настройки — пара (источник, получатель), с запасным вариантом «источник». Либо отдельная
настройка `profit.transit_manual_s` по получателю. Ряд истории обрезать до `transit_auto_after`.

## 🟠 5. Адрес депозита биржи-получателя — только после покупки

**Где:** предпроверка `src/core/precheck.rs:168–216` адрес не запрашивает; впервые его просит `transfers.rs:196–199`
уже с монетами на руках.

**Что произойдёт:** раньше получатель-биржа (BingX) получал депозит от своего кошелька, а адреса депозита BingX для
нужных монет существовали. Теперь MEXC — получатель. Адаптер MEXC прямо отвечает «У X нет адреса депозита MEXC в
сети BSC — создайте его в кабинете MEXC» (venues/mexc/wallet.rs:282–289). Сделка BingX → MEXC (или DEX → MEXC):
покупка прошла, перевод упал → `Step::Stuck` → режим застрявшей монеты (продажа обратно с убытком на комиссиях
или перегон). То же, если биржа-отправитель требует белый список адресов вывода для API — проверить: в
официальной документации BingX и MEXC, нужно ли заносить адрес в адресную книгу. Раньше адрес вывода с BingX был
один (свой кошелёк), теперь это адреса депозита MEXC по монетам.

**Исправить:** в предпроверке, если B — биржа, запрашивать `deposit_address(asset, net_b)` (можно с памятью по
(биржа, монета, сеть)). Ошибка — отказ до покупки. Если выяснится, что нужен белый список, — проверка по нему там же.

## 🟠 6. σ на бирже смешивает разные объёмы

**Где:** `src/core/vol.rs:43–64` (ключ ряда — (площадка, монета, сторона)), `evaluate.rs:56–63`.

```rust
vol.sample(&dir.buy_on, &dir.asset, Side::Buy, p.buy, now, w);
vol.sample(&dir.sell_on, &dir.asset, Side::Sell, p.sell, now, w);
```

`p.buy` / `p.sell` — средние цены на объёме сравнения направления: меньшая из глубин обеих сторон, не выше
`money.max_per_trade_usd[A]` (prices.rs:296–318). С одной биржей у ряда (bingx, монета, продажа) был один источник —
направление DEX → BingX. Теперь ряд (mexc, монета, продажа) получает замеры от BingX → MEXC и от DEX → MEXC, и у
каждого свой объём (так же ряд (bsc_dex, монета, продажа) — от BingX → DEX и MEXC → DEX).

**Что произойдёт:** в одном тике ряд получает цену продажи на объёме X, а потом на объёме Y (у направлений разная
глубина A). Разница средних цен уровней стакана выглядит как движение цены → ln(p/prev)² растёт → σ завышена
(сделки зря отсекаются). На тонких стаканах это может быть в разы.

**Исправить:** σ мерить по лучшей цене стакана (или по фиксированной доле), а не по средней на объёме направления.
Либо ключ ряда — по направлению (A, B, монета).

## 🟠 7. Память котировок DEX: один объём на сторону

**Где:** `src/core/quote_cache.rs:20–21, 43–46`, `prices.rs:255–273`.

```rust
type Key = (VenueId, String, bool);            // площадка, тикер, покупка
(*q_qty == qty && *g == generation && ...)     // годится только тот же объём
```

**Что произойдёт:** продажа на DEX нужна направлениям BingX → DEX и MEXC → DEX, а объём у каждого свой
(`max_per_trade_usd[A] / опорная цена`, затем меньшая глубина). Тик монеты пересчитывает оба направления подряд,
и каждое затирает запись другого — сторона продажи на DEX в память почти не попадает, и выигрыш решения 109 для неё
пропадает (полный обход пулов на каждый тик, как до правки). С N биржами ещё хуже.
Ключ по тикеру, а не по адресу: две монеты с одним тикером на одной DEX при совпавших объёме и поколении получат
чужую котировку. Вероятность мала, но ключ должен быть по адресу.

**Исправить:** ключ (площадка, адрес токена, сторона) и несколько объёмов на ключ (маленькая карта объём → котировка
с тем же сроком). Либо объём сравнения стороны DEX — общий для всех направлений монеты.

## 🟠 8. Один тикер монеты на все биржи

**Где:** `src/core/registry_build.rs:80–97`; используется: `subscribe.rs:30–37`, `dirctx.rs:120–136`,
`precheck.rs:39`, `prices.rs:215–218` → адаптер `quote` по `asset.ticker` (venues/mexc/book.rs:67), вывод
(`coin = asset.ticker`, venues/mexc/transfers.rs:55).

```rust
let p = super::presence::cex(venue, ticker, &nets, bsc, &fresh, inp.market);   // присутствие — по тикеру ЭТОЙ биржи
let asset = Asset { ticker: ticker.to_string(), bsc_contract: ... };
coins.entry(key).or_insert((asset, vec![])).1.push(p);                         // asset — от ПЕРВОЙ биржи (по алфавиту)
```

Записи группируются по адресу контракта, а `CoinEntry.asset.ticker` берётся у первой биржи (kinds отсортированы:
bingx, bsc_dex, mexc — engine.rs:54). Дальше подписка, котировки, ордера, вывод и депозит на всех биржах идут по
этому тикеру.

**Что произойдёт:** если у MEXC тот же токен (тот же адрес) называется иначе (переименования и «…2» у бирж
встречаются), то MEXC подписывается на тикер BingX. Стакана под тикером MEXC не будет → присутствие MEXC
`NoSpotBook`, направления с MEXC молча пропадают. Деньги не под риском: вывод с неверным тикером не дойдёт до
сделки, потому что направления нет. Но если BingX выключена или её справочник сетей пуст (п. 1!), владельцем
становится MEXC: тикер записи меняется, `Asset` меняется, и с ним теряются ключи — `active`, `spreads`, `signals`,
чёрный список (`bl.get(&c.asset)`), ряды σ, статистика газа.
Если у одной биржи на одном адресе две монеты, в записи будут два присутствия одной площадки и дубли направлений

**Где:** `src/core/usdt_return.rs:131–152`.

## 🟡 24. Нагрузка при N биржах

- Направлений у монеты с M площадками — M·(M−1) (registry.rs:98–124). Тик площадки пересчитывает 2·(M−1) направлений
  **последовательно** (evaluate.rs:49–87), каждое — 2 котировки (4, если объём не влез, prices.rs:314–318). Сторона
  DEX считается заново для каждого напарника (п. 7).
- Кандидаты считаются параллельно без предела, если `profit.calc_concurrency` не задан (candidates.rs:66–75):
  при N биржах одновременных расчётов больше в (M−1) раз на монету.
- Перебор справочника на каждое событие стакана (п. 9) — O(число монет) × частота кадров всех бирж. С MEXC монет
  стало ~11 тыс.
- Пересборка справочника (O(монеты × площадки)) толкается опросом сетей каждой биржи, первыми стаканами и
  `SpotPairs`. Частота растёт с N, а п. 1 добавляет пересборку и переподписку на каждую предпроверку.
- Предпроверка CEX ↔ CEX с MEXC: `coin_networks_of` у MEXC — весь `config/getall` (~5.6 МБ, вес 10). На каждую
  сделку с MEXC — одна загрузка (при п. 1 ещё и затирание).
- `convert::price_of` перебирает биржи по очереди (convert.rs:109–122) — линейно, не страшно.

Что растёт квадратично: направления и котировки на тик (M²), одновременные расчёты кандидатов одной монеты (M²).
Линейно по монетам: поиск по справочнику на событие.
