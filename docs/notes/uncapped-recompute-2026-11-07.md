# Пересчёт старых записей «без потолка» по окнам — инструкция для сервера (решение 218, 07.11.2026)

## Зачем

До решения 217 запись «без потолка» по сделке считалась ПОСЛЕ нашей покупки — по стакану, который наша покупка уже
съела (на экране: «посчитано после покупки — занижено», basis `live_after_buy`). Программа `uncapped_recompute`
пересчитывает такие записи по записанному окну сделки — по стаканам на момент решения о входе — той же моделью и тем
же поиском, что бот (`costs::evaluate_with`, `size_uncapped.rs`). Запускается один раз.

## Что считается и что нет

| Сделка | Как |
| --- | --- |
| Биржа ↔ биржа | Обе стороны — последний полный стакан (сначала торговый снимок, см. ниже) каждой биржи из окна сделки строго до момента решения (время события «План…» сделки). basis `recomputed_window` |
| Биржа → DEX | Биржа — так же; DEX — из плана сделки: средняя цена продажи плана как постоянная цена без кривой пулов — **приблизительно**. basis `recomputed_window_dex_plan` |
| DEX → биржа, цикл DEX ↔ DEX | Не пересчитывается (причина в отчёте) |
| Нет окна, окно открыто после входа, биржа не писалась | Не пересчитывается (причина) |
| В окне нет полного стакана до момента решения | Не пересчитывается (причина). Полный стакан, по порядку (решение 221, 08.11.2026): сначала снимок N уровней торгового потока (тот, по которому бот реально котировал) без неприменимых изменений после него; только если его нет — запасной: стакан всей глубины по изменениям (полный + изменения). Какой взят — в столбце «источник» отчёта и в snapshot записи («снимок стакана торгового потока» / «стакан всей глубины по изменениям (запасной…)»). Пример: Bybit без `venue.window_depth_limit` — в окне только изменения торгового стакана, снимка нет |
| Последняя запись сделки уже не старая (пересчитана раньше или посчитана по снимку) | Не пересчитывается — повторный запуск ничего не дублирует |

Чего на момент сделки в базе нет — берётся из плана сделки: ставка комиссии тейкера, затраты вывода (комиссия —
постоянная, налог перевода — той же долей), возврат USDT, σ, время в пути, курсы затрат (BNB и т. п.). Правила пары
биржи (шаг, minQty, minNotional) и минимумы вывода и депозита на момент сделки не записаны — не применяются (в записи
сказано). Настройки модели — текущие из базы бота: `card.max_search_usdt`, `money.min_profit_usd`, `money.min_profit_pct`,
`uncapped.max_evals`, `uncapped.ladder_usdt`, `size.*`, `venue.quote_asset`, `profit.price_move_k`,
`profit.liquidity_share_h`. Не задана — сделка не пересчитывается, причина в отчёте.

## Что пишет

- Старые записи **не удаляются и не меняются**.
- По каждой пересчитанной сделке **дописывается** новая строка таблицы `uncapped` (тот же формат записи, начало — как у
  старой, тот же период на экране). Все новые — одной транзакцией.
- Основная запись сделки — последняя: экран «Упущено из-за потолка» (итоги и список), отчёт Excel «Упущено», карточка
  сделки и Telegram берут её; пометка «пересчитано по окну» (у биржа → DEX — «DEX из плана, приблизительно»).

## Где взять

Артефакт сборки `arb-linux` (GitHub → Actions → Linux build → Artifacts): рядом с `arb` лежит `uncapped_recompute`
(статический musl, как бот). Новый бот (с решением 218) нужен и для экрана: он показывает пометки и берёт последнюю
запись сделки.

## Запуск на сервере

Пути ниже — пример: папка данных бота — та, что передаётся боту в `--data-dir` (в ней `arb.sqlite` и `windows/`).

1. Отчёт без записи (бот может работать):

   ```sh
   ./uncapped_recompute --data-dir /opt/arb/data --dry-run --report /opt/arb/data/uncapped_recompute_dry.csv
   ```

   В stdout — строка на сделку и итоги: «биржа ↔ биржа», «биржа → DEX (DEX из плана)», «не пересчитано» по видам причин.
   В CSV (разделитель «;», UTF-8 с BOM — открывается Excel): сделка, направление, группа, было упущено, стало упущено,
   потолок было, потолок стало, источник (окно, стаканы, приближения), причина.

   Папка окон по умолчанию — `<data-dir>/windows`; другая — `--windows-dir <папка>`. Только часть сделок — `--deal <id>`
   (можно несколько раз).

2. Показать отчёт Тиграну, получить «да».

3. Остановить бота (как он запускается на сервере: `start.sh` / systemd). Пока бот работает, `--apply` откажет:
   «база занята — бот запущен … Остановите бота и повторите --apply».

4. Сделать копию базы (на всякий случай):

   ```sh
   for f in arb.sqlite arb.sqlite-wal arb.sqlite-shm; do [ -f /opt/arb/data/$f ] && cp /opt/arb/data/$f /opt/arb/data/$f.before-218; done
   ```

   (Файлы `-wal` и `-shm` — журнал WAL; если они есть, копируются вместе с базой.)

5. Записать:

   ```sh
   ./uncapped_recompute --data-dir /opt/arb/data --apply --report /opt/arb/data/uncapped_recompute_apply.csv
   ```

   В конце: «Режим --apply: дописано записей N (id …); старые записи не изменены».

6. Запустить бота. Экран «Упущено из-за потолка»: строка «посчитано после покупки — занижено» уменьшилась на число
   пересчитанных; у пересчитанных сделок — пометка «пересчитано позже по записанному окну».

## Почему бот должен быть остановлен

База — SQLite в режиме WAL. Работающий бот держит соединение (разделяемую блокировку) и записи в памяти; чужие строки он
не ждёт. `--apply` открывает базу с исключительной блокировкой (`PRAGMA locking_mode = EXCLUSIVE`, `BEGIN EXCLUSIVE`,
без ожидания): бот запущен — отказ; пока программа пишет, бот, запущенный в это время, базу не откроет. Проверено двумя
процессами (python sqlite3) 07.11.2026. `--dry-run` открывает базу только на чтение.

## Откат

Новые строки отличаются полем `basis`: `recomputed_window` / `recomputed_window_dex_plan`. Откат при остановленном боте —
вернуть копию `arb.sqlite.before-218` или удалить эти строки:

```sql
DELETE FROM uncapped WHERE json_extract(body, '$.basis') IN ('recomputed_window', 'recomputed_window_dex_plan');
```
