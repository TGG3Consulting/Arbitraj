# Общие пулы в долях графа — разбор (решение 223, 08.11.2026)

Живой случай: сделка `20261108102130440FLUX` (mexc → bsc_dex, кошелёк w2, налогов у FLUX нет). План продажи — граф,
4 доли 0.30 / 0.30 / 0.30 / 0.10; все четыре начинаются одним пулом pancakeswap_v2 `0xf1ca293f…` (FLUX → промежуточная),
дальше разными пулами в USDT. Ожидаемые выходы долей 13.6066 / 13.6068 / 13.6065 / 4.5525. Продажа трижды:
«проба исполнителя откатилась — execution reverted: minOut»; алерт «убыток при продаже сейчас −0.49%» — по той же котировке.

Признак ошибки прямо в цифрах: три доли одного размера через один и тот же первый пул дали почти одинаковый выход
(разница — только от разных вторых пулов). Значит, первый пул для каждой доли считался на ОДНОМ и том же исходном
состоянии — как будто у каждой доли своя копия ликвидности.

## 1. Как исполняются доли (факт по коду)

### Исполнитель ArbExecutor (contracts/ArbExecutor.sol, exec/executor/call.rs)

- `call::build` складывает шаги **доля за долей в порядке `route.legs`** (это порядок долей котировки = порядок
  кандидатов сплита). Первый шаг доли берёт `shareBps` ТЕКУЩЕГО остатка входа (`bps = вход доли / ещё не распределённый
  вход`, последняя доля — 10000), каждый следующий шаг доли — 10000 (весь промежуточный токен: прошлая доля его уже
  израсходовала).
- `execute` идёт по шагам по порядку; **каждый шаг — отдельный обмен в своём пуле** (`_step`). Общий первый пул P
  получает 4 отдельных обмена: доля 1, потом доля 2 на состоянии после доли 1, и т.д. Одним свопом суммарно — нет.
- Шаг V2: вход переводится в пару, выход считается контрактом по `getReserves()` и `balanceOf(pair) − reserve`
  (`_v2Out`) — то есть ровно getAmountOut на резервах ПОСЛЕ прошлых долей. Пара после swap записывает резервы =
  балансы (`UniswapV2Pair.swap` → `_update(balance0, balance1)`, v2-core 6a9e7c97 L159-L187, L73-L86): резерв входа
  + весь вход (комиссия остаётся в паре), резерв выхода − выход.
- Шаг V3: `pool.swap(to, zeroForOne, amount, MIN/MAX_PRICE)` — цикл пула от текущих slot0/liquidity; после него пул
  пишет slot0 = (цена, тик) и liquidity из state (PancakeV3Pool.sol L752-L781).
- **minOut — один на всю транзакцию**: `minOut = Σ min_out долей` (call.rs), проверяется по приросту баланса
  кошелька. min_out доли = max(количество × worst_price, ожидаемое × (1 − exec.dex_slippage_pct), минимум верификации)
  (exec/order.rs + exec/leg_min.rs). Минимум верификации = ожидаемый выход доли из quote/verify_decide.rs × (1 − допуск).

### Бандл (exec/bundle.rs)

Ноги группируются по Universal Router (внутри группы — в порядке маршрута), ноги форка — после групп. Порядок между
группами может отличаться от порядка маршрута, НО доли, делящие пул, всегда в одной группе (пул определяет роутер: нога
UR целиком в одном роутере, пул форка — только в ногах форка того же семейства) — относительный порядок долей каждого
общего пула сохраняется. Состояние пула зависит только от обменов через него, поэтому модель «по порядку маршрута»
точна и для бандла. Промежуточные минимумы шагов UR (`chain::steps`, от `pool_out` пути) тоже по этим путям.

## 2. Матмодель

Выбор: **(а) последовательные обмены** — выход доли k считается на состоянии пула после долей 1..k−1 в порядке
исполнения. Это ровно то, что делает сеть. Модель (б) «один своп суммы с распределением выхода» НЕ эквивалентна:

- V2 (x·y=k с комиссией) не путь-независим: комиссия первой доли остаётся в резерве входа, вторая доля видит худшую
  цену. Игрушка 1000/1000, 0,25%: один обмен 100 → 90.70243; два по 50 подряд → 90.69752 (−0.0049). На записи
  (тест four_shares…): одна доля 20000 CAKE → 40671.5720 USDT, та же сумма 30/30/20/20 подряд через те же пулы →
  40671.4958.
- V3 путь-независим до округлений шагов (комиссии вне ликвидности): CAKE-USDT Pancake V3, 20000 + 30000 CAKE подряд =
  40844.197865723015277595 + 60721.683356140208662834 = 101565.881221863223940429; один обмен 50000 —
  …940430. Разница 1 wei.

Состояние после обмена доли (quote/pool_after.rs):

- **V2**: точный вход `a` (как исполнитель/бандл), выход `o = getAmountOut(a)` той же математикой и комиссией, что
  котировка; `reserveIn += a`, `reserveOut −= o`.
- **V3**: тот же цикл swap (math/swap_cl.rs, общий `walk`), `swap_final` возвращает (цена, тик, ликвидность) после
  цикла. Тик — как в контракте: дошли до тика — `tickNext − 1` / `tickNext`; остановились внутри диапазона со сдвигом
  цены — `getTickAtSqrtRatio(цена)` (math/tick_math.rs `tick_at_sqrt_ratio`: наибольший тик с ratio(tick) ≤ цена —
  определение TickMath.sol L56-L63; двоичный поиск по точному порту getSqrtRatioAtTick; сверено с официальными
  значениями v3-core). Карта тиков обменом не меняется. Горячий расчёт котировки getTickAtSqrtRatio не платит.
- **Остальные виды** — V4/Infinity CL и Bin (крючок может менять состояние/комиссию между обменами), Elastic
  (reinvestL растёт от комиссии), Algebra (динамическая комиссия плагина), Solidly (часть комиссии уходит из пары),
  StableSwap, DODO, WooFi, Maverick — состояние после обмена не считается: **вторая доля через такой пул не
  открывается** (сплит), а маршрут с таким общим пулом в верификации/живом пересчёте — NoRoute с причиной.

Цепочка состояния доли — по обменам точным входом от входа доли (первый хоп пути), выход хопа после крючка — вход
следующего: так исполнит сеть. У продажи эта цепочка совпадает с route_calc до единицы (тот же расчёт «с начала»). У
покупки route_calc считает «с конца» (точный выход), а сеть исполняет точный вход `path.usdt` (exec/order.rs) — на
состояние пишется то, что исполнит сеть; монеты доли в котировке — консервативные (≤ факта на единицы wei).

### Сплит (quote/graph_split.rs)

Шаг пути `i`, у которого есть общий пул с уже открытой долей, оценивается совместно: все открытые доли и путь `i` (его
количество + шаг) — по порядку кандидатов на последовательных состояниях (quote/graph_seq.rs). Отдача шага = прирост
СУММЫ выходов (чужие доли после него в общем пуле теряют — это входит в отдачу), газ — как раньше (R1). Путь без общих
пулов с открытыми долями — старый расчёт (побайтно). Итог — пересчёт долей с общими пулами по порядку.

## 3. Доказательство на числах (записи tests/route_common, блок 130521896)

- V2 WBNB-USDT, 40 + 60 WBNB подряд: 29660.451317560444250794 + 44326.781707196577861001 USDT — до wei равно
  ручному getAmountOut на резервах после первой доли; вторая доля в одиночку (старая модель) — 44457.882354531234453354
  (+131.10 USDT, +0.30%).
- V3: вторая доля 30000 CAKE после первой — 60721.68 USDT, в одиночку — 61160.21 (+0.72%). Тик 7200 → 7131,
  пересечено 2 инициализированных тика, L 8377566760538168581932002 → 8168519527470794930743019 = L − Σ liquidityNet
  пересечённых тиков (проверено по карте).
- Сценарий FLUX (4 одинаковых пути через общий V3 + общий V2, продажа 20000 CAKE): старая модель разложила
  30/30/20/20 и заявила 40893.2081 USDT; истинное последовательное исполнение этой раскладки — 40671.4958 (**старая
  котировка завышена на 0.545%** — того же порядка, что −0.49% у FLUX). Новый сплит — одна доля, 40671.5720 = один обмен
  всего объёма. Покупка 20000: старая заявила 41463.73, истина 41692.65 (+0.55%), новая — 41692.57.
- Маршруты без общих пулов: котировка графа на обеих записях (с газом и без, покупка/продажа 1…100000 CAKE, 56
  котировок) побайтно та же, что до правки (tests/data/graph_shared_2026-11-08/gold_before.txt).

Почему minOut: верификация считала минимум каждой доли на исходном состоянии → Σ минимумов > истинного
последовательного выхода, как только завышение больше допуска exec.dex_slippage_pct → проба исполнителя откатывалась
по `minOut` (защита сработала верно, деньги не рисковали), а котировка «убытка» шла по той же завышенной модели.

## 4. Риски и открытые вопросы

1. **Округление bps исполнителя (было и до правки).** Доля входа в контракте — `uint16` bps от остатка, вниз; у FLUX
   0.30/0.30/0.30/0.10 bps = 3000 / 4285 / 7500 / 10000 (call.rs делит на плановый остаток), сеть проведёт
   0.30 / 0.29995 / 0.3000375 / 0.1000125 входа (доля 2 −0.017%, доли 3 и 4 +0.0125%).
   Итог почти не меняется (второй порядок), но покомпонентно доли не совпадают с котировкой.
2. **Минимум доли по worst_price.** min_out доли = max(кол-во × worst_price, …). При последовательном счёте поздние
   доли общего пула честно дешевле средней — их «кол-во × worst_price» может быть выше их ожидаемого. У исполнителя
   минимумы суммируются (Σ max ≥ max Σ) — общий minOut строже, чем граница сделки; у UR/бандла — откат такой ноги.
   Вопрос Тиграну: исполнителю ставить minOut = max(Σ минимумов верификации, qty × worst_price) вместо Σ max по долям?
3. **Форки V2.** Модель «резервы = балансы после swap» — код UniswapV2Pair/PancakePair. Форк, который в swap уводит
   часть комиссии из пары, дал бы другое состояние для второй доли (защита — minOut). По каждому форку не сверялось.
4. **Виды без расчёта состояния** (V4/Infinity CL и Bin, Algebra, Elastic, Solidly, Stable, DODO, WooFi, Maverick) —
   вторая доля через общий пул не открывается: честно, но меньше сплитов. V4 CL без крючка можно добавить (тот же цикл).
5. Порядок долей в маршруте между запусками бывает разным (перебор путей идёт через множества) — было и до правки; на
   корректность не влияет (порядок котировки = порядок исполнения в пределах одной котировки).
6. Состояний пулов FLUX в записях нет, доступа к узлу из среды разработки нет — сценарий проверен на записи CAKE.
   Нужна запись пулов FLUX (0xf1ca293f…, 0x6fe9e9de…, 0x172fcd41…, 0x36696169…, 0x28df0835…, 0x813c0dec…) на блоке
   сделки — повторить котировку старой и новой моделью на них.
7. Запись routes_2026-10-29: путь CAKE→BTCB→WBNB→USDT даёт ~1.9 млн USDT за 1 CAKE (старая котировка тоже) — похоже на
   кривую топологию/карту записи теста; на выводы не влияет (используется только для сверки математики V2).
