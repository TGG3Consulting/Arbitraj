# Переразвёртывание исполнителя ArbExecutor v2 (решение 272)

> **ЧЕРНОВИК ДО ФИНАЛЬНОЙ ВЕРСИИ КОНТРАКТА. Переразвёртывать ещё РАНО.** В контракт v2 до развёртывания войдут
> дополнительные шаги для других DEX (решение владельца: одно переразвёртывание на всё). Хеш байткода ниже — версии
> решения 290 (задача t121: вид шага LB = 18 — Liquidity Book V2.1 / LFJ, код в сети 16 212 байт); до него — после ревью 289 (правки комментариев ArbExecutor.sol: ссылка Swaps.sol L98, отступ комментария Step; код в сети тот же — 15 946 байт)
> и решения 289 (задача t120: вид шага BALANCER = 17 — Balancer V2 / ACSI Finance, код в сети 15 946 байт, и отложенные
> правки комментариев IPools.sol / ArbExecutor.sol из TASKS 288 п. 6; до него — решение 288, задача t119: вид шага SMARDEX = 16 + smardexSwapCallback — SmarDex, и KYBER_DMM = 15 — KyberSwap Classic DMM, решение 287; до них — решение 286, задача t118: вид шага IZI = 14 + swapX2YCallback / swapY2XCallback — iZiSwap и Biswap V3; до него —
> задача t117: NOMI_STABLE = 12 — Nomiswap Stable, решение 284, и METRIC = 13 + metricOmmSwapCallback — Metric OMM,
> решение 285; задача t114, `squadV3SwapCallback`); после следующих правок контракта он сменится, и этот документ будет обновлён.

Зачем: исполнитель v2 умеет `executeNative`, и через него BNB (монета сделки) торгуется через пулы форков V2/V3,
Algebra, Solidly, DODO, StableSwap, Maverick и Slipstream. Старые исполнители (v1) после обновления бота работают
как раньше (ERC-20 через исполнитель — байт в байт), только BNB через них не идёт. Переразвёртывать нужно кошельки,
через которые должен идти BNB, и кошелёк строки «Пробы и сигналы» (им мерится газ обёртки).

## Перед началом
1. Обновлённый бот запущен, секреты разблокированы.
2. Задана **`dex.native_wrapped`** (адрес WBNB) — «Настройки» → DEX. Ревью 272 (А1): этот адрес уходит аргументом
   конструктора и **навсегда** записывается в исполнитель (сеттера нет). Не задана — «Развернуть исполнитель» отвечает
   «не задана dex.native_wrapped …» и ничего не отправляет.
3. На кошельке есть BNB на газ развёртывания: окно подтверждения покажет точную сумму в BNB и USDT.

## Порядок — для каждого кошелька
Экран **«Маппинг кошельков»** → вкладка «Кошельки» → карточка кошелька → блок «Исполнитель ArbExecutor».
1. Строка «Версия» сейчас: «v1 — нативный BNB через форки не торгуется, переразверните» (или «не сверена» —
   нажмите «Проверить подключение» рядом с «Развернуть исполнитель», она покажет v1). При первой сверке v1 бот один раз
   шлёт уведомление `wallet.executor_v1` («у кошелька X исполнитель v1 — нативный BNB через форки не торгуется»;
   включается на экране «Уведомления», группа «Кошельки DEX»).
2. Нажмите **«Развернуть исполнитель»**. В окне проверьте: кошелёк (владелец) — этот кошелёк; стоимость; **«Обёртка BNB
   (навсегда)»** — адрес WBNB из `dex.native_wrapped`; SHA-256 байткода — `940fc09907eb0a746aa2232fb33b01f2a13b8f52d38b37ab523ff2788bba45dc`
   (код создания v2 без аргумента конструктора, `contracts/out/ArbExecutor.sha256`); solc 0.8.37.
3. **«Подтвердить и отправить»** (задача t114: вместе с хешем уходит адрес обёртки из окна; если `dex.native_wrapped`
   сменили после оценки — отказ «обёртка BNB для конструктора сейчас … а подтверждена … — запросите оценку заново»,
   ничего не отправлено). После блока: «Исполнитель развёрнут: 0x… Код в сети совпал с репозиторием, обёртка в
   конструкторе 0x… Сверка: Подключено: … версия v2, обёртка 0x… = dex.native_wrapped …». Новый адрес записан у
   кошелька сам, в Telegram — `wallet.executor_deployed`.
4. Строка «Версия» — **«v2 — нативный BNB монетой сделки идёт через исполнитель (обёртка 0x…)»**. Если «не сверена» —
   нажмите «Проверить подключение» исполнителя. Если «v2, но обёртка в исполнителе … ≠ dex.native_wrapped …» — адрес
   обёртки в настройке сменили после развёртывания: BNB через этот исполнитель не идёт (ERC-20 — как обычно);
   переразверните при верной настройке.
5. Повторите для следующего кошелька (у каждого кошелька свой исполнитель, решение 132). Порядок между кошельками не
   важен: пока кошелёк не переразвёрнут, его старый исполнитель работает как раньше. Запись версии при сверке не
   перезапускает слежение за кошельками (ревью 272, Б1) — ожидания зачислений идущих сделок не теряются.

## Кошелёк строки «Пробы и сигналы»
- Газ обёртки BNB для пулов, через которые BNB идёт только исполнителем, бот мерит сам пробой
  (`check/native_probe_exec.rs`) кошельком строки «Пробы и сигналы». Пока замера нет, котировка BNB через такой пул —
  «не проверено» (CoinNotChecked).
- **Пока у кошелька проб исполнитель v1 / не сверен / с другой обёрткой**, в фактах таких пулов и в журнале
  «dex.native_probe» (один раз): «проба нативной монеты (WRAP/UNWRAP) не запускается — газ обёртки через исполнитель не
  измерен: у кошелька «…» исполнитель 0x… версии v1 (executeNative нет) — переразверните исполнитель (кошелёк строки
  «Пробы и сигналы» — переразверните исполнитель кошелька проб; после сверки газ перемеряется сам)». Котировка BNB через
  такой пул отвечает «проба WRAP/UNWRAP не прошла — …» с той же причиной.
- **После переразвёртывания кошелька проб** газ обёртки перемеряется сразу, не дожидаясь планового прохода
  `tax.recheck_interval_s`: сверка исполнителя кошелька проб (после развёртывания, «Записать после проверки» или
  «Проверить подключение» исполнителя) нашла v2 с верной обёрткой — бот ставит монету BNB во внеочередную перепроверку
  (та же очередь, что кнопка «Перепроверить» / `POST /api/coins/recheck`: налоги, крючки, сверка с квотером её пулов;
  проба пулов WBNB перемеряет газ обёртки через исполнитель). В журнале «dex.native_probe»: «исполнитель кошелька проб
  «…» сверен (v2, обёртка = dex.native_wrapped) — внеочередная перепроверка BNB …», затем первый замер. Если нужно
  повторить вручную — экран «Монеты» → строка BNB → «Перепроверить на bsc_dex».

## Что будет после
- **Разовый approve новому адресу.** Разрешения ERC-20 выдаются адресу исполнителя, а у нового адреса их нет. Первая
  сделка через новый исполнитель по каждому токену отправит approve — это газ, он попадёт в итог этой сделки. Продажа
  BNB разрешения не требует (BNB идёт value транзакции).
- Разрешения старому адресу остаются. Вызвать старый исполнитель может только владелец (кошелёк бота). Кнопки отзыва
  разрешений в боте нет.

## Что проверить
1. «Ручное управление» → «Сухая сделка DEX», монета BNB, продажа и покупка на маленькую сумму, режим «как пойдёт
   сделка»: форма — «граф: исполнитель 0x…», проба прошла. Режим «через исполнитель» (код v2 и слот обёртки =
   `dex.native_wrapped` подставлены) проверяет то же до развёртывания.
2. Первая реальная сделка BNB через форк: в хронологии сделки — исполнитель, монеты — по событию `NativeSettled`.
3. Снимите квитанции продажи и покупки для теста — шапка `tests/bsc_dex_executor_v2_live.rs`.

## Откат бинарника бота (факт кода)
Исполнитель v2 по адресу остаётся в сети, денег не хранит; меняется только то, как его сверяет старая сборка.
- **Сборка до решения 272** (одна версия кода): onchain.rs сверял код по адресу только с одним
  `contracts/out/ArbExecutor.bin-runtime` (тогда — код v1). У кошелька с v2 сверка не проходит: «код по адресу … не
  совпал с contracts/out/ArbExecutor.bin-runtime» → InvalidAddress: ни разрешений, ни сделок через исполнитель у этого
  кошелька (маршрут формы «бандл» при заданном исполнителе идёт в исполнитель — exec/trade.rs, запасного бандла нет —
  такая сделка отказывает). Столбцы `executor_version` / `executor_wrapped` старая сборка не читает
  (SELECT по списку столбцов) и не трогает; смена адреса в ней их НЕ сбрасывает.
- **Сборка решения 272 до задачи t114 (rel/dex-all f16a0fcf и раньше)**: знает v1 и v2 СВОЕЙ сборки (код v2 без
  squadV3SwapCallback, runtime SHA-256 25ffb809…). Код нового v2 (runtime SHA-256 779a8936… после решения 286; 36d20c29… — после 285; 75e811d6… — после 284, 25b6435e… — после t114) не равен ни одному →
  «код по адресу … не совпал ни с v2 …, ни с v1 …» → та же остановка исполнителя у этого кошелька. Записанная новой
  сборкой версия «v2» в базе остаётся (сверка не прошла — не перезаписывается), но сделка всё равно отказывает на сверке
  перед разрешениями.
- **Кошельки с v1** работают в любой сборке как раньше: артефакт v1 (`contracts/out/v1/`) во всех сборках один.
- **Если откатиться всё же нужно**: на кошельках, уже переведённых на v2, — «Записать после проверки» со СТАРЫМ адресом
  v1 (старый контракт в сети, владелец тот же; обе старые сборки его примут) — ERC-20 через исполнитель пойдёт как
  раньше. После возврата новой сборки — снова «Записать после проверки» с адресом v2 (повторно разворачивать не нужно).
- **Возврат на новую сборку** после работы старой: версия у кошелька могла остаться от прошлой сверки (сборка до 272
  при смене адреса её не сбрасывает). Новая сборка перезаписывает её первой же сверкой (сделка, проба, «Проверить
  подключение»), а сделка и проба через исполнитель после сверки ещё раз проверяют обратный вызов пулов маршрута по
  только что сверенной версии (задача t114: exec/executor/trade.rs, check/probe_exec.rs). Для порядка — нажмите
  «Проверить подключение» исполнителя у каждого кошелька сразу после возврата.

## Итоговый порядок для Тиграна (экран «Маппинг кошельков»)
1. Выложить новую сборку (бот + интерфейс вместе: подтверждение развёртывания теперь несёт и адрес обёртки), запустить,
   разблокировать секреты.
2. «Настройки» → DEX: проверить `dex.native_wrapped` = адрес WBNB. Для SquadSwap V3 (id DEX `squadswap-v3-bsc`) —
   `dex.v3_swap_callback = squadV3SwapCallback(int256,int256,bytes)` (остальные значения — docs/TASKS.md, решение 281). Nomiswap Stable (решение 284) — значения настроек в docs/TASKS.md; её шаг NOMI_STABLE (вид 12) есть
   только у исполнителя v2 — у кошелька с v1 пулы DEX «без пути исполнения: исполнитель v1 не знает шаг исполнителя
   NOMI_STABLE …». Metric OMM (решение 285, id `metric-bsc`) — шаг METRIC (вид 13), тоже только v2. iZiSwap / Biswap V3 (решение 286, id `iziswap-bsc`, `biswap-v3`, `biswap-v3-1`) — шаг IZI (вид 14), тоже только v2. KyberSwap Classic DMM (решение 287, id `kyberswap_classic_bsc`) — шаг KYBER_DMM (вид 15), тоже только v2. SmarDex (решение 288, id `smardex-bsc`) — шаг SMARDEX (вид 16), тоже только v2. Liquidity Book V2.1 (решение 290, id `traderjoe-v2-1-bsc`) — шаг LB (вид 18), тоже только v2.
3. На каждом кошельке («Кошельки» → карточка → «Исполнитель ArbExecutor»): «Проверить подключение» → строка «Версия»
   v1 / v2. Кошелёк на v1 → «Развернуть исполнитель» → в окне сверить кошелёк, стоимость, обёртку (= WBNB), SHA-256
   `940fc09907eb0a746aa2232fb33b01f2a13b8f52d38b37ab523ff2788bba45dc` → «Подтвердить и отправить» → дождаться «Код в сети совпал с репозиторием … версия v2, обёртка … =
   dex.native_wrapped».
4. Первым — кошелёк строки «Пробы и сигналы» (газ обёртки BNB перемеряется сам после его сверки v2), затем кошельки
   бирж и «DEX ↔ DEX» — в любом порядке.
5. После переразвёртывания: пулы Squad получают путь исполнения только у кошельков со сверенной v2. В списке DEX
   интерфейса (название DEX + строка исполнителя, pools/dex_rules.rs for_ui — по кошельку строки «Пробы и сигналы»):
   «исполнитель: шаг V3 — исполнимо через ArbExecutor»; при v1 или не сверенном исполнителе — «без пути исполнения: …»
   с точной причиной (версия / «не сверен»).
6. Проверка — раздел «Что проверить» ниже (сухая сделка BNB; при Squad — сухая сделка монеты с пулом Squad в режиме
   «как пойдёт сделка»).

## Если что-то не так
- «код по адресу … не совпал ни с v2 …, ни с v1 …» — адрес не наш или бот старой версии: адрес не использовать.
- «исполнитель … версия v1, executeNative нет — нативный BNB не исполняется» — версия у кошелька не совпала с кодом в
  сети; нажмите «Проверить подключение» исполнителя (версия перезапишется по коду).
- «обёртка в исполнителе … ≠ dex.native_wrapped …» — см. шаг 4 порядка.
- Вернуть старый исполнитель: «Записать после проверки» со старым адресом (версия станет v1). Если проверка нового
  адреса не прошла, прежний адрес и его сверенная версия возвращаются как были (ревью 272, Б2).
