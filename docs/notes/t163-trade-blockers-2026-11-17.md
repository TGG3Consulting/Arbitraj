# t163 — четыре причины, по которым кандидаты не доходят до сделки (разбор 17.11.2026)

Исходные данные — журнал живого бота за 16.11.2026 20:03–22:04 UTC (сборка 8fe83aa1; биржи bingx, mexc, gate, kucoin,
bitget, xt, poloniex + bsc_dex): сделок 13, отказов кандидатов ~52 900. Разбор — по коду рабочей копии (ветка
t163/trade-blockers от 906ba0d9, ссылки «файл:строка» — на неё) и по официальной документации бирж.
Метки: **факт кода**, **факт документации**, **факт ответа API**, **не доказано** (нужна проверка на сервере).

## 1. XT: «минимальный депозит неизвестен — сделки нет» (2683 отказа)

**Где рождается.** `src/core/dirctx_venue.rs:92-104` (`DirCtx::check_deposit`, решение 35): у сети монеты на бирже B
`deposit_min = None` → `Fail::Stop`. Вызов — `src/core/costs.rs:122` (каждый расчёт объёма направления «… → B»). То же
правило у перегона застрявшей монеты — `src/core/relay_value.rs:86-87`. Это отказ на первом же расчёте подбора — счёт
не тратится, но направление DEX → XT (и любая биржа → XT) не торгуется **никогда**.

**Откуда бот берёт минимум у XT (было).** `src/venues/xt/networks_parse.rs:148`:
`deposit_min: absent_ok.then_some(Decimal::ZERO)` — поле ответа не читается вообще; `absent_ok` — настройка
`venue.deposit_min_absent_ok [xt]` (`src/venues/xt/wallet.rs:236`). Шапка `networks_parse.rs:18-19` утверждала:
«Чего в документации НЕТ: минимума депозита». FIRST_RUN (строка про XT) — «до решения Тиграна не задавать». Итог:
настройка у xt не задана → `None` → отказ на каждом расчёте (**факт кода**; что настройка на живом боте не задана —
следует из текста отказа, значение — в промпте П1 ниже).

**Что говорит официальная документация сейчас (факт документации).** https://doc.xt.com/docs/spot/Deposit&Withdrawal/GetSupportedCurrencies
(GET /v4/public/wallet/support/currency, без параметров, путь `public`) — у каждой сети `supportChains[]`:
`depositMinAmount` — «Minimum deposit amount»; там же `depositFeeRate` — «Deposit fee rate (percentage)»,
`depositConfirmations` — «Deposit confirmation block count», `withdrawPrecision` — «Withdrawal amount precision»,
`withdrawFeeCurrency`. Пример: `"chain": "Bitcoin", "depositMinAmount": 1, "depositFeeRate": 0.2,
"depositConfirmations": 2, "withdrawMinAmount": 10, "withdrawPrecision": 4`. В старом зеркале документации на GitHub
(`xt-com/xt4-api`, `_deposit_withdrawal/supportedCurrenciesGet.md`) этих полей нет — бот писался по нему.

**Живой ответ (факт ответа API, прочитан 17.11 через WebFetch, без записи в файл — сырой файл записать на сервере, П1).**
`depositMinAmount` есть у всех просмотренных сетей; сеть BSC называется `BNB Smart Chain`:

| Монета | depositMinAmount (BNB Smart Chain) | depositEnabled | depositFeeRate | depositConfirmations |
| --- | --- | --- | --- | --- |
| USDT | 0.1 | true | 0 | 15 |
| USDC | 0.01 | true | 0 | 15 |
| WIN | 0 | true | 0 | 15 |

**Причина (факт кода + документации):** бот не читает поле, которое XT отдаёт и документирует.

**Исправление (коммит «t163 XT»).** `networks_parse.rs`: `deposit_min = depositMinAmount` (> 0); поле нет или «0» — как у
Bitget / HTX / Phemex / CoinEx (урок 21: «0» и пусто могут значить разное) — по `venue.deposit_min_absent_ok [xt]`.
Значение не придумывается. Решение 365.

**Что остаётся владельцу (WIN и все монеты с `depositMinAmount = 0`).** Вопрос ниже, в «Вопросах».

## 2. Gate: «кадра стакана пары нет N мс (venue.book_stale_ms …)» (сотни на монету)

**Где рождается.** `src/venues/gate/book.rs:138-152` (`Books::freeze`): котировки нет, если последний кадр пары старше
`venue.book_stale_ms` и **нет действующего подтверждения тихой пары** (`until` — решение 213). Тот же текст и то же
правило — у всех 14 бирж (`<биржа>/book.rs`, строки с «кадра стакана пары нет»).

**Как Gate шлёт стакан (факт документации + факт ответа API).** Spot WebSocket v4
(https://www.gate.com/docs/developers/apiv4/ws/en/), канал `spot.order_book`: «Periodically notify top bids and asks
snapshot with limited levels», уровни 5/10/20/50/100, интервал 100ms/1000ms; шлёт ли кадр без изменений книги — НЕ
сказано. Живая запись 04.11 и случай 07.11 (решение 213, `gate/mod.rs:315-321`): кадры идут только при изменении книги,
у тихих пар кадров нет часами при живой подписке. Живость соединения — `spot.ping` → `spot.pong` («Check if connection to
server is still alive»), бот считает любой кадр (и pong) признаком живого соединения (`gate/book.rs:16-22`).
Итог: у Gate «нет кадра» = «нет изменений», а не «стакан устарел», если соединение живо и подписка цела.

**Сверка тихих пар есть — почему не спасает (факт кода).** Сторож пар (`core/feed_watch.rs`, решения 202/213/t79)
спрашивает биржу по REST и подтверждает тихую пару (`book_confirmed` → `until`). Но:
- спрашивает только пары, молчащие дольше `venue.book_stale_ms × venue.pair_dead_mult`
  (`core/feed_watch_logic.rs:111, 131-150, 160-166` — `fresh` по `dead_after`, у свежей пары `continue`);
- а котировка отказывает уже после `venue.book_stale_ms` (`gate/book.rs:141`);
- ответ, пришедший, пока последний кадр моложе `book_stale_ms × pair_dead_mult`, выбрасывается
  (`core/feed_confirm.rs:200-204`).

Пример на советах FIRST_RUN (Gate: `pair_dead_mult = 3`, `pair_resub_interval_ms = 3000`; `book_stale_ms` возьмём 5000):
пара молчит 5 с → отказ «кадра нет 5000 мс»; сторож спросит биржу только после 15 с тишины + до 3 с до прохода. Пара,
у которой книга меняется раз в 6–14 с (обычная «полутихая» монета), **никогда** не подтверждается и стоит в отказе
большую часть времени — между кадрами. Это и есть ложные отказы: стакан верный, соединение живо, биржа просто молчит,
потому что книга не менялась. Защита «не торгуем по устаревшему» тут ничего не ловит — она только теряет сделки.

**Исправление (коммит «t163 сторож»), для всех 14 бирж — общая логика ядра.** В режиме подтверждения (адаптер умеет
`book_version` и заданы `venue.quiet_confirm_*`) сторож спрашивает биржу, когда пара **станет** устаревшей для котировки
раньше следующего прохода: тишина > `book_stale_ms − pair_resub_interval_ms` (не меньше нуля). Ответ учитывается, если
кадр не пришёл после отправки запроса (раньше — «если кадр старше book_stale_ms × pair_dead_mult»). Повторный запрос
по паре — как и было, не чаще `venue.quiet_confirm_min_ms`, на площадку — не чаще `venue.quiet_confirm_max_per_s`; сброс
срока проверки — только когда после неё пришёл новый кадр. Срок свежести подтверждённой пары тот же (отправка +
quiet_confirm_min_ms + интервал прохода), живость соединения обязательна, как раньше. Переподписка мёртвых пар
(режимы без подтверждения, круги 202) — без изменений (`dead_after`). Новых настроек нет. Решение 366.

Чем это не ослабляет защиту: стакан пары свеж только по ответу биржи «книга та же» (номер у Gate, содержимое у
остальных — как и было), просто вопрос задаётся вовремя. Если книга менялась, а кадра нет — «кадры потеряны» и
переподписка, как раньше.

Что ещё может давать отказ у Gate (**не доказано**, нужен журнал сторожа и настройки — П2): ведро
`venue.quiet_confirm_max_per_s` меньше числа тихих пар / `quiet_confirm_min_ms` (запросы не успевают — пара ждёт),
ошибки REST (CheckFailed), исход Unchanged (у Gate без уровней — стакан не ставится). USDC_USDT в списке (246) —
пара у Gate ликвидная; по журналу видно, есть ли у этих отказов хвост «подтверждение биржи истекло».

**Доработка по независимому ревью (Н2, 17.11).** Первая версия спрашивала заранее ВСЕ пары с тишиной > book_stale_ms
− interval: спрос — все пары с кадрами реже ~2 с, а ведро даёт за проход не больше `venue.quiet_confirm_max_per_s`
(`feed_confirm.rs` Bucket: запас 1 с; проход — раз в `pair_resub_interval_ms`), и доставалось оно первым по списку
снимка — совсем тихие пары могли остаться без проверок. Исправлено (решение «366 (ревью t163, Н2)»):
- раньше спрашиваются только пары, нужные торговле сейчас (`core/feed_need.rs`: «держится» / «кандидат» на «Живом
  экране», очередь расчёта `queued` — снимается после расчёта, `candidates.rs:189`; монеты идущих сделок —
  `feed_hold.rs` holders); остальные — как до 366;
- ведро — по сроку ожидания, нужные первыми, без бесконечного голодания (`core/feed_confirm_queue.rs`, доказательство в
  шапке);
- «книга изменилась, кадр в пути» (пункт д ревью). По коду сравнение этого НЕ различает: `verdict` (`feed_confirm.rs`)
  даёт Lost, если номер/содержимое REST новее последнего кадра и книга менялась после подписки; спасает только правило
  «кадр пришёл после отправки запроса — ответ не нужен». Пуш бирж идёт пачками раз в 100–1000 мс (Gate
  spot.order_book 100/1000ms, XT depth 1000 мс, BingX 300 мс, Bitget 200 мс), поэтому запрос сразу после изменения книги
  получит «новее» при живой подписке. Ограничено: у нужных пар первое «новее» не переподписывает — повторная сверка
  следующим проходом (venue.pair_resub_interval_ms — больше интервала пуша при советах FIRST_RUN); кадр пришёл — сверка
  снята; второе «новее» без кадра — кадры потеряны и переподписка, как всегда. У обычных проверок поведение прежнее —
  ранняя проверка число переподписок не увеличивает (каждая ранняя «новее» требует двух ответов подряд без кадра);
- сводка core.feed_watch: «отложено ведром», проверки нужных пар и их исходы — видно, хватает ли ведра;
- ёмкость: quiet_confirm_max_per_s × quiet_confirm_min_ms / pair_resub_interval_ms пар (в первом тексте FIRST_RUN / TASKS
  было «/ 1000» — ошибка).

## 3. Узел BSC: «Блок N создан N мс назад — больше feed.max_block_age_ms» (475) и «Последний блок N получен N мс назад — больше feed.stale_after_ms» (302)

**Где рождаются (факт кода).**
- «получен … назад»: `src/venues/bsc_dex/node/heads.rs:81-96` (`Heads::fresh`): часы бота сейчас − `received_at` (момент,
  когда опрос `eth_blockNumber` увидел рост номера, `heads.rs:173-183`) > `feed.stale_after_ms [bsc_dex]`. Только часы
  бота — рассинхрон серверов сюда не входит.
- «создан … назад»: `src/venues/bsc_dex/node/head_age.rs:84-118`: часы бота (`Utc::now().timestamp_millis()`) − время
  последнего известного блока в мс (timestamp·1000 + доля секунды из mixHash, BEP-520, `node/block_ms.rs`) >
  `feed.max_block_age_ms [bsc_dex]`. Здесь рассинхрон часов сервера бота с сетью входит в возраст напрямую.
- Что при превышении: `Heads::fresh` — StaleData у всех котировок и проверок DEX (`heads.rs:79-80`, вызывающие —
  quote/*, exec/*, check/* — шапка `heads.rs:12-13`): отказ всех направлений с DEX и циклов DEX ↔ DEX, пока голова не
  станет свежей; переход «свежо ↔ устарело» — одна запись `venue.head_age`.

**Расчёт возраста — проверено (факт кода).** Единицы: мс и мс (`head_age.rs:85`, `block_ms.rs:22-27`); часовой пояс:
оба значения — Unix-время (UTC) — сдвига нет; округление до секунд — исправлено решением 259 (доля секунды из mixHash;
`mixHash ≥ 1000` — доля 0, возраст не занижается). Ошибки в формуле нет.

**Из чего складывается «возраст» при узле на другом сервере (факт кода, величины — не доказано).** Возраст в момент
проверки = (время, пока блок дошёл до узла) + (до одного периода опроса) + (RTT `eth_blockNumber`) + (RTT
`eth_getBlockByNumber` новой головы) + (рассинхрон часов сервера бота и сети). **Найдено в коде:** цикл опроса
(`heads.rs:189-239`) спит `bsc.blocks_poll_ms` ПОСЛЕ работы круга, а работа включает оба запроса к узлу по сети, —
фактический период опроса = `bsc.blocks_poll_ms` + оба RTT + запись журнала, а не «раз в bsc.blocks_poll_ms», как
написано в шапке и в каталоге настроек. С узлом на другом сервере это добавляет к обоим «возрастам» до двух RTT на
круг. **Исправление (коммит «t163 опрос блоков»):** круг держит ритм — спит остаток периода (период минус время работы
круга, не меньше нуля). Решение 367. Больше ничего в логике не меняется.

Оценить по выгрузке, что дало отказы (порог мал, часы, сеть, узел отстаёт) — нельзя: нужны факты с серверов (П3).

## 4. Минимумы, найденные только на финальной котировке (poloniex minNotional 361, kucoin 250, bitget 176)

**Где рождаются (факт кода).** `src/core/profit.rs:176-185` — отказ «финальная котировка: …» после успешного подбора
объёма. Тексты: `src/core/costs_quote.rs:148-177` (`order_limits`: «сумма ордера N меньше minNotional»),
`src/core/costs_withdraw.rs:96-104` (`return_b`: «возврат N USDT с B меньше минимума вывода»).

**Подбор уже учитывает минимумы с начала (факт кода).** Каждая точка подбора — тот же полный расчёт `costs::evaluate`
со всеми минимумами (TooSmall); нижняя граница — бисекция «меньше минимума» (`size_bounds.rs:94-141`), и если даже
наибольший объём бюджета меньше минимума — отказ сразу («даже наибольший объём … меньше минимума», `size_bounds.rs:
105-111`). Лучшая точка берётся только среди допустимых (`size_memo.rs:165-173` — только `Ok`). Значит, до финальной
котировки доходит объём, который **на котировках подбора** проходил все минимумы.

**Почему тогда падает финальная котировка (факт кода + не доказано, что это все случаи).** Финальная котировка —
другой расчёт в другой момент: `profit.rs:176-178` пересчитывает `choice.qty` внутри `quote_stage::final_scope`; DEX
отдаёт котировку исполнителя (граф / «лучший из двух» / KyberSwap — `bsc_dex/venue.rs`, `quote/graph_fit.rs`,
`best_of/quote.rs`), биржа — стакан на эту миллисекунду (после подбора, который идёт сотни мс — секунды). Если прибыль
падает с ростом объёма (проскальзывание), лучшая точка подбора — **на самом минимуме** (`choice.qty = min_qty`), и
любое ухудшение цены на финальной котировке на волосок уводит её под minNotional / минимум вывода USDT → TooSmall.
Это объясняет механизм; доля таких случаев — по тексту отказа: в нём есть «оптимум X …; допустимо MIN–MAX»
(`profit.rs:333-363`) — П4.

**Ранний отказ ДО подбора (просили посчитать).** Уже есть по сути: первый расчёт нижней границы — на наибольшем объёме
бюджета (`size_bounds.rs:104-111`); если и там меньше минимума — отказ «подбор объёма: даже наибольший объём …». Эти
787 отказов к нему не относятся: у них подбор нашёл допустимый объём (иначе текст был бы «подбор объёма», а не
«финальная котировка»). Отдельный ранний отказ их не уберёт.

**Покрывает ли t159 (ветка /home/claude/arb159, только чтение).** `core/size_scan.rs` (решение 343) — участки
допустимости продажи по minNotional / maxNotional по худшей цене стакана B (несвязное множество внутри подбора).
Случай «оптимум на минимуме + финальная котировка чуть хуже» он **не** покрывает: участки строятся по стакану подбора,
финальная котировка — позже и по другой цене; минимум вывода USDT (возврат с kucoin / bitget) монотонен и в участки не
входит (`t159` заметка, строка 26 таблицы).

объём больше выбранного** (точки подбора есть в `Memo`, их надо отдать из `size_search::search_in` вместе с `Found`) и
пересчитать финальной котировкой один раз; прошёл пороги — сделка, нет — прежний отказ с обоими текстами. Это не

## Ревью: XT — счёт зачисления депозита и как держать «→ XT» выключенным (Б1, Б2)

- На какой счёт XT зачисляет депозит — **не установлено**: страницы Get deposit history, Get supported currencies и

  - venue.deposit_min_absent_ok [xt] не трогать (= нет): тогда по 266 монетам с «0» направление закрыто и так.
