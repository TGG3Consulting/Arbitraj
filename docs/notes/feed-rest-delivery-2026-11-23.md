# Время доставки REST-подтверждений и восстановление стаканов

Сторож спрашивал все пары прохода одновременно. После завершения всех запросов он разом перечитывал снимок площадки. У результата каждой пары было собственное время получения. Быстрый ответ при этом ждал самый долгий запрос. Затем обработка согласно порядку запуска могла дополнительно ждать записи в журнал по соседним парам.

Сторож теперь отдаёт завершившиеся ответы в порядке готовности, параллельно с остальными запросами. Пара проверяется по текущему состоянию подписки. Пришедший позднее кадр и более новая подписка отсеивают устаревший REST-ответ. Лимит запросов на площадку, расписание и защитные проверки хранятся в прежних местах. Размер очереди ответов равен размеру уже разрешённого прохода. Соседние стаканы в ответ на одну пару материализовать не требуется.

В существующей сводке потока выводятся число REST-ответов, максимальный разброс моментов получения внутри одного прохода и максимальное ожидание готового ответа до начала его обработки. Первая величина времени показывает, сколько первый ответ того же прохода ждал бы общего барьера. Длительные действия по предыдущей паре всё ещё могут задержать начало обработки следующего ответа.

Момент начала фиксируется при первом опросе конкретного запроса, перед вызовом метода адаптера. В этот интервал входят внутренняя подготовка и ожидание самого адаптера. Кадр или переподписка с той же миллисекундной отметкой, что начало проверки, даёт неопределённый порядок. Такой ответ сторож пропускает. Адаптеры, реализующие только прежний метод полного снимка, по-прежнему обслуживают точечный запрос через выбор своей подписки из полного снимка.

На публичном раннере 23 ноября в 18 запросах к книгам ответили все пары. Максимум ожидания раннего ответа на общем барьере для трёх проходов Binance составил 1,26, 1,25 и 1,62 мс. Для XT получено 63,10, 166,62 и 4,51 мс. Два интервала между кадрами BTC при смене подписки на Binance составили 1600,42 и 1699,72 мс. На XT измерено 1004,74 и 995,21 мс. [Исходный артефакт GitHub](https://github.com/TGG3Consulting/Arbitraj/actions/runs/45259025868).

Для отдельной сетевой диагностики GitHub запускает три группы одновременных публичных запросов книг BTC/ETH/USDC и три открытия собственной рыночной подписки BTC на каждой бирже. Моменты получения, версии, ошибки и источник измерения записываются в `public-feed-measurements.json`. Принимаются только непустые двусторонние снимки с положительными ценой и количеством, номер книги после переподключения должен быть не ниже предыдущего. Артефакт отличает время открытия и подписки от периода между последним кадром закрытой подписки и первым кадром следующей.

В сохранённом журнале 23 ноября на Binance есть 67 предупреждений соединения. На XT 39 строк предупреждений о потере синхронизации быстрого стакана. При обрыве Binance сохраняет живой SBE там, где он уже ведёт пару. XT может немедленно выдать страховой снимок. Если такого снимка ещё нет, требуется дождаться очередного достоверного стакана. Число предупреждений не определяет время недоступности пары. Для исторического расчёта интервала нужны времена последнего достоверного кадра, снятия стакана и первого принятого резервного или восстановленного кадра для одной и той же пары. Удалённая проба GitHub измеряет только собственное соединение на публичной точке доступа. Из этого измерения торговые настройки площадок и упущенная прибыль не выводятся.
