# t154 — несколько логов одного пула от одного действия в сети: промежуточное состояние не в ядро (решение 357)

Ветка `t154/off-map-all-kinds`, от HEAD 3ed83fd3. Задача — п. 1 и п. 2 «найдено, не исправлено» ревью 332 (TASKS, DECISIONS
«332 (ревью)»). Требование Тиграна: решение на всё, что есть (все виды пулов, все пути событий), а не на один вид. Ниже —

## 1. Как лог доходит до пула (все пути)

- **WebSocket** (`bsc.pool_events_source` = ws): подписка `logs` пачки (`group.rs` subscribe; две подписки — «все события»
  глубоких пулов и «только ликвидность» мелких), уведомления каждой подписки переносит своя задача в общий канал пачки
  `g.rx` (`group.rs:85-92`). Узел шлёт **по одному уведомлению на лог**, метки «логи блока кончились» нет: bnb-chain/bsc
  `eth/filters/api.go` (FilterAPI.Logs): `case logs := <-matchedLogs: for _, log := range logs { notifier.Notify(rpcSub.ID,
  &log) }`. Порядок внутри подписки — (blockNumber, logIndex).
- **Квитанции блоков по HTTP** (решение 68): задача ленты раздаёт ВСЕ логи блока подпискам разом под замком
  (`node/receipts.rs:152-174` deliver → `tx.send(raw)` по каждому логу), дальше — та же задача переноса `group.rs:87` в
  `g.rx`. Метки «блок кончился» в канале тоже нет; сессия видит логи по одному.
- **Сессия пачки** (`session.rs:105`): лог глубокого пула → `listen_log::on_log` (`session.rs:227`). Пары общего контракта
  WooFi — `per_block.rs:135` on_member_log (перечитать все пары на блоке лога); пары многомонетного пула (Multi) —
  `listen_site.rs:129` (load_group на блоке лога). Полосы (решение 330, ветка t153, только чтение `/home/claude/arb153`
  `session_lanes.rs`) зовут тот же `listen_log::on_log` по логу, события одного пула — по одному, по порядку.
- **listen_log::on_log**: отброс учтённого (`listen_log.rs:82`, `registry.rs:86` has_applied), применение (`events.rs:105`
  apply → разбор вида; Updated / Bins отмечают позицию лога `events.rs:136-138`), затем ветка: Updated (`:104`) — как есть
  (V3/CL/Algebra — off_map), Bins (`:122`) — перечитать бины события **на блоке события** (`:193` reread_bins, тег блока —
  состояние на КОНЦЕ блока), Refresh (`:128`) — пул целиком на блоке события (`refresh_event.rs` → `load.rs:496-498`:
  synced_block = блок, synced_log = None — **остальные логи этого блока отбрасываются**, состояние — конец блока). После
  ветки — пул ядру (`listen_log.rs:172` emit) и он же уже лежит в реестре, откуда его берут котировки (`quote/select.rs:68`
  и др. — только valid).

Отсюда общий признак опасного случая: состояние в памяти после лога N из нескольких логов одного пула **не равно ни одному
состоянию хранилища контракта** (ни в какой момент выполнения), и по нему котировка может дать больше, чем даст сеть.

одного пула. «Промежуточное» — после первого из них память отличается от любого реального состояния.

## 3. Граница: вызов, транзакция или блок

- **Граница «блок»** (ждать все логи пула блока) невозможна без задержки всех пулов: метки конца блока нет ни у
  WebSocket (раздел 1, geth шлёт лог за логом), ни в канале пачки у квитанций; «следующий лог другого блока» в тихой пачке
  может не прийти до следующего блока. Ждать её — задержать на блок КАЖДЫЙ пул с одним логом (запрет владельца).
- Поэтому граница — **«пока ИЗВЕСТНО, что логи пула ещё идут»**:
  1) лог, за которым по коду контракта в том же вызове всегда идёт ещё лог пула (Integral SwapFee → Swap; LB
     CompositionFees → DepositedToBins) — известно без узла;
  2) пулы из бинов: в тот же запрос, что читает бины события (тег блока = конец блока), добавить активный бин у узла на
     конце блока (LB getActiveId, Infinity Bin getSlot0). Активный бин меняет только обмен, последний Swap обмена несёт
     конечный бин (LBPair.sol L520 emit на каждом бине с вводом; цикл кончается только на бине, где остаток входа стал 0 — то есть на
     бине с вводом и логом, L507-L534; Infinity Bin — Swap несёт activeId после обмена: research/flow/bsc_v4.md, раздел 4,
     `events_bin.rs` swap). Значит, «активный бин памяти ≠ активному бину конца блока» — факт,
     что логи этого пула в блоке ещё не применены (свои или других tx).
- Состояние между транзакциями блока реально, но по нему тоже нельзя торговать, если известно, что оно уже не последнее —
  правило 2 закрывает и этот случай для бинов (там память — смесь, а не реальное состояние). У остальных видов состояние
  после каждого лога — реальное (раздел 2), и следующий лог того же блока придёт в той же пачке уведомлений.

## 4. п. 2 «найдено»: чтение на голове ставит valid = true ждущему повтора — риск?

Да. Факты: StaleData при перечитывании бинов события (`listen_log.rs:159-166`) → valid = false, Invalidated, пул в очередь
повтора (`stale_read.rs:46`); событие уже применено (активный бин сдвинут, `events.rs:136-138`), бины НЕ перечитаны. Пока
ждёт, Bins-события применяются без чтения (`listen_log.rs:101`). Голова LB (`per_block_lb.rs:31-35` ready — пул с
LbBin и бинами) читает и при `lb_head::same` (активный бин и ЕГО резервы равны памяти) пишет `lb_head::renewed` →
`load.rs:498` valid = true. «Равны» не видит неактивные бины: WithdrawnFromBins из бина, не являющегося активным, со
сбоем перечитывания → в памяти у этого бина старая (большая) ликвидность → пул снова достоверен → котировка в эту сторону
завышена. Исправление — в lb_head.rs (раздел «Что сделано»).
