# Отказы «расчёт не уложился в срок 5000 мс» — разбор узкого места (решение 129)

Живой случай 03.11: свой узел BSC (127.0.0.1, голова 0,7 с), 17 отказов за ~4 мин, почти все с 16:34:20 — в момент
включения MEXC (`venue.enabled[mexc]`), один в 16:16. Монеты USDC, ASTER, BEAT, CLO, LYN, FAR, CAT (bsc_dex → bingx),
AKE, BROCCOLIF3B, CREPE1. Включены `dex.intermediate_enabled`, `dex.route_gas_aware`, граф-роутер со сплитами,
исполнитель, `bsc.node_http_rps` = 500, `dex.pools_per_sub` = 1000, `index.factory_scan`. Срок — `profit.calc_timeout_ms`
= 5000. Прежний текст причины «узел медлит или перегружен» был догадкой: код не знал, где стоит расчёт.

Разбор — по коду, без запуска на живом. Точный ответ даст замер этапов (ниже): после выкладки причина отказа сама
скажет, на каком этапе стоял расчёт и ждал ли он узел.

## Путь расчёта

`candidates::run` → `tokio::spawn(calc_one)` (без предела, если `profit.calc_concurrency` не задана) →
`profit::decide`:

1. `DirCtx::build` — синхронно, всё из памяти ядра (справочник сетей, σ, правила пар). Запросов нет.
2. `limits::budget` — только настройки и учёт (баланс не читается, решение 94). Запросов нет.
3. `size_search::search` — **последовательно** до `size.max_evals` полных расчётов `costs::evaluate`; каждый:
   - котировка A (`costs_quote::quote` → `Venue::quote`);
   - стоимость вывода A (`costs_withdraw::withdraw_a`: у биржи — справочник в памяти; у DEX — `wallet/transfer_cost.rs`:
     замер газа из проверки × `gas.wei`);
   - котировка B **дважды** (доля глубины `h` и сам объём);
   - возврат USDT (`return_b`: биржа — справочник; DEX — `withdraw_cost`);
   - курсы затрат (`convert::rates` → котировка BNB у бирж по порядку — стакан в памяти).
4. Финальная котировка — ещё 1–3 `evaluate` в `quote_stage::final_scope` (при `exec.via_kyber` — запрос KyberSwap).

Биржевые котировки (BingX `book.rs`, MEXC `book.rs`) — проход по стакану в памяти и комиссия из памяти: REST в
расчёте нет. Значит, всё время расчёта — котировки DEX (их до 2 × `size.max_evals` + финальные на кандидата).

## Что исправлено (решение 129)

- `pools/graph.rs` `cached`: граф строится один раз на состояние реестра (версия реестра растёт при любой записи —
  `put`/`update`/`retain`), блок головы и настройки графа (`dex.route_max_pools_per_edge`, полоса, порог, гистерезис,
  USDT); все котировки этого состояния берут готовый снимок (`Arc`). Результат тот же: граф зависит только от этих
  входов. Проверка — `tests/bsc_dex_graph.rs` (тот же снимок без изменений; новый — после записи и нового блока; равен
  построенному заново).
- `pools/depth_key.rs`: ключ кэша глубины — отметки синхронизации пулов пары без копирования записей
  (`Registry::pair_marks`).
- `quote/route_gas.rs`: пулы «WBNB — USDT» берутся один раз на котировку, а не на каждый путь (`rate::best_in` — та же
  математика). Проверка — `tests/bsc_dex_route_gas.rs` (газ пути = `rate::to_usdt`).
- Торговая логика, выгодность, пороги и значения настроек не менялись.

## Замер этапов (всегда, без настройки)

Ядро (`core/calc_timing.rs`) ставит замер на задачу расчёта: этапы `контекст направления`, `бюджет`, `подбор объёма`,
`финальная котировка`, части — `котировка A <площадка>`, `котировка B <площадка>`, `стоимость вывода <площадка>`,
`стоимость возврата USDT <площадка>`, `курсы затрат` (части одного имени складываются: время, сколько раз). Адаптеры
сообщают запросы в счётчик шлюза (`gateway/calc_meter.rs`): узел BSC (`node/pace.rs` — вызовов, ожидание очереди
темпа, ответ) и агрегатор (`kyberswap/rest.rs`). Плюс «очередь до старта» — от постановки в очередь до первого шага
расчёта (если велика — рантайм tokio перегружен).

Причина отказа по сроку теперь, например:

```
расчёт не уложился в срок 5000 мс: стоит на этапе «подбор объёма» → котировка A bsc_dex 3210 мс; очередь до старта
1.2 мс; этапы: контекст направления 0.1 мс; бюджет 0 мс; подбор объёма 5000 мс [котировка A bsc_dex 1650 мс ×9
(узел 2 запр., очередь 0.3 мс, ответ 1.1 мс), стоимость вывода bsc_dex 0.4 мс ×9, котировка B bingx 0.2 мс ×18,
курсы затрат 0.1 мс ×9]; запросы за расчёт: (узел 2 запр., очередь 0.3 мс, ответ 1.1 мс)
```

Как читать: много времени в части DEX при почти нулевых «очередь/ответ» узла — счёт (CPU, п. 1–5); большое «ожидание
очереди» узла — темп `bsc.node_http_rps` и другие классы; большой «ответ» — сам узел; большая «очередь до старта» —
голодание рантайма. Повтор отказа на том же этапе и части в журнал не пишется (ключ без чисел).

У прошедших и отклонённых по другим причинам — то же в поле `timing` строки «Кандидатов»: «Живой экран» → карточка
кандидата → «Время расчёта: … мс» (раскрывается таблица этапов и частей).
