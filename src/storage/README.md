# storage — хранение

| Файл | Что делает |
| --- | --- |
| `db.rs` | Открывает SQLite (`<data-dir>/arb.sqlite`), создаёт таблицы, выполняет запросы в отдельном потоке; решение 218 — `open_existing`: уже существующая база для внешней программы (чтение или запись с исключительной блокировкой — бот должен быть остановлен) |
| `journal.rs` | Журнал: запись + живой поток в интерфейс |
| `journal_op.rs` | Решения 341, 354: операции очереди журнала — запись, повторяющаяся строка с меткой, обновление по метке, «забыть» метку; у каждой — свой живой поток; выполнение в транзакции пачки |
| `journal_writer.rs` | Решения 341, 354: поток-писатель очереди журнала — пачки по journal.batch_max, карта «метка → id», живой поток с настоящими id |
| `journal_counted.rs` | Решения 155, 354: повторяющиеся строки журнала через очередь без ожидания базы (counted_queued, update_queued, forget_queued) |
| `journal_queue.rs` | Решение 341 (всегда): очередь записи журнала, одна на базу — свой поток ОС пишет пачками (journal.batch_max) по порядку; предел длины journal.queue_max (потеря — запись `journal.queue_lost`); чтение дожидается записанного (flushed); закрытие базы дописывает очередь |
| `ledger_db.rs` | Решение 353: учёт ядра в своём файле `<data-dir>/ledger.sqlite` (core_state, daily_result, wallet_queue): писатель — своё соединение в своём потоке ОС, чтение — второе соединение; synchronous — ledger.synchronous; прямой режим для src/bin |
| `ledger_move.rs` | Решение 353: перенос недостающих и более новых строк учёта из основной базы в ledger.sqlite при открытии (основная база не меняется) |
| `write_modes.rs` | Решения 341, 353: настройки journal.queue_max, journal.batch_max, ledger.synchronous — на лету |
| `rules.rs` | Правила шлюза: список, создание, изменение; решение 354 — список из снимка в памяти (Db::rules_cache: при открытии базы и сразу после изменения, под замком основной базы) |
| `wallet_queue.rs` | Состояние очереди кошелька DEX (переживает перезапуск) |
| `episode_files.rs` | Файлы эпизодов арбитражной ситуации (решение 74): `<data-dir>/episodes/<id>.jsonl.zst`, запись в отдельном потоке, занятое место; решение 255 — чтение потоком (`each`) |
| `episodes_db.rs` | Список эпизодов (таблица `episodes`: id, начало, JSON сводки) |
| `windows_db.rs` | Список окон (решение 125; таблица `windows`: id, начало, тикер, была ли сделка, итог, JSON сводки) — страница с фильтрами монеты, сделки и итога. Файлы окон — тот же `episode_files.rs`, папка `<data-dir>/windows` |
| `uncapped_db.rs` | Записи расчёта «без потолка» (решение 141; таблица `uncapped`: вид, id сделки, тикер, начало, JSON) — выборка за период, запись сделки, уборка по сроку; решение 218 — записи сделок для пересчёта по окнам (`deal_rows`) и запись новых строк одной транзакцией (`insert_all`) |
| `venue_state.rs` | Найденные адаптером факты, которые не нужно искать заново (площадка, вид, id → значение) |
| `notify_mirror.rs` | Решение 251 (б): сообщения дубля «Ручного управления» в Telegram (ключ записи → чат, id сообщений, запись, текст) — переживают перезапуск |

Таблицы: `settings`, `settings_history`, `rules`, `journal` (решение 155: столбцы `repeats`, `last_at` — у повторяющихся записей; старая база получает их при открытии, db.rs ADDED_COLUMNS), `wallet_queue` (очередь кошелька DEX — площадка, JSON состояния), `venue_state` (факты адаптеров: блок развёртывания контракта, история пулов V4 — площадка, вид, id, значение), `daily_result` (с решения 353 — в ledger.sqlite; итог дня по датам: фактический и предварительные убытки сделок — core/daily.rs, решение 53), `core_state` (с решения 353 — в ledger.sqlite, как и `wallet_queue`; учёт ядра: сделки, переводы, газ, ручное управление — вид, id, JSON; core/persist.rs). `episodes` (сводки эпизодов, решение 74 — episodes_db.rs). `uncapped` (расчёт «без потолка», решение 141 — uncapped_db.rs). `notify_mirror` (сообщения записей «Ручного управления» в Telegram, решение 251 (б) — ключ записи, JSON; notify/mirror_store.rs). `dex_wallets`, `dex_wallet_map`, `dex_wallet_meta`, `dex_wallet_history` — кошельки DEX и маппинг «биржа → кошелёк» с историей (решение 132; settings/accounts/), ключей там нет — только имя секрета. Сырые сообщения и записи эпизодов — файлы zstd (raw_log.rs, episode_files.rs).
