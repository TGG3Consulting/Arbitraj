## 3. Метод

1. **Журнал** `core.candidate_rejected` целиком (страницы назад, сохраняются только отказы, обрыв продолжается).
   Строка «только из-за запаса»: текст отказа по порогу И `profit` не проходит пороги И `profit + R` проходит.
   Эпизод — монета + направление, разрыв > 120 с (`--gap-s`).
2. **T_real** — решение (`plan.at`) → первая продажа на B завершена, по чистым сделкам. Почему не transfer-секунды журнала:
   отрезок под риском цены начинается с решения и кончается продажей (покупка, вывод, зачисление, перевод на торговый
   счёт); `transit-times-2026-11-09.md` п.1: «зачислен» в хронологии — после to_trading, секунды журнала — только перевод.
   Медиана и p75 по паре (A, B) того же типа направления; < 5 сделок (`--min-pair-deals`) — по площадке-источнику;
   нет и там — «не посчитано». Чистые сделки — как в прошлом разборе: закрыта, продажи только на B, без перегонов, без
   ручных пометок в хронологии.
3. **Цена DEX (А)**: для каждого хопа маршрута котировки продажи — события пула от блока котировки `route.block`
   до блока «решение + T_real» (последний блок с timestamp ≤ момента; метки блоков узла, точность 1 с). База — последнее
   событие ≤ блока котировки (поиск назад до `--lookback` блоков). Нет событий в отрезке — цена не менялась (r = 1).
   r хопа — цена «выход за вход» в целевом блоке / в блоке котировки; доля — произведение; маршрут — среднее по
   `expected_out` долей. **Исход отказа** `cf = (profit + R) + proceeds × (r − 1)`.
4. **Проверка метода**: у сделок биржа → DEX та же модель от блока котировки плана до блока перед блоком нашей продажи —
   сравнивается с фактическим движением продажи (`method_check_deals`: расхождение, совпадение знака, корреляция).
5. **(Б)**: по сделкам DEX → биржа — сколько запаса нужно было, чтобы отсечь каждую убыточную (в USDT, долей выручки и в
   единицах k / доли закрытия / границы σ при T плана), и таблица вариантов. Отказы DEX → биржа: **цены биржи после отказа
   в данных бота нет** — окна стакана (`/api/windows`) пишутся, когда кандидат прошёл (`core/window_run.rs`); скрипт
   считает только, сколько отказов случайно покрыто окном той же монеты на B.
6. **(В)**: перебор значений `price_move_k` (глобально), `closure_share`, `sigma_floor_per_s`, `transit_credit_s` [B],
   `transit_manual_s` [A], `sigma_min_changes = 1` (сетки — `evaluate.py` GRIDS; это перебор, не советы). Для каждого:
   отсечённые сделки (их факт) и допущенные эпизоды «только из-за запаса» (их cf). Итог за период журнала =
   cf допущенных − факт отсечённых; отдельно по одним сделкам за всю историю. **Новая настройка** (кода нет) —
   `NEW reserve_min_share [B]`: запас не меньше доли выручки; считается отдельно, помечена `new_setting`.

## 4. Что посчитается и что нет

| Посчитается | Не посчитается (причина) |
|---|---|
| (А) по строкам и эпизодам: сколько в плюс, сумма cf при T_real мед и p75, по источникам | Хопы видов Bin, Pmm, Solidly, StableSwap, OraclePmm, TickBin, CL-контракт (Algebra, Elastic), Member — разбор цены не написан; счётчик причин в `not_computed_reasons` |
| Проверка модели пула на сделках биржа → DEX | Пул без события за `--lookback` блоков до котировки, а в отрезке события есть — базы нет |
| (Б) по сделкам: убытки, нужный запас, варианты | (Б) по отказам: нет истории стакана биржи (кроме случайно покрытых окнами) |
| (В) по всем существующим настройкам и областям | `sigma_min_changes ≥ 2` (число изменений в плане не пишется); k по монете (перебор только глобально) |
| Сверка записанного запаса с формулой (`reserve_formula_mismatch_rows`) | Отказы без данных расчёта (`no_data`) |
| Диагностика узла: earliest, ответы на блоки (`--node-info`) | Блоки/логи старше earliest своего узла, которых нет в кэше (причина «блок старше …»; архив — только `--archive-url`) |
| | Запрос не уложился в срок (причина «узел не ответил за N с») |

## 5. Допущения (каждое — в README.txt выхода)

1. cf меняет только предельную цену пула, глубина не пересчитывается; цена покупки на бирже и затраты — по плану
   (прошлый разбор: отклонение покупки +3.7 USDT на 983 сделках — мало, но не ноль).
2. Объём — как в записи: бот подбирает объём по прибыли С запасом (`core/size_search.rs`), при другом запасе мог быть иным.
3. Эпизод — не больше одной сделки; строка с повторами — числа последнего повтора.
4. Пороги и настройки запаса каждой строки/сделки — **на её момент** (Calc.at) по `/api/settings` + `/api/settings/history`
   (v2, раздел 8 п.1), с областью «площадка · направление» (решение 242); строки, где запас не сходится с формулой,
   считаются с k по записи (если доля не задана). Вариант перебора меняет ровно одну настройку, остальные — на момент строки.
5. Своё влияние на пул в проверке сделок исключено целиком блоком продажи (берётся блок перед ним).

**8.2. «узел не отдал блок N (обрезана история?)».** Факты: 4199 строк — один и тот же блок 132009995, ещё 5 строк —
132008971, 131563531, 131957771, 132007947. Это блоки СТАРШЕ головы (на 590754 блока ниже головы первого запуска,
на 601088 — третьего), не будущие. Граница по строкам биржа → DEX: не посчитаны строки с моментом 03.11 16:22 —
06.11 12:43:17, посчитаны — 06.11 12:45:41 — 09.11 14:16; наименьший блок котировки у посчитанных — 132011063.
Почему один номер у 4199 строк: v1 кэшировал ответ null на eth_getBlockByNumber (блок старше 64 от головы считался
неизменным), и все следующие поиски блока по времени, проходившие через него, падали из кэша (третий запуск — 121
запрос к узлу). Когда узел впервые вернул null на 132009995 — по файлам не установить. По записям о настройке сервера
(не проверено на сервере) в systemd-юните bsc-node стоят флаги `--history.transactions/blocks/logs=600000`, но живой
geth запущен вручную из tmux — его флаги неизвестны; 600000 блоков сходится с границей (132611083 − 600000 = 132011083), но
это не факт, пока не прочитана командная строка процесса (раздел 6, п. 1.1). **v2:** null не кэшируется (старые
null-строки кэша отбрасываются при загрузке, счётчик `cache_null_blocks_dropped`); earliest — бинарный поиск по
eth_getBlockByNumber (≈ 28 запросов), перепроверка раз в 10 мин (история с обрезкой сдвигается за головой); блок/окно
логов старше earliest, которых нет в кэше, — причина «блок старше самого раннего доступного узлу (earliest = X)» без
запроса к узлу; окно логов, частично старше earliest, обрезается по earliest только если нужная часть не старше;
события «после котировки» обрезке не подлежат (иначе «цена не менялась» вместо «нет данных»). Кэш прошлых запусков
(заголовки и логи старше 64 блоков от головы неизменны) используется и ниже earliest — счётчик
`cache_logs_below_earliest_used`; если диагностика покажет, что узел на логи блока, которого у него нет, БЫСТРО отвечает
пусто, — запуск с `--ignore-cache-below-earliest` (раздел 6, п. 4). Строки и сделки идут от старых к новым — у границы
истории первыми.

**Недостающая история — вариант (не включён).** Метки блоков и логи пулов старше earliest — история цепочки, она есть у
публичных архивных узлов BSC. Внешние узлы для торговли запрещены; для разбора (только чтение истории) — флаг
`--archive-url` (по умолчанию пусто): только eth_getBlockByNumber / eth_getLogs / eth_call, тот же `--rps`, ответы в кэше
с приставкой «arch », запросы в `node.archive`. Какой узел и можно ли — решает Тигран; лимиты провайдера на eth_getLogs
(окно 200 блоков, частота) — проверить по его документации до запуска.

строки до перезапуска в 15:20; запуск 2 — сделки 1…300 из кэша к 15:23:40, дальше ни строки до 15:45. Сделки в

запрос — до 6 попыток × urlopen timeout 60 с (предел каждой операции сокета, не запроса) + паузы 1.5…9 с, ≈ 6.5 мин
без строки в журнале (строка — раз в 50 сделок); узел молчал или отвечал медленно — по файлам не установить (раздел 6,
п. 1.2: eth_getLogs по 132009995 с пределом 60 с). Других мест бесконечного ожидания в коде v1 нет: пауза предела
частоты ≤ 1/rps (но по системным часам), циклы поиска блока конечны, блок «в будущем» отсекался по метке головы.
**v2:** запрос в отдельном потоке с join по сроку — попытка ≤ `--rpc-attempt-s` (20 с), весь запрос со всеми повторами
≤ `--rpc-deadline-s` (60 с), потом причина «узел не ответил за 60 с (метод)»; `--max-timeouts` (5) таких подряд —
остаток фазы пропускается с причиной; пауза частоты — по монотонным часам; в progress.log перед КАЖДЫМ запросом
«узел → метод параметры (попытка N)», ответ дольше 5 с и сбой — отдельной строкой, перед каждой строкой/сделкой — её id
и блоки; `--node-info` — диагностика узла без разбора.

**8.4. r хопа и cf (проверено по коду, без изменений).** Биржа → DEX: продажа на DEX, маршрут котировки продажи —
монета → USDT (первый шаг обязан быть из монеты, иначе «не поддержан»); цена пула — token1 за token0 (V2 reserve1/reserve0
из Sync, V3/CL sqrtPriceX96²); r хопа = цена «выход за вход» в целевом блоке / в блоке котировки: вход token0 → r,
token1 → 1/r; cf = (прибыль + запас) + выручка × (r − 1) — рост цены продажи даёт плюс. Математика пулов и
`deals_check_stats` в v2 не менялись (порядок обхода сделок — от старых к новым — на статистику не влияет); 78 сделок
проверки метода первого запуска моложе границы, их окна логов — в кэше. Ограничение (было и в v1): у пула-синглтона
(Infinity CL / Uniswap V4) порядок токенов берётся сортировкой адресов маршрута — если пул на нативной монете
(адрес 0), а шаги маршрута показывают WBNB, порядок может отличаться; в продаже монета → USDT это возможно только у BNB.
