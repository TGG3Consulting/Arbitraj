# Две сети (BSC + Arbitrum) в одном боте — разбор и план (19.11.2026)

Основа: ветка `feat/arbitrum` от `274801a0` (последняя версия только BSC — ветка `stable/bsc-2026-11-19`).
Источник фактов: четыре разбора кода (ядро+шлюз, 14 бирж+KyberSwap, адаптер DEX, настройки/база/API/UI/тесты),
только чтение, с файлами и строками. Разбор другого ИИ (prompt-multinetwork-analysis.md) учтён и проверен.

## Решение Тиграна (19.11.2026)

- Один процесс, две сети. Запуск — двумя кнопками: можно запустить только BSC, только Arbitrum или обе вместе.
- Кошельки одни и те же на обе сети (один ключ secp256k1 = один адрес 0x… в BSC и в Arbitrum).
- Это меняет план 10.11 («один экземпляр — одна сеть — свой сервер»): нужна сквозная переделка ядра, базы, настроек
  и интерфейса — сеть должна быть в идентичности монеты, в направлениях, в ключах учёта и настроек.

## Факты: что привязано к одной сети

### Ядро и шлюз
1. Монета = `Asset{ticker, bsc_contract: Option<Address>}` (core/types/market.rs:25-57), равенство и хэш — только по
   адресу. От неё — `CoinKey` (core/coin_key.rs) → замки credit_lock, sell_turn, rides, active, manual_waits;
   id области настроек «монета» (settings/scope.rs:87-100, только формат 0x+40); ключи учёта; справочник.
2. `Direction{asset, buy_on, sell_on}` — сети нет. Для биржа↔биржа сеть перевода нигде не записана.
3. Ломается сразу при второй DEX:
   - core/native.rs:35-56 — все DEX обязаны дать одну нативную монету (BNB ≠ ETH → ошибка).
   - core/convert.rs:20 `GAS_TICKER = "BNB"` — хардкод (подписка на стакан газа, предпроверка, учёт газа).
   - core/inner.rs:52 + registry_build.rs:49-66 — один адрес USDT на всё ядро («в BSC»).
   - core/balances_cache.rs:174 `dex_id()` — «первая DEX» (7 вызовов); core/deal_card.rs:25 `"bsc_dex"`.
   - core/subscribe.rs:51-63,213-243 — каждой DEX отдаются все монеты и все промежуточные монеты всех DEX.
   - core/registry_build.rs:131-152 — адрес монеты добавляется в presence каждой DEX.
4. Сеть перевода: core/transfers.rs:58-107, dirctx.rs:155-169, presence.rs:27-60 — одна сеть `venue.bsc_network`.
5. Газ в типах ядра назван в BNB: `gas_bnb`, `tip_bnb`, `bnb_usdt`, `risk.min_bnb_balance` и т. д.
6. Шлюз: `VenueKind{Cex,Dex}` — у площадки нет сети (gateway/contract.rs:26-32); `tx_hash::norm` переводит
   хеш в нижний регистр — для EVM годится, для Solana — нет.

### Биржи (все 14)
- У всех в ответе API есть адрес контракта по КАЖДОЙ сети; адаптер оставляет его только для `venue.bsc_network`
  (условие `is_bsc` в networks_parse.rs каждой биржи). Вывод и адрес депозита берут сеть из запроса ядра.
- Сеть зашита через настройку, а не из запроса: kucoin/withdraw_quota.rs:38, kucoin/fund_move.rs:49,
  okx/fund_move.rs:50, xt/deposits.rs:32; gate — сбор минимумов депозита только по BSC (deposit_plan.rs:42-61);
  coinex — карта «тикер → адрес» без сети (contracts.rs:41-60).
- KyberSwap: chainId 56 в коде (node.rs:29), газ в BNB, переводы в другие сети отклоняет. Выключен, не в приоритете.

### Адаптер DEX
- Адреса контрактов — все из настроек (в коде нет ни одного). Математика, котировка, граф, пробы (eth_simulateV1),
  узел (JSON-RPC, WS, multicall) — EVM-общие.
- Зашито под BSC: chainId 56 (node/mod.rs:49, send/tx.rs:162, connection*.rs); `ID = "bsc_dex"` (ctx.rs:26 +
  9 файлов); тикер газа "BNB" (wallet/balances.rs:30, ~10 мест); 13 из 14 каналов отправки — билдеры BSC
  (send/channels.rs:14-29), для Arbitrum по коду годится только `public`; умный режим — формат PancakeSwap
  (exec/universal.rs:65, quote/mixed_quoter.rs); приёмка исполнителя v3 по записи на пулах BSC
  (exec/executor/live_proof.rs:31-44); газ — только legacy-транзакция, «база газа = 0» (send/tx.rs:13,144-170);
  миллисекунды блока из mixHash (node/block_ms.rs — на другой сети откатится к секундам, не падает).
- Настройки узла `bsc.*` (21 шт.) — область «вся система» и местами читаются через `At::default()`.
- ~20 статиков процесса с ключом Address без сети (pools/, exec/executor/, quote/ — список в разборе).
- main.rs:280-311 — создаётся ровно один адаптер DEX.

### Настройки, база, API, UI, тесты
- Областей «сеть» нет. По смыслу «одна на сеть»: `bsc.*`, `risk.min_bnb_balance`, `kyber.*`, `venue.bsc_network`
  у бирж, `venue.bsc_contract_chain` (coinex), `profit.transit_*`/`transfer.*` у бирж (время по сети разное).
- `venue_dir` id (`bingx:cex_dex`, `dex_dex`) — нет DEX/сети: денежные пороги, лимиты, просадка, closure_share
  BingX→DEX BSC и BingX→DEX Arbitrum сольются.
- Область DEX (адреса контрактов по id индексатора) и область канала — без площадки.
- База: столбца «сеть» нет. Маппинг кошельков `dex_wallet_map(row)` — строка = биржа/dex_dex/probe;
  исполнитель и обёртка — одни на кошелёк (`dex_wallets.executor*`); очередь nonce `queue_key = "{dex}:{wallet}"`.
  Учёт `core_state`: id `gas`, `withdraw_fact`, `deposit_hold`, `transit` (биржа↔биржа) — без сети.
  `windows`/`uncapped` — фильтр по `$.asset.bsc_contract`.
- API: `wallets_dex.rs:41` — «первая DEX»; баланс газа — поле `bnb`.
- UI: Маппинг кошельков, Балансы, Монеты, Сделки, Настройки — одна DEX, «BNB», «адрес BSC».
- Тесты: записанных данных Arbitrum нет вообще (`tests/data/*/arb_*` — это «arbitrage», данные BSC).

## Предлагаемая архитектура (на утверждение)

1. **Сеть — сущность ядра.** `ChainId` — строковый id из настроек (список сетей задаётся в интерфейсе: `bsc`,
   `arbitrum`), ядро конкретных сетей не знает. У сети: какая площадка DEX её обслуживает, тикер газа, обёртка,
   адрес USDT, id цепи (chainId) — всё в настройках площадки DEX этой сети.
2. **Монета = (сеть, адрес).** `Asset{ticker, chain, contract}`; адрес — свой тип, сейчас 20 байт EVM, с местом
   под 32-байтовый адрес Solana. Равенство и хэш — по (сеть, адрес). USDT в BSC и USDT в Arbitrum — разные монеты
   для DEX, но одна и та же монета на счёте биржи (у биржи баланс по тикеру, сети — у ввода/вывода).
3. **Площадка DEX — по одной на сеть**: `bsc_dex`, `arb_dex` — два экземпляра одного кода, id из конфигурации,
   у шлюза — метод «сеть площадки». Настройки узла/каналов/резерва газа — в области площадки DEX.
4. **Направление несёт сеть**: биржа↔DEX — сеть DEX; биржа↔биржа — два отдельных направления, через BSC и через
   Arbitrum, каждое со своими затратами вывода и временем. Это даёт параллельные сделки по одной монете в разных
   сетях без конфликта замков.
5. **Биржи**: имя сети — настройка «биржа × сеть» (вместо одной `venue.bsc_network`); адаптеры отдают адрес
   контракта по каждой сети, а не только BSC.
6. **Кошельки** — те же (решение Тиграна). Маппинг «биржа → кошелёк» не меняется. Меняется то, что по сети:
   баланс, газ, очередь nonce, адрес исполнителя (развёртывается в каждой сети отдельно), обёртка.
7. **Две кнопки запуска**: «Старт/Стоп» по каждой сети отдельно (сеть стоит — её направления не входят в сделки,
   идущие сделки доводятся до конца, как сейчас при «Стоп»).
8. **Старые данные**: всё, что без сети, читается как BSC (serde default + перенос ключей настроек одним
   переносом, как решение 211). BSC после каждого шага работает как раньше — проверка на текущих тестах.

## Порядок работ (BSC работает на каждом шаге)

1. Сеть в типах ядра без изменения поведения: `ChainId`, `Asset.chain` (по умолчанию bsc), id площадки DEX
   и chainId из настроек, тикер газа из `dex.native_ticker`, переименование `*_bnb` → `*_native` с сохранением
   имён в базе. Итог — тот же BSC-бот, тесты зелёные.
2. Ядро «много DEX»: убрать `dex_id()`/«первую DEX», USDT/нативная/газ по сети, presence и подписки по сети,
   сеть в направлении, сеть перевода по направлению. Перенос ключей настроек и учёта.
3. Биржи: адрес контракта и имя сети по каждой сети; исправить 4 места, где сеть зашита настройкой.
4. Управление: две кнопки, кошельки по сети (баланс, исполнитель, nonce), интерфейс.
5. Адаптер DEX Arbitrum: узел, chainId 42161, модель газа Arbitrum, каналы отправки Arbitrum, индексатор пулов,
   список DEX Arbitrum и их адреса — по официальной документации и фактам своего узла; развёртывание исполнителя.
6. Записанные данные Arbitrum для тестов (ответы узла, пулы, квитанции, ответы бирж по сети Arbitrum).
