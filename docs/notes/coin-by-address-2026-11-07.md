# Монета = адрес контракта BSC (решение 211) — проект, 07.11.2026

Тигран, 07.11.2026: «метчить монеты всегда по адресам, только по адресам; сквозная переделка без костылей; ядро не
сломать». Основа — исследования A–D 07.11 (адаптеры, ядро, DEX/API/UI/Telegram, живые данные).

## Факты (до переделки)
- Адрес контракта BSC приходит в бот ТОЛЬКО из REST-справочника сетей каждой биржи (`coin_networks`,
  `CoinNetworkInfo.asset.bsc_contract`; поля: bingx/kucoin/bybit/bitget/binance/phemex/poloniex `contractAddress`,
  gate `addr`, mexc/xt `contract`, okx `ctAddr`, htx — `venue.contract_field`, coinex — `/v2/assets/info`, kraken —
  совпадение адресов ввода и вывода). Всё остальное у бирж — по ИХ тикеру: WS-стакан (символ пары), ордер, вывод,
  адрес депозита, статусы, балансы, события аккаунта, делистинг. Адрес в запросах CEX не используется нигде.
- Ядро: `Asset {ticker, bsc_contract}` — Eq/Hash по обоим полям, тикер один на все площадки; справочник режет монету
  по ключу «адрес|тикер» (решение 118, Я-8). Отсюда: один адрес под разными тикерами = разные монеты, направлений
  между ними нет. Решения 200/206 (обёртка шлюза, склейка тикеров) — заплатка поверх, упирается в занятые тикеры.
- Живые данные 07.11: 45 адресов разрезаны по тикеру (bingx NMT = gate NETMIND = 0x03aa…; bingx FIL = gate FIL3;
  bingx SIDEKICK = kucoin K …); 16 тикеров означают РАЗНЫЕ токены у разных бирж (BOMB, GPT, APX, ART, PIGGY, NFP, BNX,
  POP …). Открытых сделок нет, монет на руках нет.

## Модель после переделки
1. **Идентичность монеты — адрес BSC.** `Asset` остаётся `{ticker, bsc_contract}` (формат JSON и БД тот же), но
   `Eq`/`Hash` — по адресу; у монеты без адреса (не торгуется с переводом; BNB решается решением 62 до сборки) — по
   тикеру, как сейчас в CoinKey. `ticker` монеты ядра — ПОКАЗНОЕ имя (детерминированно: тикер большинства площадок
   монеты, при равенстве — DEX, затем по алфавиту), не ключ.
2. **Тикер у каждой площадки свой.** `Presence.ticker` — тикер этой площадки. Справочник: ключ = адрес.
3. **Один переводчик в ядре** (`core/venue_ticker.rs`): из справочника — (площадка, адрес) → тикер площадки и
   (площадка, тикер) → адрес. Все вызовы шлюза с монетой идут через `on_venue(asset, venue)` (Asset с тикером
   площадки и тем же адресом); всё, что приходит от биржи без адреса (стакан по символу, Balance, Transfer,
   Invalidated, SpotPairs, DelistItem, Costs в монете), переводится в адрес через карту (площадка, тикер) → адрес.
   Это одно место; адаптеры не меняются (им и сейчас приходит Asset, они берут ticker).
4. **Один адрес — два тикера на ОДНОЙ бирже** (OLD/новый): берётся тикер с торгуемой парой и открытыми вводом/выводом;
   иначе оба не годятся — монета на этой бирже не торгуется, журнал (раз на изменение).
5. **Один тикер — разные адреса у разных бирж** — разные монеты (как и должно быть).
6. **Убираются решения 200/206** целиком: обёртка `gateway/aliased*`, `alias_map`, `alias_auto`, настройки
   `coin.ticker_alias*` (из каталога), `/api/coins/ticker-splits`, `/api/coins/ticker-aliases-auto`,
   `TickerAlias.svelte`. Двойного перевода быть не должно.
7. **DEX-адаптер:** налоги и газ перевода (`check/state.rs`) — по адресу; `registry.by_ticker` → по адресу монеты;
   лишний фильтр `quote/mod.rs:136` (`e.ticker == asset.ticker`) убрать; баланс кошелька монеты — по адресу.
8. **Настройки области «монета»** (`Scope::Coin`): ключ — адрес (`coin:0x…`). Миграция при старте: старые `coin:ТИКЕР`
   переводятся в `coin:0x…` по справочнику, если тикер однозначен (один адрес на всех площадках); неоднозначные —
   остаются как есть, журнал и показ в интерфейсе (человек решает). Чтение — по адресу; ручной блок, автоблок
   (недостача зачисления, проскальзывание продажи) — по адресу.
9. **Интерфейс:** `dirKey`/`coinKey` — по адресу (+ площадки); показ имени монеты «NMT / NETMIND» (тикеры площадок);
   делистинг — по тикеру своей площадки; фильтр — по любому тикеру и адресу.
10. **Хранилище:** сделки, эпизоды — JSON совместим (Asset тот же). `windows`/`uncapped` — колонка адреса (миграция
    ALTER TABLE), фильтр окон по адресу или тикеру.

## Опасные места (проверять отдельно)
Вывод (`core/transfers.rs` поиск сети монеты — по адресу), ордер/котировка (тикер площадки), подписка (`subscribe.rs`
wanted/cex_pair — тикер площадки), зачисление (`credit_watch.rs` — по адресу), затраты и балансы в монете (сравнение
с тикером площадки), лимиты вывода (`withdraw_limit` — по адресу).

## Фазы
1. Ядро: тип Asset (Eq/Hash), Presence.ticker, справочник по адресу, переводчик, ticker_index, подписка, тик.
2. Параллельно: (a) ядро — все вызовы шлюза и сравнения по тикеру → переводчик/адрес; (b) DEX-адаптер — ключи по
   адресу; (c) API/UI/уведомления + удаление 200/206 + миграция Scope::Coin.
3. Независимая проверка (агент, не видевший реализацию): тесты на записанных данных (gate/kucoin/bingx справочники),
   сквозной сценарий NMT/NETMIND, 16 тикеров-двойников, все существующие тесты.
