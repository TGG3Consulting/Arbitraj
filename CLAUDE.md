# ARB — миссия, ценности и правила проекта

> Этот файл — главный. Он читается перед любой работой над проектом и имеет приоритет над любыми другими инструкциями.
> Если задача противоречит этому файлу — остановиться и спросить Тиграна. Не домысливать.

## Что это

Система спотового арбитража на разнице цены одной и той же монеты. Два направления, каждое включается и выключается отдельно в интерфейсе (решение 85):
- **BingX ↔ DEX в сети BSC** (PancakeSwap, Uniswap и другие) через свой кошелёк — купить на одной площадке, перевести монету по сети BSC, продать на другой (сделка с переводом между площадками).
- **DEX ↔ DEX в сети BSC** — замкнутый цикл внутри блокчейна (из базовой монеты кошелька через пулы разных DEX обратно в неё же), атомарно одним бандлом в одном блоке, без биржи и без перевода.

Первый этап — сеть BSC. Дальше — новые биржи (Gate, MEXC и другие) и новые сети тем же конвейером.

## Миссия

Зарабатывать на разнице цены одной и той же монеты — **только если прибыль после всех затрат выше порога**:
- **BingX ↔ DEX:** купить там, где дешевле, перевести по сети BSC, продать там, где дороже.
- **DEX ↔ DEX:** пройти замкнутый цикл по пулам (базовая монета → … → та же базовая монета) и получить на выходе больше, чем вложено, — одной атомарной сделкой в одном блоке.

## Что система делает

1. Постоянно слушает цены и ликвидность всех подходящих монет на всех подключённых площадках.
2. Отсекает шум.
3. Считает оба направления с полной стоимостью сделки: для BingX ↔ DEX — обе стороны по монете (A → B и B → A); для DEX ↔ DEX — оба обхода цикла.
4. Исполняет сделку: для BingX ↔ DEX — покупка → перевод → продажа; для DEX ↔ DEX — атомарный бандл свопов по циклу в одном блоке (всё-или-ничего).
5. Сверяет план с фактом и останавливается при любых отклонениях.

## Ценности

1. **Каждая миллисекунда важна.** Всё слушаем постоянно через WebSocket. Никакого опроса «раз в N минут».
   Исключения — номер блока узла BSC опрашивается (решение 57); справочник пулов берётся у индексатора по REST по
   интервалу (решение 58: это список адресов, не цены — цены только со своего узла); события пулов могут браться из
   квитанций блоков по HTTP (решение 68) — настройкой, наряду с WebSocket.
2. **Не торгуем вслепую.** Нет данных или данные устарели — сделки нет.
3. **Только факты.** Данные площадок — только из их API и официальной документации. Непонятно — спросить Тиграна.
4. **Всё под контролем человека.** Всё видно и управляется из графического интерфейса.
5. **Простота для ИИ.** Маленькие файлы, понятная структура, подробные комментарии.

## Жёсткие правила (не нарушаются никогда)

### Торговля
- **Только спот. Фьючерсов в проекте нет.**
- Всегда считаются **оба направления** для каждой монеты, каждое — независимо.
- Первичный фильтр монет: монета есть на споте биржи; биржа выводит и принимает её по сети BSC;
  у монеты есть пул с USDT на DEX (или, если включено, — с промежуточной монетой из списка, например BNB; решение 52);
  **адрес контракта у биржи совпадает с адресом токена в пуле**
  (исключение — BNB: нативная монета без адреса контракта сопоставляется с WBNB по настройке; решение 62).
- Выгодность считается по реальной ликвидности (стакан биржи — по уровням, DEX — по содержимому пула) и учитывает **все** затраты:
  торговые комиссии, комиссию пула, комиссию вывода, газ BSC, налог токена, проскальзывание,
  риск движения цены за время перевода, изменение ликвидности к моменту продажи.
- **DEX ↔ DEX (решение 85):** торгуется тот же граф пулов (решение 80) и исполняется тем же атомарным бандлом свопов (решение 84). Считаются оба обхода цикла, каждый независимо. В затраты входят комиссии всех пулов маршрута, газ BSC (свопы + approve), налог токена на каждом свопе, проскальзывание на каждом шаге, чаевые канала. Комиссий вывода, перевода, депозита, времени в пути и риска движения цены за перевод НЕТ — перевода нет, цикл исполняется в одном блоке. Первичный фильтр «монета есть на бирже / биржа выводит и принимает по BSC» к этому направлению не применяется: нужна только ликвидность пулов маршрута и совпадение адресов токенов в этих пулах.

### Интеграции — только по официальной документации
- **Все интеграции делаются исключительно по официальной документации и API площадки.**
  Каждая подписка на WebSocket, каждый запрос к REST, каждый параметр, поле, код ошибки и лимит —
  только после чтения официальной документации и ответов самого API.
- **Никогда не гадать.** Нет в официальной документации — не придумывать, а спросить Тиграна.
  Противоречие в документации — проверять на реально записанных ответах API, и тоже сообщить Тиграну.
- У каждой функции адаптера в комментарии — ссылка на раздел официальной документации, по которому она написана.

### Архитектура
- Слои: **ядро → шлюз → адаптеры площадок**.
- Ядро ничего не знает о конкретных площадках и работает только со своими типами данных.
- Каждая площадка — изолированный адаптер: свой REST, свой WebSocket, свои подписки, свой разбор ответов и ошибок.
  Наружу — данные в формате ядра.
- Новая площадка = новый адаптер по тому же контракту. Ядро и шлюз не меняются.
- Поведение при сбоях задают **правила шлюза**: общие (на все площадки) и для одной площадки (сильнее общих).
- Стартовое правило Тиграна: **ордер отправлен и не исполнился — отменяем, больше не пробуем.**

### Код
- **Никаких хардкодов.** Ни одного зашитого числа, порога, лимита, таймаута, списка или адреса.
  Всё — в хранилище настроек, меняется на лету из интерфейса, без перезапуска, с журналом изменений.
- **Никаких моков и заглушек.** Нет данных — система это показывает и не торгует. Тесты — только на реально записанных данных.
- Данные площадок (комиссии, сети, шаги цены, адреса контрактов) — только из API площадок.
- Один файл — одна задача, ориентир — не больше 200 строк.
- В начале каждого файла шапка-комментарий: что делает, кто вызывает, от чего зависит.
  У каждой функции комментарий: что принимает, что возвращает, какие ошибки бывают.
- В каждой папке `README.md`; карта модулей — `ARCHITECTURE.md`.
- Ядро не импортирует ничего из папки адаптеров — только из шлюза.

### Готовая фича — это всегда пять частей
1. Код.
2. Её настройки в хранилище настроек.
3. Экран или элементы в графическом интерфейсе — фича полностью управляется и настраивается из интерфейса.
4. Комментарии в коде.
5. Запись в `ARCHITECTURE.md`.

Без любой из пяти частей фича не готова.

Если применимо: важные события фичи — в настраиваемые уведомления Telegram; новое подключение (ключ, токен, адрес) — с кнопкой «Проверить подключение», которая пишет «Подключено» или точную причину сбоя.

## Стек
- Rust: tokio, tokio-tungstenite, reqwest (rustls), serde + sonic-rs или simd-json, alloy (сеть BSC), rust_decimal.
- Настройки и учёт: SQLite с историей изменений. Стартовых значений нет — все параметры задаёт Тигран в интерфейсе; не задан параметр — функция не работает.
- Секреты: зашифрованный файл, пароль вводится при запуске в интерфейсе, ключи только в памяти (docs/SECURITY.md).
- Исполнение — сразу полный автомат, без ручного подтверждения сделок.
- Интерфейс: веб-сервер axum (REST + WebSocket) и веб-интерфейс в браузере на Svelte.
- Сырые сообщения площадок пишутся на диск (zstd) для разбора и подбора порогов.
