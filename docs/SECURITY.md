# SECURITY — ключи и доступы

> Решение Тиграна: ключи хранятся в зашифрованном файле, расшифровываются паролем при запуске и живут только в памяти.

## Какие секреты есть
- API-ключ и секрет BingX — с правом торговли и вывода.
- KuCoin (решение 137): API-ключ `kucoin.api_key`, секрет `kucoin.api_secret` и passphrase `kucoin.api_passphrase`
- Bitget (решение 162): API-ключ `bitget.api_key`, секрет `bitget.api_secret` и passphrase `bitget.api_passphrase`;
  права ключа — спот-торговля (stow), вывод (wwow, только с привязкой IP), перевод (wtow — если включены переводы
  spot ↔ p2p); без фьючерсов, маржи и копитрейдинга; адреса вывода — в адресной книге кабинета (код 11000)
  (задаётся при создании ключа; в запрос уходит только HMAC-SHA256 от неё, Base64). Права: General, Spot, Withdrawal,
  FlexTransfers (переводы main ↔ trade); Margin и Futures — нет. Ключ привязать к IP сервера. Токены WebSocket (bullet)
  — секрет сессии: в журнал и сырой журнал не пишутся.
- OKX (решение 161): API-ключ `okx.api_key`, секрет `okx.api_secret` и passphrase `okx.api_passphrase` (задаётся при
  создании ключа, уходит в заголовок OK-ACCESS-PASSPHRASE; в журнал и сырой журнал не пишется, запрос входа WebSocket —
  тоже). Права: Read, Trade, Withdraw; ключ основного счёта (не субсчёта). Ключ привязать к IP сервера (без IP ключ с
  правами trade/withdraw OKX отключает после 14 дней простоя). Вывод — только на проверенные адреса, заданные в
  кабинете OKX (код 58207).
- Poloniex (решение 169): API-ключ `poloniex.api_key` и секрет `poloniex.api_secret` (passphrase нет; подпись
  HmacSHA256). Права ключа через Spot API не читаются (эндпоинта нет): в кабинете включить торговлю спотом и вывод
  («withdrawal privilege must be enabled for your API key»), без фьючерсов (у фьючерсов — отдельные ключи). Белый список
  IP и адресов вывода — только в кабинете (https://poloniex.com/profile/settings/spot-api-key); вывод через API — без
  подтверждения по почте.
- Binance (решение 160): API-ключ `binance.api_key` и секрет `binance.api_secret`, тип ключа — HMAC (passphrase нет).
  Права (GET /sapi/v1/account/apiRestrictions, «Проверить подключение» читает права ТЕКУЩЕГО ключа): Enable Reading,
  Enable Spot & Margin Trading (у Binance спот и маржа — один флаг), Enable Withdrawals (Binance включает вывод только
  при ограничении ключа по IP — привязать к IP сервера), Permits Universal Transfer — только если депозит зачисляется на
  Funding (venue.deposit_to_spot). Фьючерсы, опционы, Portfolio Margin — не нужны (показываются как лишние права).
  Белый список адресов вывода: адрес кошелька DEX (сеть BSC) добавить заранее — новый адрес выводится с задержкой
  (код −4036). Подпись потока аккаунта (WebSocket API) в журнал не пишется.
- XT.com (решение 167): API-ключ `xt.api_key` (AppKey) и секрет `xt.api_secret` (SecretKey), подпись HmacSHA256
  (passphrase нет). Права при создании ключа: QUERY, TRADE (спот и маржа одним правом), WITHDRAW; TRANSFER — только
  если депозит придёт не на спот; FUTURE и LEVER_LOAN — не нужны. Ключ привязать к IP сервера (bindIps). Ответ
  GET /v4/user/account/api-key содержит secretKey — в журнал и сырой журнал не пишется. Адрес кошелька DEX (BSC),
  вероятно, нужно заранее добавить в адресную книгу (код WITHDRAW_004).
- Phemex (решение 168): API-ключ `phemex.api_key` (поле id ключа; заголовок x-phemex-access-token) и секрет
  `phemex.api_secret` (подпись HMAC SHA256; passphrase у Phemex нет). Права — «Read & Trade & Withdraw», для вывода IP
  сервера обязателен; отдельного права «только спот» у Phemex нет — денег на фьючерсном счёте не держать. Вывод — только
  с главного аккаунта и только на адреса из «withdrawal address list» кабинета. Запроса «сведения о ключе» нет:
  «Проверить подключение» — пробными вызовами. Подпись входа WebSocket (user.auth) в журнал не пишется.
- Приватные ключи кошельков DEX в сети BSC (решение 132) — у каждого кошелька свой: секрет `wallet.<id>.key` (кошелёк,
  добавленный на экране «Маппинг кошельков») или прежний `bsc_dex.wallet_key` (кошелёк «BingX», перенесённый один раз).
  Ими бот подписывает свопы, переводы, разрешения и развёртывание исполнителя — только от кошелька счёта сделки.
- Токен Telegram-бота для уведомлений.
- Ключ CoinGecko для справочника пулов (`index.api_key`, решение 58) — только при заданном заголовке `index.key_header`; идёт в заголовке запроса, в журнал и сырые сообщения не попадает.
- Ключи провайдера узла BSC (`bsc.node_ws_key`, `bsc.node_http_key`) и резервного провайдера (`bsc.node_ws_key_backup`, `bsc.node_http_key_backup`) — если провайдер ставит ключ в адрес; в настройке адреса пишется `{key}`.
- Ключ провайдера узла BSC для агрегатора KyberSwap (`kyber.node_http_key`, решение 91) — если провайдер ставит ключ в адрес `kyber.node_http_url`; пишется как `{key}`, в журнал и ошибки не попадает. Кошелёк у исполнения через `kyberswap` — кошелёк счёта сделки (решение 132), отдельного ключа кошелька у неё нет. Идентификатор `kyber.client_id` (заголовок X-Client-Id) — не секрет, это обычная настройка.
- Ключи платных каналов отправки `channel.<id>.key` (Blink, bloXroute Cloud API, NodeReal Bundle API, BlockRazor Builder, Flashblock).
- Полный список с описаниями — `KNOWN` в `src/secrets/mod.rs`.

## Как хранятся
- Все секреты лежат в одном зашифрованном файле `secrets.enc` вне репозитория.
- Шифрование — по паролю; пароль нигде не сохраняется.
- При запуске бот ждёт пароль: вводится на экране «Разблокировка» в интерфейсе. До разблокировки торговля невозможна.
- Расшифрованные ключи существуют только в памяти процесса. На диск, в логи, в интерфейс, в сообщения об ошибках они не попадают никогда.
- Добавить, заменить или удалить секрет — только через интерфейс, после ввода пароля.

## Бэкап и перенос (импорт/экспорт настроек)
- Экран «Импорт/экспорт настроек» умеет делать полный бэкап: «Экспорт с секретами» (`GET /api/settings/export?secrets=true`)
  выгружает настройки и файл хранилища `secrets.enc` **как есть** — то есть зашифрованным. Расшифровки при экспорте нет,
  открытым текстом ключи в файл не попадают никогда; хранилище при экспорте можно даже не разблокировать.
- В файле бэкапа зашифрованный блоб лежит в секции `[secrets] blob` (base64 — только транспорт, не расшифровка).
- Импорт полного бэкапа ставит этот блоб в путь `secrets.enc` без расшифровки (проверяется лишь формат конверта) и
  **блокирует** хранилище: расшифровать и пользоваться им можно только исходным паролем на экране «Разблокировка».
- Файл полного бэкапа = ваши ключи в зашифрованном виде: его утечка опасна так же, как утечка `secrets.enc`.
  Хранить в безопасном месте, не пересылать по открытым каналам. Формат и алгоритм шифрования при переносе не меняются.

## Правила
- Файл `secrets.enc`, папки с данными и логами — в `.gitignore`; в репозиторий не попадают.
- В логах и журнале ключи маскируются целиком.
- Кошельки бота — отдельные, только под бота (у каждой биржи свой, решение 132); на них держится сумма, нужная для работы, а не все средства.
- Если BingX поддерживает белый список адресов вывода и привязку API-ключа к IP — включаем оба. Есть ли это у BingX, проверяется по их официальной документации (раздел «API BingX» в ТЗ).

## Как устроено шифрование (решение №27)
- Ключ из пароля — **Argon2id** (RFC 9106, версия 0x13), библиотека `argon2` (RustCrypto). Параметры — настройки
  `security.kdf_memory_kib`, `security.kdf_iterations`, `security.kdf_parallelism` (минимум OWASP: 19456 КиБ, 2 прохода, 1 поток).
- Шифрование — **XChaCha20-Poly1305** (аутентифицированное), библиотека `chacha20poly1305` (RustCrypto).
  Неверный пароль, порча файла или подмена параметров обнаруживаются.
- Формат `secrets.enc` (JSON): заголовок {версия, argon2id, параметры, соль 16 байт, xchacha20poly1305, nonce 24 байта} + шифротекст.
  Заголовок подписан вместе с содержимым (associated data). Параметры при открытии берутся из заголовка файла.
- Каждое сохранение — новая соль и новый nonce, атомарная запись (временный файл → сброс на диск → переименование).
- Соль и nonce — системный источник случайных чисел (`getrandom`).
- Ключ, пароль и значения секретов в памяти затираются при удалении (`zeroize`).
- Каждое изменение (добавить, заменить, удалить секрет, сменить пароль) требует ввести пароль заново — пароль не хранится.
- Длина пароля — не меньше `security.password_min_len`.
- Значения секретов не отдаются наружу: API показывает только имена. Все действия — в журнале, без значений.
- Неудачная разблокировка пишется в журнал.

## Кошельки DEX и маппинг (решение 132)
- Ключ кошелька вводится на экране «Маппинг кошельков» (имя + ключ + пароль секретов) и сразу записывается в
  зашифрованный `secrets.enc` под именем `wallet.<id>.key` — тем же механизмом, что любой секрет (пароль, Argon2id,
  XChaCha20-Poly1305). Добавление — только при разблокированных секретах (нужна сверка «этот ключ уже у кошелька X»).
- В SQLite (`dex_wallets`) хранится только ИМЯ секрета, имя кошелька, адрес исполнителя и ключ очереди. Адрес кошелька
  выводит из ключа адаптер DEX в момент запроса; сам ключ не попадает в базу, журнал, историю изменений, логи и ответы
  API никогда (тест `tests/api_wallets.rs`). API отдаёт только имя секрета и адрес.
- Ядро знает только id счёта (`DexAccountId`); ключ по id выбирает адаптер DEX. Без счёта адаптер не подписывает и не
  отправляет транзакции, не отдаёт адрес депозита и балансы — потерянный счёт не уводит деньги на чужой кошелёк.
- Удаление кошелька убирает только запись (и запрещено, пока кошелёк в маппинге или в незавершённой сделке); ключ
  остаётся в секретах — удалить его можно на экране «Разблокировка» (на кошельке могут быть деньги).
- Перенос прежнего ключа `bsc_dex.wallet_key` в кошелёк «BingX» не читает и не копирует ключ: кошелёк ссылается на тот
  же секрет.
- Кошельки и маппинг в экспорт настроек пока не входят (техдолг, docs/ROADMAP.md): полный бэкап с секретами переносит
  ключи, но записи кошельков и маппинг после импорта задаются заново.

## Доступ к веб-серверу
- Запросы с чужим Host или с чужой страницы браузера (Origin) отклоняются (`src/api/guard.rs`).
- Авторизация входа — открытый вопрос; до решения — запуск только на 127.0.0.1.
