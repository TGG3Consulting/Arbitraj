# Пара venue_dir с сетью (T487-05 / блок 430-а) — разбор и почему отложено до отдельной задачи

Дата разбора: 2026-11-21. Автор: Claude (ветка feat/arb-launch-blockers).

## Что просили

Разделить область «площадка + тип направления» (venue_dir, решение 242) и «пару» дневного лимита/просадки
(day_pair, решения 258/414) по СЕТИ: BingX → DEX BSC и BingX → DEX Arbitrum должны иметь РАЗНЫЕ лимиты, просадку и
closure_share. Предложение из TASKS 430-а: суффикс «@arbitrum» у сети не по умолчанию, у BSC id прежний.

## Факт по коду (проверено, не догадка)

- Ключ области и ключ «пары» — одна строка, её строит `settings/venue_dir.rs::id(venue, kind)` → «bingx:cex_dex» или
  «dex_dex». Без сети.
- Эта строка — одновременно: (1) ключ настройки в SQLite (`Scope::VenueDir(id)` → «venue_dir:bingx:cex_dex»);
  (2) **персистентный ключ учёта** в дневной книге и просадке: `drawdown_limit.rs`/`daily` хранят
  `pairs: BTreeMap<String, PairDay>` и `pair_paused` ПО ЭТОЙ строке.
- `VenueDir { venue, kind }` строится из `d.buy_on`/`d.sell_on` (`core/venue_dir.rs::rule`), **сеть в него не входит
  и на входе функций её нет**. day_pair идёт через тот же `rule` → `id`.
- Читают venue_dir 11 мест (шапка core/venue_dir.rs: profit, card_max, uncapped, precheck_dex_sell, prices,
  limits_parts, cycle_plan, dirctx, reserve, risk_ready, uncapped_recompute_ctx); day_pair/drawdown — ещё ~дюжина
  (daily_*, drawdown_*, risk*, commands*, report, notify-меню) + экран пар (api/settings.rs, settings/venue_kinds.rs).

## Почему отложено (не домысливаю и не рискую — CLAUDE.md)

1. **Это НЕ блокер запуска.** Проверено: Arbitrum-сделки DEX (CEX↔DEX, DEX↔DEX) не исполнятся, пока не развёрнут
   ArbExecutor на кошельке Arbitrum, а деплой закрыт `deploy_gate`, пока нет записи приёмки v5 × chainId 42161
   (её делает серв на узле ПОСЛЕ этого релиза — docs/notes/arbitrum/v5-record-integration.md). До этого venue_dir
   Arbitrum-сделок DEX никто не читает.
2. **Отсутствие разделения — поведение в запас (строже), а не дыра.** Сейчас BSC и Arbitrum одной пары делят ОДИН ключ
   учёта → их убытки складываются в один дневной лимит/просадку → торговля останавливается РАНЬШЕ, не позже. Разделение
   даёт каждой сети свой бюджет → суммарно допускается БОЛЬШЕ убытка. Для «никакого риска» на запуске текущее поведение
   безопаснее.
3. **Правка рискованная и широкая (~40 файлов, живой учёт BSC).** Ключ пары — персистентный ключ дневной книги и
   просадки. Если при добавлении сети неверно определить сеть BSC-сделки, её ключ сменится → накопленный за день убыток
   и состояние паузы по BSC потеряются/разъедутся. Это ровно то, что запрещено («BSC — железобетонно, никакой риск»).
   Менять живой учёт ради не-блокера под автономией — против CLAUDE.md «точечные правки / не домысливать».

## Открытый вопрос Тиграну (нужен до реализации)

**Как определять сеть сделки на входе venue_dir для КАЖДОГО типа направления?**
- CEX→DEX / DEX→CEX: сеть — у DEX-стороны (sell_on/buy_on = bsc_dex/arb_dex); берётся из реестра/`core/chain.rs`
  `tag_of_dex`.
- DEX↔DEX: сеть — у DEX (buy_on).
- **CEX↔CEX (cex_cex): сети DEX в сделке нет — перевод идёт по сети (сейчас BSC).** Чем помечать пару BingX→MEXC по
  Arbitrum vs по BSC? Сетью перевода направления (как T487-03 сделал для времени в пути пары, core/transit_source.rs —
  там ключ пары уже с сетью перевода)? Это и есть недостающий факт: нужно решение Тиграна, брать ли сеть из той же
  логики, что T487-03 (сеть перевода направления), и для cex_cex тоже.

Пока этот факт не задан — реализацию не начинать (иначе догадка в ключе живого учёта).

   байт-в-байт), но проверить `daily_migrate.rs` и загрузку книги.

6. Пять частей готовой фичи: DECISIONS (следующий номер), ARCHITECTURE, SETTINGS_CASES (если появится кейс настройки),
   UI, комментарии.
