## Как сделано

- Соединение SBE на каждую пачку монет рядом с JSON (`market.rs` → `sbe_run.rs`), те же пачки, темп подписок и пределы.
- Локальный стакан (`sbe_book.rs`): изменения копятся с момента, когда очередь снимков реально отправляет запрос (Start);
  пункт 4 (lastUpdateId < U первого отложенного) — снимок заново; u ≤ lastUpdateId — отбросить; U > номер + 1 — пропуск.
- Арбитр (`fast.rs`, `fast_sbe.rs`): пока быстрый стакан пары синхронизирован — ядру он; JSON — страховка: последний
  кадр запоминается, сверяется по содержимому (верхние N уровней). Пропуск / сбой снимка / обрыв SBE — пара сразу на
  JSON: последний кадр JSON, если он получен позже последнего отданного быстрого (по часам бота), иначе «недостоверно» до
  следующего кадра JSON (≤ 100 мс). После снимка — снова быстрый.
- Ключ: секрет `binance.sbe_api_key` (только API Key ключа Ed25519; приватный ключ не нужен — подписи нет).
- Без адреса / ключа / настроек очереди — соединение SBE не запускается, всё как раньше; запись `venue.book_fast` в
  журнале и строка «SBE (быстрый стакан): …» в «Проверить подключение».

## Что НЕ сделано и почему (нет в документации)

1. **Сверка по номеру страховки и быстрого стакана (п.4 общей постановки).** Связь lastUpdateId частичного стакана JSON
   с U/u потока изменений в документации не описана (как в решении «202/213 (Binance)»), времени биржи в частичном
   стакане нет. Поэтому «не старее уже отданного» — по времени получения на нашем сервере, сверка — по содержимому и
   только для подтверждения свежести тихой пары; расхождение содержимого пропуском не считается.
2. **Обёртка двоичного кадра.** Что двоичный кадр комбинированного потока /stream — ровно messageHeader + сообщение (без
   обёртки, как `{"stream","data"}` у JSON), документация прямо не говорит: сказано только «market data events in SBE in
   WebSocket binary frames». Проверить на живом кадре (иначе декодер вернёт ошибку длины — соединение переподключится,
   пары на страховке JSON, ничего не сломается).
3. **Подключение к /stream без streams=.** Документация показывает /ws/<stream> и /stream?streams=…; живая подписка
   разрешена. Соединение JSON уже подключается к /stream без параметра; для SBE — так же, проверить «Проверить
   подключение» на живом.
4. **Идут ли кадры изменений у пары без изменений книги** — не сказано («pushed at regular intervals»). Тихая пара
   подтверждается страховкой по содержимому.
5. **Новые версии схемы (1:1 и далее).** Корневой блок читается по blockLength заголовка (поля в конце пропускаются);
   новые группы перед symbol разбор сломают — ошибка кадра, переподключение, страховка. Нужна новая схема.

## Риски

- Старт: все пары на страховке JSON, пока очередь снимков не дойдёт (200 пар при 2/с — 100 с).
- Пропуск номеров на SBE → снимок не раньше venue.ws_reconnect_pause_ms (без круга ресинков); всё это время — JSON.
- venue.ws_silence_ms у Binance должна быть > 20000 (ping сервера раз в 20 с), иначе соединение SBE с тихими парами
  будет рваться по тишине.
- Тестов декодера на кадрах нет: живых кадров нет, двоичных примеров в документации нет (TASKS).
