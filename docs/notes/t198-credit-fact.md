## 2. Корень (факт кода f4da7719)

1. `fills.rs:162` `deal.qty = t.amount` — количество сделки = запись депозита биржи. Ни одна точка не сверяла её с
   балансом до продажи.
2. Отказ «мало средств» на продаже (`ErrorCode::InsufficientBalance`, у MEXC 10101/30004/30005) — не `retry_safe`, не
   `rejected_unsent` → `Retry::No` → человеку. Деньги при этом не тронуты (ордер не поставлен).
3. `remain_others.rs` вычитал из факта учёт ДРУГИХ сделок = их записи депозитов — на общем счёте с удержанием вторая
   сделка видела «всё чужое».
4. Сверка (`reconcile_confirm::expected`) сравнивала сумму записей с балансом → расхождение = удержание биржи → пауза
   площадки.
5. Расчёт прибыли не знал второго удержания: план +18.22 предполагал продажу записи.

## 4. Распределение долей (credit_split.rs) — правило и обоснование

Входы на один счёт (биржа, монета; торговый + перекладываемые на торговый, free + locked): факт F; учёт
подтверждённых C; ждущие — запись R_i и снимок посторонних U_i; «в пути» (сделка на шаге «перевод» через счёт); ожидаемое
удержание h; допуск tol (transfer.credit_amount_tolerance_pct).

- U = max(U_i) (не снят — 0, замер «неоднозначный»); пул P = F − C − U; R = ΣR_i.
- P ≥ R → каждой R_i, лишнее P − R никому (кейс 7).
- 0 < P < R → R_i × P / R, вниз до точности входных чисел; остаток округления никому.
- P ≤ 0 → 0 (алерт человеку, не «фантом»).
- есть «в пути» → доля ≤ R_i × (1 − h) (монеты сделки в пути могли уже прийти в P).

Почему пропорционально записям, а не «по приращению баланса в момент зачисления»: приращение однозначно только когда
между двумя чтениями зачислился ровно один депозит и ничего не продавалось. Пропорция — одна формула для всех случаев;
при одной ждущей она совпадает с приращением (вся P её, не больше записи). Удержание — доля перевода (у WKC = налог
токена), одинаковая у депозитов одной монеты на одной бирже, — пропорция не перекладывает удержание одной сделки на
другую. Сделка никогда не получает больше своей записи; посторонние (снимок до вывода) не получает никто.

Проверка на числах живого случая (tests/core_credit_fact_t198.rs): обе ждут, F = 5 915 283 179.1468 → 5 887 892 666.2232
и 27 390 512.9235, удержано 120 720 064.1933 (1.99999999 %); по очереди (как вживую) → 5 887 892 665.5528 и
27 390 513.5940; учёт после долей ≤ факта → сверка без расхождения.

## 5. Удержание биржи — мера (deposit_hold.rs)

- Замер — факт: последнее однозначное распределение (в пути никого, посторонние сняты у всех ждущих): записи, досталось,
  % — в учёте ядра SQLite (вид deposit_hold), как факты переводов withdraw_seen; последний замер заменяет прежний; 0 % —
  тоже факт.
- Ожидаемое удержание биржи-получателя: DEX / нативная — 0; замер есть — он; замера нет — налог перевода токена
  (проверки налогов DEX); налога нет — 0; налог не измерен — 0 (такие сделки не проходят расчёт — transfer_tax.rs).
- Консервативно до первого замера: удержание = налог перевода токена. Обоснование: факт WKC — удержание ровно равно
  налогу токена; первая сделка WKC с этой строкой затрат имела бы план ≈ +12.96 USDT (18.22 − 2 % от 262.99) и продала бы
  долю сразу, без перегона. Если биржа не удерживает, первая сделка замерит 0 % и снимет допущение.
- В расчёт прибыли и количества СЛЕДУЮЩИХ сделок: новая статья затрат `CostKind::DepositHold` («Удержание биржи при
  зачислении») на шаге «перевод», в монете: приход на B = вывод − затраты вывода − удержание (costs_source.rs Live
  withdraw; план DEX на A — plan_costs.rs, той же долей; «Перегон» — relay_value.rs). Монеты без налога токена — строки нет,
  расчёт прежний.
- Интерфейс: экран «Монеты» → окно монеты → «Удержание биржи при зачислении» по каждой бирже монеты (DepositHolds.svelte,
  поле deposit_holds GET /api/coins): замер или «не измерено — в расчёте как налог перевода N %».

## 7. Пауза площадки (решение 221) — пересмотр

Сужать паузу до монеты не стали: «Пауза ложится всегда только на биржу, где проблема» — прямое правило Тиграна в
решении 221; необъяснённое расхождение значит, что бот не знает, куда делись монеты на счёте (ручные действия,
неизвестное удержание, доступ к аккаунту) — это свойство счёта, а не монеты. Корень паузы WKC убран иначе: удержание,
учтённое в долях, расхождением больше не является (учёт подтверждённых = доли ≤ факт), ждущие доли в сверку не входят.
Необъяснённое — как раньше.

## 8. Что сознательно не сделано

- (Заменено ревью, раздел 9: факт читается всегда.) Перед продажей монеты без налога токена и без замеренного удержания факт не читается (кроме ждущих доли и отметки
  отказа): запись депозита у них = зачисленное (механизм удержания наблюдался только как налог токена), а отказ «мало
  средств» безопасен (ордер не поставлен) и ведёт к чтению факта и замеру. Так первая продажа не ждёт лишнего запроса к
  бирже (у MEXC ~0.3 с, решение 412).
- Окна ожидания «биржа ещё не дозачислила» нет: доля — по факту в момент перед продажей (без новой настройки времени).
  Если баланс отстаёт от статуса SUCCESS, сделка возьмёт меньше, остаток останется на счёте и будет виден в хронологии.
- События баланса MEXC (поток без хеша) и transfer.credit_by_event [mexc] не трогались (решение 107).
- Экран «Сделки» не показывает запись зачисления отдельным полем — всё в хронологии сделки.

### «Не присвоено» — определение (уточнение ревью)

Не присвоено (Split.unassigned) — монеты, которые по факту на счёте и по распределению достались бы ждущей сделке (не
больше её записи), но не отданы из-за ограничения доли «запись × (1 − ожидаемое удержание)» (нет снимка посторонних
или через счёт идёт сделка в пути). Они остаются на счёте. Удержано (held) — то, чего на счёте нет. По каждой ждущей:
запись = доля + не присвоено + удержано; лишнее сверх записей — отдельно, никому. Пример WKC: запись 6 008 053 740.36,
факт 5 915 283 179.1468, в пути, 2 % → доля 5 887 892 665.5528, не присвоено 27 390 513.5940, удержано 92 770 561.2132.
