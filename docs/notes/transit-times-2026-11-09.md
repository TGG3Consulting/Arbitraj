# Время в пути переводов: отправка и зачисление по площадкам (разбор 09.11.2026)

Разбор данных бота (коммит на сервере 343d90a) для настроек `profit.transit_manual_s` (площадка-источник) и
`profit.transit_credit_s` (площадка-получатель). Код не менялся. Источники: код `git show 343d90a:…`, данные бота
(GET `/api/deals`, `/api/journal` — весь журнал, id 1…1 451 635, 31.10 21:19 – 08.11 21:42 UTC, `/api/settings`,
`/api/settings/history`, `/api/coins`, `/api/transits`).

## 1. Какие моменты перевода пишет бот (факт кода)

| Момент | Где в коде | Куда пишется |
|---|---|---|
| **S — запрос вывода** (`started = Utc::now()`, до цикла вывода и до `withdraw_limit::take`) | `core/transfers.rs:192` | Не пишется отдельно. Восстанавливается: S = момент зачисления − `secs` из журнала |
| Ответ площадки на вывод (`created`) | `transfers.rs:204-205`; `updated_at = Utc::now()` в адаптерах: `bingx/transfers.rs:80`, `mexc/transfers.rs:98`, `gate/transfers.rs:97`; DEX — `bsc_dex/wallet/transfer.rs:158` | `deal.transfers[0].updated_at` — только в пути «по блокчейну» (`transfer_chain.rs:92-94`) |

| **Событие баланса DEX** (Transfer на кошелёк): уходит ядру, когда голова ≥ блок перевода + `send.deposit_confirmations`; `at = Utc::now()` в этот момент | `bsc_dex/wallet/events.rs:150-160`, `events_tx.rs:109-110` | Журнал `core.credit_event` — «Transfer в блоке N, хеш …» + вердикт |
| Событие баланса биржи (`at` = время события биржи) | `bingx/account_update.rs`, `mexc/account_update.rs:75-80` | — (у BingX, MEXC, Gate `venue.balance_events` не включён — событий нет) |

| Хеш вывода от биржи в пути «по блокчейну» — фоном, после зачисления | `transfer_chain.rs:132-187` | Журнал `core.transfer_chain` «хеш вывода … совпал» |
| Хронология сделки | `deal.rs:151-154` (время = момент вызова `note`); `fills.rs:146` «Перевод зачислен» — **после** перевода на торговый счёт (`to_trading`), `credit_chain.rs:131` | `deal.timeline` |

**Вывод по п.1.** Хронология сделки момент начала вывода не содержит и строку «зачислен» пишет после `to_trading` — для
разбора не годится. Надёжные точки — журнал: `secs` (полное время, им же кормится T), `core.transfer_sent` (H),
`core.credit_event` (номер блока перевода).
- **DEX → куда угодно:** отправка и зачисление разделяются честно: H наступает после попадания в блок (вывод DEX ждёт квитанцию).
- **Биржа → DEX:** H — момент, когда биржа *показала хеш в API*, а не появление в сети; биржи показывают его на 5–20 с позже
  блока (см. п.2, «лаг хеша»). Честная точка «в сети» — блок N из `core.credit_event`: I = t(событие) − 3 × 0,45 с
  (3 = `send.deposit_confirmations[bsc_dex]`, 0,45 с — интервал блока по данным бота: 1015 событий, блоки
  131 464 271…132 466 426, наклон 450,1 мс/блок, p10–p90 449,4–450,8).
- **Биржа → биржа:** блока нет (кошелёк бота не участвует) — разделение только по H из API; «отправка» завышена,
  «зачисление» занижено на лаг хеша отправителя. Сумма верна.

## 3. Не установлено
1. **Биржа → биржа**: честное разделение отправки и зачисления — блока перевода у бота нет. Нужно: время блока транзакции
   по хешу (свой узел BSC: `eth_getTransactionReceipt` → блок) или время отправки из истории выводов биржи.
2. **Внутри зачисления на бирже**: сколько из 16 с BingX / 37 с MEXC / 82 с Gate — подтверждения, а сколько — обработка биржи.
   Есть только число подтверждений из API (10 / 61 / 20) → 4,5 / 27,5 / 9 с при 0,45 с/блок; остальное (≈11 / ≈9 / ≈73 с) —
   обработка биржи плюс шаг опроса бота (`venue.status_poll_ms`: bingx 500, mexc и gate 2000). Что `minConfirm` = подтверждения
   для зачисления — по названию поля в адаптере; официальную документацию по этому полю в этом разборе не проверял.
   Нужно: время зачисления из истории депозитов биржи (поле времени в ответе API).
3. **Площадки без переводов**: binance, okx, htx, kraken, coinex, phemex, poloniex — данных нет; xt (1 перевод), bybit (2) — мало.

**Какой квантиль.** Медиана: сумма «медиана отправки + медиана зачисления» совпадает с медианой полного времени по
направлению (таблица выше: 11 vs 9,6; 54 vs 59,8; 18 vs 17,0; 39 vs 38,2; 47 vs 47,3) — значит разложение верное и T
«честное типичное». p75 по двум частям даёт сумму выше p75 полного времени (части складываются как худшие одновременно)
и по смыслу дублирует k = 4,5 в k·σ·√T. Режим «авто» берёт среднее последних 5 переводов, а средние у bingx (отправка 19,9 из-за
хвоста) и bitget выше медианы — для них p75 ближе к тому, что потом даст «авто». Предложение: **медиана**; у источников с тяжёлым
хвостом (bingx: p90 25 с, макс 520 с) хвост покрывают `transfer.max_time_s` и карантин, а не T. Решение — за Тиграном.

Отдельно: история «авто» за период, когда `credit_by_chain` был выключен (05.11 17:58 – 08.11 16:46), содержит лаг хеша биржи
(mexc → DEX по статусу 69,9 с против 59,8 по блокчейну; bingx 14,6 против 9,6) — эти T «авто» сейчас завышены, пока ряд из 5 не обновится.

## 5. «DEX → биржа — несколько секунд»?
Неверно для зачисления, верно для отправки. DEX → биржа (монета, n 235): медиана 35,1 с — это и есть «36 с»: смесь
DEX → bingx 17,0 и DEX → mexc 38,2 (и gate 82,7, bitget 70,6). Из чего складывается:
- **отправка с DEX: 0,8 с** (медиана, p90 1,0) — подпись, отправка, попадание в блок и квитанция своим узлом;
- **зачисление на бирже: 16,1 с BingX, 37,4 с MEXC, 82,3 с Gate, 70,2 с Bitget, 17,5 с KuCoin.** Из них подтверждения блоков по
  API биржи: BingX 10 × 0,45 = 4,5 с, MEXC 61 × 0,45 = 27,5 с, Gate 20 × 0,45 = 9 с; остальное — обработка на бирже и шаг опроса бота
  (событий баланса у BingX/MEXC/Gate нет, опрос статуса депозита).
«Несколько секунд» по данным — только DEX → кошелёк (сам перевод) и BingX → DEX по блокчейну (9,6 с).
