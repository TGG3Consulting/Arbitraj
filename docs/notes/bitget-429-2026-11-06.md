# Bitget: откуда HTTP 429 (06.11.2026, решение 201)

Живой журнал 06.11 (с 23:00 местного): 30 ответов 429 у bitget; виды записей — `core.registry` («Справочник сетей не
обновлён: пауза после 429»), `core.command` («Продать сейчас» отклонена: «баланс торгового счёта: пауза после 429»),
`core.candidate_rejected`. До решения 201 пауза после 429 у адаптера Bitget была ОДНА на всю биржу: 429 любого
эндпоинта останавливал все запросы, включая баланс, ордер и «Продать сейчас».

Лимиты — из официальной документации Bitget Classic v2 (выписка: docs/notes/bitget-analysis-2026-11-05.md, разделы 2–9;
«The overall rate limit is 6000/IP/Min», у каждого эндпоинта свой предел, считаются независимо). Частоты — из кода и
живых настроек bitget (venue.status_poll_ms = 2000, venue.networks_poll_ms = 60000, venue.rate_limit_pause_ms = 2000,
venue.order_poll_ms = 200, venue.fee_cache_s = 3600, venue.symbols_refresh_s = 3600).

## Вывод

Самый вероятный источник 429 — **/api/v2/spot/public/coins (3/с на IP)**: на него идут и предпроверка каждого
кандидата bitget, и полный справочник по каждому толчку аномального спреда любого направления. Это не ошибка кода
адаптера (запросы по делу), а сочетание частот; код не менялся. Что сделано в решении 201:

1. Пауза после 429 — **по эндпоинту** (venues/bitget/reply.rs): 429 справочника монет больше не останавливает баланс,
   ордер и «Продать сейчас» (у Bitget предел у каждого эндпоинта свой).
2. Ручные команды и продажа сделки ждут конец паузы (exec.rate_limit_wait_max_ms) вместо отказа.

Что может решить Тигран (настройками, без кода): задать у bitget **venue.networks_fresh_ms** (толчок внутри окна
свежести берёт справочник из кэша — решение 129), тогда полный справочник не чаще раза в это окно. Предпроверка
?coin= — по одной монете на кандидата; если 429 останутся — вопрос, кэшировать ли её (решение 113 требует свежих сетей
перед сделкой).
