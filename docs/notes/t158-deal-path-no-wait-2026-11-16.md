### 3.4 Сколько сделка теряла (оценка)

- Обычная сделка биржа → DEX → продажа: на пути **4 ожидания Telegram до продажи и закрытия** (`deal.buy_filled`,
  `deal.transfer_sent`, `deal.transfer_credited`, `deal.sell_filled`) и 1 после (`deal.closed`, держит замок монеты).
  Каждое — HTTP sendMessage + запись журнала. **Оценка:** при живом Telegram — десятки–сотни мс на каждое; при сбое
  сети Telegram — до `http.timeout_ms` на каждое (значение задаёт Тигран), т.е. до 4 × `http.timeout_ms` до продажи.
  Повторов у этих событий нет (dispatch.rs `send` без повтора), поэтому больше `http.timeout_ms` одно ожидание не длится.
- Застрявшая монета: `stuck.detected` и `stuck.market_sold` / `stuck.relayed` — ещё 1–2 ожидания ДО ордера.
- Журнал: каждая запись — ожидание замка соединения за всеми записями, которые сейчас в очереди к нему (журнал всех
  площадок и ядра, учёт, окна, эпизоды, «без потолка»), плюс синхронизация WAL (synchronous FULL). **Оценка:**
  доли мс — единицы мс в тишине; под шквалом записей (например `log.quote_timing_min_ms` = 0 — каталог сам
  предупреждает: «сотни в секунду») — десятки мс и больше.

## 4. Уведомления (решение 340) — как сделано

**Без настройки** (прямое распоряжение Тиграна): ни один шаг сделки не ждёт отправки уведомления.

- `Notifier::send`, `send_tagged`, `send_with_buttons` (notify/dispatch.rs, dispatch_role.rs) больше не отправляют
  сами: кладут задание в **одну очередь на рантайм** (notify/queue.rs) и сразу возвращаются. Сигнатуры не менялись —
  все 87 вызовов `.notify(…).await` / `.send(…).await` в коде остаются как есть, их `.await` больше не ждёт сеть.
- Очередь разбирает **одна фоновая задача по порядку постановки** → порядок уведомлений одной сделки (куплено →
  переведено → зачислено → продано → закрыта) сохраняется по построению (одна FIFO-очередь, один исполнитель).
- Повторы — по существующим правилам: у «Общего» повтора нет (как было), у ролей — один повтор через `retry_after`
  своей задачей (dispatch_role.rs, как было), у изменений настроек — `send_retry` в своей задаче (как было).
- Ёмкость — необязательная `notify.queue_max` (сообщений). Не задана — очередь без предела (ничего не теряется). Задана
  и очередь полна — уведомление не ставится, счёт потерь и запись журнала `notify.queue_lost` (Warn) на 1-й, 2-й, 4-й…
  потере (как у gateway/lost_log.rs ветки t155 без интервала) — не молча. Сделка не ждёт ни в одном случае.
- Логика, зависящая от ответа Telegram: id сообщения нужен только дублю «Ручного управления» (mirror_send.rs,
  mirror_edit.rs, mirror_store.rs) и меню чата «Управление» (ctl/) — это свои задачи, ядро их не ждёт (broadcast);
  не менялись. `deliver` возвращает только `retry_after` для `send_retry` — тоже своя задача.
- Пропал ли кто-то, кто читал журнал сразу после `send`? В рабочем коде — нет (поиск: никто не читает журнал после
  отправки). В тестах — tests/notify_journal_off.rs и tests/core_precheck_fast_266.rs читали записи «не отправлено» /
  выключенного события сразу после вызова; им добавлено ожидание пустой очереди (`Notifier::idle`).

**Содержимое — на момент события**, по каждому уведомлению:
- Текст всех уведомлений собирает вызывающий в момент события (строка передаётся в `send`) — снимок по построению.
- Карточка сделки («Монета», «Путь», «Где сейчас», notify/alert_card.rs) раньше бралась в момент ОТПРАВКИ. С очередью
  отправка позже, и «Где сейчас» у «Куплено» могла бы показать «в пути». Поэтому карточка снимается **при постановке
  в очередь** (queue.rs `snap`: тот же разбор текста `dispatch::body` → «Сделка: <id>» → `alert_card::lookup`) и
  передаётся отправке через task-local (alert_card.rs `scoped`); шаблон (alert.rs) берёт снимок, а без него — как
  раньше свежую (дубль «Ручного управления» — своя задача, там как было). Замок `inner.deals` при постановке: вызов
  `notify(…).await` в задаче tokio не может держать `std::sync::MutexGuard` (он не Send — будущее не собралось бы),
  поэтому взаимной блокировки нет.
- `deal.closed` (deal_closed.rs): текст итога — из копии сделки на момент закрытия; строки «без потолка» (одно чтение
  SQLite, deal_ceiling.rs) — теперь в фоновом задании очереди (читаются при отправке; расчёт «без потолка» к этому
  моменту только полнее — деньги сделки от него не зависят); карточка — из той же копии сделки (`deal_card::card`).
- Отказ: в очередь не поставлено (нет рантайма tokio — только в чужих потоках без рантайма; полная очередь) —
  запись журнала с кодом события, сделка идёт.

Объединение с t155: в t155 есть общий счёт потерь `gateway/lost_log.rs` (`Lost::hit`). После слияния счёт
`notify/queue.rs` (`Lost` свой, 40 строк) заменить на `gateway::lost_log::Lost` с видом `notify.queue_lost` — поведение
то же (1-я, 2-я, 4-я… запись), плюс общий интервал `log.events_lost_interval_s`.

**Что пишется** (`ledger::save` → persist.rs:17, таблица core_state вид `deal`, JSON сделки целиком):

**Что обязано лечь на диск ДО действия с деньгами:** запись 1 (иначе ордер ушёл, а сделки в учёте нет — деньги без

«Transfer» обе → Halted). Записи «заметок» (хронология), газ, итог закрытия могут идти следом.

своей транзакцией), окна, эпизоды, «без потолка», состояние площадок, дубль Telegram. **Оценка:** мс в тишине,
десятки мс и больше под шквалом журнала.

## 7. Журнал (решение 341) — как сделано и почему под настройкой

- `journal.queue_max` (записей, необязательная). Задана — `Journal::write` кладёт запись в очередь и сразу
  возвращается; **отдельный поток ОС** (не пул блокирующих задач tokio) пишет всё, что накопилось, **одной
  транзакцией** (`BEGIN … COMMIT`), по порядку постановки; затем каждая запись уходит в живой поток интерфейса с
  настоящим id. Очередь полна — запись не ставится, счёт потерь, и при следующей пачке писатель сам добавляет запись
  `journal.queue_lost` (Warn: сколько потеряно с прошлой записи и всего) — не молча.
- Не задана — как раньше (запись ждётся). Включили и выключили на ходу — пока в очереди что-то есть, новые записи тоже
  идут в очередь (порядок не ломается), потом — прямо.
- Остановка бота: при первом включении очереди ставится обработчик Ctrl+C / SIGTERM (storage/journal_stop.rs): дописать
  очередь и завершить процесс с кодом 0. Без настройки обработчик не ставится — остановка как раньше.
- `write_counted` / `update_counted` (строки повторов, нужен id) — прямые, как раньше; порядок их строк относительно
  записей очереди может отличаться на время одной пачки (это разные строки, одна запись не теряется).
- Закрытие строки отказов направления на пути сделки (executor.rs:190) при заданной `journal.queue_max` — фоном.

**Почему под настройкой (риск по разбору):** (1) возвращаемая `Entry` в режиме очереди — без id (id = 0); в рабочем
коде результат не читает никто (таблица 1), но тесты читают журнал сразу после действий — 28 вызовов
`journal.list` в 20 тестовых файлах; без настройки они не меняются. (2) Новый поток-писатель и обработчик сигнала меняют
поведение остановки. **Вопрос Тиграну:** «включать очередь журнала без настройки (всегда)?» — сам без настройки не
включено.

Объединение с t155: счёт потерь писателя (`journal_queue.rs`) можно заменить на `gateway::lost_log::Lost` после
слияния только частично — писатель журнала сам пишет запись о потерях в свою пачку (через `Lost::hit` писал бы
рекурсивно в ту же очередь); поэтому свой счётчик остаётся.
