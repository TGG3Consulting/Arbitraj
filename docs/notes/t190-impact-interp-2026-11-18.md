## Постановка (Тигран, 18.11.2026)

Лесенка влияния крючка B/C (hooks.impact_points, решение 335): для суммы между точками котировка брала влияние
ближайшей БОЛЬШЕЙ точки — завышение влияния, занижение прибыли, потеря сделок. Нужно: линейная интерполяция по сумме
между двумя соседними замеренными точками. Ниже первой и выше последней — как было. Базовое поведение, без новой
настройки (CLAUDE.md «Базовое поведение — в логике»).

## Факты кода до правки

- `src/venues/bsc_dex/quote/hook_curve.rs` `at` (до правки — строки 77–91): неубывающая лесенка — `steps[..=j]`
  максимум, где j — первая точка с входом ≥ x (значение ближайшей большей, накопленный максимум); лесенка с убыванием —
  наибольшее по всем точкам; x выше наибольшей — None («не измерено»); у лесенки с убыванием x ниже наименьшей — None.
- `at` вызывается только из `HookCurve::pct_at`, а он — из котировки: `quote/direct.rs` (продажа), `quote/route_calc.rs`
  (sell_step), `quote/graph_seq.rs`, и из `HookCurve::settle` (покупка «с конца»: `quote/direct.rs` calc_u,
  `quote/route_calc.rs` buy_step). Путь сделки (exec/trade_hooks.rs apply) подставляет в тот же `HookCurve` лесенку
  сделки — значит интерполяция действует и в расчёте сделки.
- `settle` (до правки): итерация «доля → вход → влияние» от наименьшего значения вверх, не больше числа точек + 2 шагов;
  конечность держалась на том, что значения берутся из конечного набора точек.

## Что сделано

1. `quote/hook_curve.rs`: `at` — интерполяция (`pick(.., up = false)` + `lerp`); прежнее правило оставлено как `upper`
   (`pick(.., up = true)`). Значение точки — накопленный максимум до неё (как было; шумовое падение в пределах
   разрешения не делает расчёт лучше факта). Вход не переводится в Decimal (больше 96 бит) — берётся значение большей
   точки (прежнее правило). Лесенка с убыванием, x ниже наименьшей / выше наибольшей — без изменений.
   `HookCurve::value(flat, x, up)` — значение без лимита; `pct_at` = `value(.., false)` + лимит hooks.max_impact_*.
2. `quote/hook_settle.rs` (новый; settle вынесен — hook_curve.rs был бы больше 200 строк): с интерполяцией значения
   непрерывны, и прежний подъём мог бы не сойтись за «точек + 2» шагов. Поэтому: (1) подъём прежним способом по `upper`
   (конечен, как раньше); его итог годится и для интерполяции (at ≤ upper); (2) спуск `p ← at(x(p))` — каждый шаг снова
   годится (вход растёт с влиянием, at неубывает по входу), приближение к неподвижной точке сверху, шагов не больше
   «точек + 2»; (3) лимит — к интерполированному влиянию на итоговом входе. Новых чисел в коде нет.
3. Тексты: описание hooks.impact_points в каталоге (`src/settings/catalog/trade.rs:31`), `docs/SETTINGS.md`,
   `docs/SETTINGS_CASES.md` («Смысл изменён»), комментарии `quote/breaks_hook.rs`, `exec/hook_drive.rs`, `quote/README.md`.
4. Тесты: новый `tests/bsc_dex_hook_interp_t190.rs` (точки записи 17.11 GAIB / BTCMT); поправлены ожидания
   `tests/bsc_dex_hook_ladder_1117.rs` (между точками — интерполяция вместо ближайшей большей) и
   `tests/bsc_dex_hook_ladder_review4_1117.rs` n1_evicted (см. вопрос 1).

## Пример на числах записи 17.11 (GAIB, покупка; формула check/hooks_probe.rs impact)

Точки: 1 USDT → 0 %, 20 USDT → 0,0990 %, 100 USDT → 0,6735 %.

| Сумма | Было (ближайшая большая) | Стало (интерполяция) |
|---|---|---|
| 10 USDT | 0,0990 % (точка 20) | 0 + 0,0990 · 9/19 ≈ 0,0469 % |
| 50 USDT | 0,6735 % (точка 100) | 0,0990 + 0,5745 · 30/80 ≈ 0,3144 % |
| 20 / 100 USDT | значение точки | значение точки (без изменений) |
| > 100 USDT | не измерено | не измерено (без изменений) |

BTCMT (20 → 0,7443 %, 100 → 3,3658 %): на 50 USDT было 3,3658 %, стало ≈ 0,7443 + 2,6215 · 30/80 ≈ 1,7274 %.
Квотера на промежуточных суммах в записях нет: интерполированные значения — оценка между фактами, не факт.
Наклон по точкам записи: GAIB 0,0052 → 0,0072 %/USDT (растёт — если кривая между точками выпуклая, хорда выше кривой,
интерполяция не лучше факта); BTCMT 0,0392 → 0,0328 %/USDT (падает — если кривая вогнутая, хорда ниже кривой, и
интерполяция может быть лучше факта). Какая кривая между точками на самом деле — покажет только запись квотера на
промежуточных суммах (в docs/TASKS.md уже есть задача дозаписать квотер GAIB на промежуточных суммах).

## Открытые вопросы Тиграну

1. **Вытеснение точек сделки (check/hook_trim.rs, ревью 4 Н1).** Значение вытесненной точки переходит большей соседке.
   При «ближайшей большей» влияние на сумме вытесненной точки было не ниже её значения; при интерполяции на этой сумме
   берётся интерполяция между меньшей соседкой и большей — может быть ниже измеренного там значения. Код вытеснения не
   менял (точечная правка). Тест n1_evicted переписан: проверяет, что значение у большей соседки и интерполяция на 21
   USDT лежат между точками. Оставить так или менять правило вытеснения?
2. **Покрытие суммы сделки фактом (check/hook_fold.rs covered).** Сумма «покрыта», если ближайшая большая точка снята
   этой сделкой. При интерполяции влияние на сумме зависит и от меньшей соседки, которая может быть точкой хранилища
   (более старый блок). Код не менял. Требовать и меньшую соседку из этой сделки?
3. **Лесенка с убыванием** — оставлено «наибольшее по всем точкам» (в записях такой лесенки нет). Интерполировать и её?
4. Подъём в settle по прежнему правилу: если x при прежнем (большем) влиянии уходит выше наибольшей точки, а при
   интерполированном остался бы внутри, — «не измерено», как было до правки (не хуже прежнего).

## Решение Тиграна 18.11 по таблице (прогон 44294821817) — что сделано

Таблица прогона: ИТОГ A — ближайшая большая занижает 0 раз; интерполяция — 4 раза, до 0,0407 п.п. (GAIB 300 USDT);
BTCMT покупка — лесенка «с убыванием» из-за 850 USDT (4,584 % < 500: 4,696 %), прежнее правило брало 4,696 % на всех
суммах (на 45 USDT факт 1,72 % → +2,97 п.п.).

1. **Накопленный максимум у любой лесенки** (`quote/hook_curve.rs` pick): ветка «не монотонна → наибольшее по всем
   точкам; ниже наименьшей — не измерено» убрана. BTCMT покупка: 45 USDT → интерполяция между 30 и 60, 850 → 4,696 %.
   merge не менялся (лесенка с убыванием хранится сырыми фактами, максимум берёт pick).
2. **Интерполяция с запасом:** `with_margin` = at × (1 + запас/100), **не выше upper** (значения ближайшей большей
   точки). Ограничение — уточнение исполнителя по принципу «не завышать»: в самой точке (в том числе в точке пробы на
   сумме сделки) значение — факт точки без запаса, между точками — не грубее прежнего правила. Вопрос Тиграну — TASKS.
3. **Настройка** `hooks.impact_interp_margin_pct` (Decimal, ≥ 0, % от значения, по площадке DEX, необязательна;
   каталог `src/settings/catalog/trade.rs:32`, экран — «Настройки» → «Налоги и крючки» и карточка площадки DEX: экран
   строится из каталога, `/api/settings/schema`). Чтение — `quote/select.rs` hook (NotConfigured → None) →
   `HookCurve.margin`. **Не задана** — правило котировки = upper (ближайшая большая точка, с накопленным максимумом):
   на записи 18.11 оно не занижает нигде, кроме CAKE 0xc6104625 на 1 и 5 USDT (убывающая кривая ниже наименьшей
   точки, до 0,0007 п.п.). Записи: SETTINGS_CASES, SETTINGS.md, FIRST_RUN.md.
4. **Путь сделки — по коду:** `exec/hook_trade.rs` paths (стр. 64–100): расчёт путей → `Drive` решает → проба
   `trade_probe::hooks_again` на входах пулов `w.x` путей этой сделки (точная сумма) → пересчёт с лесенкой сделки
   (`exec/trade_hooks.rs` apply стр. 89: хранилище + точки этой сделки, `check/hook_fold.rs` local) → готово, когда
   каждый вход покрыт (`hook_fold.rs` covered стр. 204: ближайшая точка с входом ≥ x снята этой сделкой). Значит:
   лесенка хранилища (с интерполяцией и запасом) — сигнал, подбор объёма, оценка путей до пробы; итог сделки — по
   лесенке сделки. На входе, равном точке пробы, правило котировки даёт значение точки (pick: накопленный максимум до
   неё; with_margin не выше upper) — **запас к факту пробы не применяется**. Если вход итогового пересчёта меньше точки
   пробы (точный выход «с конца» дал меньший вход), значение — интерполяция между меньшей точкой и точкой пробы с
   запасом, не выше факта пробы. HookCurve.margin переходит в путь сделки вместе с допуском (apply меняет steps, open,
   limit — margin не трогает).
5. **Вытеснение (`check/hook_trim.rs`) и covered — не менял.** С п. 1 значение каждой точки — накопленный максимум,
   поэтому передача значения вытесненной точки большей соседке (как сейчас) поднимает и все большие суммы — не ниже
   факта вытесненной правее неё; на суммах между меньшей соседкой и вытесненной — интерполяция с запасом (может быть
   ниже факта вытесненной). covered: итог сделки на входе x берёт точку ≥ x этой сделки как верх (with_margin ≤
   upper ≤ значение этой точки с максимумом), меньшая соседка влияет только между точками — как и в котировке.
6. **Проверка запаса 5 на записи 18.11 (прикидка вне бота, Python, обмен V4 с переходом тиков; с логом прогона
   совпали число занижений интерполяции в блоке A — 4 (GAIB 45, 80, 100, 300) и наибольшее — 0,04075 п.п. (лог 0,0407)
   при старом правиле «с убыванием»):** с п. 1 у BTCMT покупки
   интерполяция занижает на 80 / 100 / 300 USDT (факт 3,0649 / 3,4067 / 4,4599 %, интерполяция 2,6113 / 2,9211 /
   4,2052 %) — кривая между 60 и 150 USDT вогнутая; нужный запас 17,4 / 16,6 / 6,1 %. При запасе 5 новое правило там
   занижает на 0,3231 / 0,3395 / 0,0444 п.п. Поэтому ассерта «при запасе 5 не занижает в блоке A» в тесте нет —
   он был бы ложным; итог — строки «ИТОГ … новое правило» в логе. Таблица 2,2 % координатора посчитана со старым
   правилом «с убыванием — наибольшее» (BTCMT там шёл по 4,696 % везде).

## Правило между точками вместо запаса (Тигран 18.11, «да»)

Запас 5 % не перекрыл BTCMT (подтвердил координатор). Новое правило (`quote/hook_rule.rs` at): для a1 < x < a2 —
max(хорда(a1, a2) в x, продолжение наклона участка [a0, a1] от a1 до x), не выше значения a2; значения точек —
накопленный максимум; в точке — её значение; первый участок (нет a0) — хорда. `HookCurve::value`: котировка — at,
подъём settle — upper. Запас `hooks.impact_interp_margin_pct` удалён (в релизе не был; SETTINGS_CASES — «удалена»):
правило работает без него, дополнительный запас только завышал бы влияние; одна лишняя настройка меньше.
