# gateway — шлюз

Единственный путь между ядром и площадками.

| Файл | Что делает |
| --- | --- |
| `feed_health.rs`, `feed_reg.rs` | Решение 202: стык «сторож пар» — свежесть соединений и пар, команды «переподписать пару» / «переподключить соединение»; общий учёт свежести для адаптеров. Решение 213: версия книги (BookVersion по REST, версия последнего кадра в PairHealth, ConnHandle::frame_ver) |
| `contract.rs` | Контракт адаптера `Venue`: функции, обязательные для каждой площадки (стык); `DexFamily`. Неприменимая функция отвечает `NotApplicable`. Решение 217: `quote_snapshot` — снимок котировки стороны (по умолчанию NotApplicable) |
| `frozen.rs` | Решение 217: «замороженный» источник котировок — `FrozenQuote` / `QuoteSnapshot` (непрозрачный хэндл: котировка на объём по данным момента снимка, стакан снимка у биржи), `FrozenBook` — снимок стакана биржи с планом комиссии тейкера (`BookFee`), им же считается живая котировка бирж; `walk`, `deepest` |
| `errors.rs` | Единые коды ошибок + понятное сообщение + сырой ответ площадки (стык) |
| `events.rs` | События адаптеров (стакан, пул, недостоверно, проверка монеты и пула, канал отправки, спот-пары биржи `SpotPairs`, монеты DEX с ещё не прочитанными пулами `PoolsLoading`) и служебные события шлюза (стык) |
| `rules.rs` | Модель правил при сбоях и выбор правила: правило площадки сильнее общего. Повтор запрещён для «результат неизвестен» (retry_allowed, решение 64). |
| `http.rs` | HTTP-обмен с двумя сроками: до заголовков (http.timeout_ms) и тишина при чтении тела (http.body_idle_ms); правдивая причина сбоя (нет связи / нет ответа / ответ не дочитан); `exchange_full` — ещё и заголовок Retry-After в секундах (решение 118, А-🔴3) |
| `http_bind.rs` | Решение 178: исходящий адрес REST площадки (venue.local_ip) — клиент с local_address и DNS только того же семейства (IPv4/IPv6); общий builder всех HTTP-клиентов (редиректы выключены) |
| `tx_hash.rs` | Сравнение хешей транзакций из ответов площадок: нижний регистр, без `0x`, до `:` (решение 118, Я-16) |
| `patience.rs` | Решение 201: «терпение» ручной работы на задачу tokio (ждать конец паузы площадки после 429 вместо отказа) и признак котировки исполнения (exec_scope) |
| `pending.rs` | Решение 231: «чем найти» операцию с исходом «неизвестен» — PendingRef (свой ID ордера / вывода, ID площадки, символ, количество, время, монета получения, хеш и nonce) в `GatewayError.pending`; `created` — найденный вывод как перевод Pending (стык) |
| `quote_stage.rs` | Признак «финальная котировка расчёта» на задачу tokio (решение 95); `final_external` — финальная котировка площадки у внешнего исполнителя (exec.via_kyber = да): по нему ядро применяет kyber.final_gate_usd (решение 121 B5) |
| `calc_meter.rs` | Счётчик внешних запросов расчёта кандидата на задачу tokio (решение 129): адаптер сообщает вызовы к узлу BSC и агрегатору, ожидание очереди и время запроса; ядро видит их по этапам |
| `urgency.rs` | Срочность запросов (решение 61): Trade → Check → Quote → Background на задачу tokio; ядро помечает путь сделки Trade |
| `tap.rs` | Запись окон (решение 125): приёмник кадров окна `TapSink` (не ждёт: полон — потеря и счёт), кадр `TapFrame` (площадка, поток Book/Trades/Diff/Snapshot, соединение, время получения нс, текст или байты как пришли), приёмники адаптера по тикеру `Taps`, что включено `TapInfo` |
| `registry.rs` | Реестр подключённых адаптеров; `get_as` — DEX, привязанный к счёту (кошельку), решение 132 |
| `network_hint.rs` | Решение 200 Б: имена сетей котируемой монеты из живого справочника биржи (venue.bsc_network не задана) — «Проверить подключение» и ошибка справочника (core/registry_sync.rs). Склейка тикеров решений 200/206 убрана решением 211 |

Готовых правил в коде нет — все вводятся в интерфейсе. Если для ошибки правила нет,
шлюз останавливает операцию и уведомляет (применение правил — этап 5).
