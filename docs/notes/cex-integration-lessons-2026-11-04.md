# Уроки интеграций BingX и MEXC — обязательный чек-лист для новых бирж (Gate, Bybit, KuCoin)

Тигран, 04.11.2026: «интегрируешь согласно официальным документациям, учитывая все ошибки, которые были до».
Источники: DECISIONS 66, 107, 113, 114, 117, 118, 125, 129–134; разборы `docs/notes/mexc-audit-2026-11-03.md`,
`mexc-core-audit-2026-11-03.md`, `mexc-fix-design-2026-11-03.md`, `mexc-cpu-starve-2026-11-03.md`,
`musl-malloc-2026-11-03.md`, `sell-precheck-2026-11-03.md`. Шаблон адаптера — `docs/ADAPTER_TEMPLATE.md`.

Каждый пункт ниже — живая ошибка, которая уже стоила денег, времени или процессора. Новый адаптер обязан закрыть
каждый пункт и в своей заметке (`docs/notes/<биржа>-integration-2026-11-04.md`) написать, как закрыт (файл:строка)
или почему неприменим (со ссылкой на документацию биржи).

## 1. Документация и факты
1. Каждый эндпоинт, канал WS, параметр, поле, код ошибки и лимит — по официальной документации; ссылка на раздел —
   в комментарии функции. Нет в документации — не придумывать, а записать вопрос Тиграну в `docs/TASKS.md`.
2. Документация противоречит сама себе или живому ответу — проверять на записанном ответе API и сообщать Тиграну.
   Пример (решение 133): MEXC не пишет IMMEDIATE_OR_CANCEL в `orderTypes` ни одной пары, но принимает его;
   проверка «тип в orderTypes» заблокировала все ордера MEXC. Перечни «разрешённых» значений из справочников —
   сверять с тем, что биржа реально принимает (пробный ордер, записанный ответ), а не только со справочником.
3. Тесты — только на записанных ответах самой биржи (без моков). Публичные ответы — записать; приватные (ключ) —
   тест `#[ignore]` с описанием, что записать на живом боте (`tests/README.md`).

## 2. Ордера (деньги)
4. Правила ордера — ОДНА функция `order_rules::ready` (решение 134): её вызывают и настоящий ордер (`trade.rs`), и
   `check_order` контракта шлюза (проверка без исполнения перед покупкой — сторона продажи проверяется ДО траты
   денег). Тип ордера, сторона торгуется через API, шаги цены/количества (округление вниз количества, вверх/вниз цены —
   по смыслу стороны), минимум/максимум количества и суммы, фильтры цены, если проверяемы. Есть официальный пробный
   ордер без исполнения — использовать в `check_order` при включённой настройке (как MEXC `/api/v3/order/test`).
5. Стартовое правило Тиграна: «ордер отправлен и не исполнился — отменяем». Предпочтительно тип/время жизни, при
   котором неисполненное снимает биржа (IOC); если IOC нет — описать и спросить Тиграна, не изобретать.
6. Свой ID ордера — новый у каждой попытки (решение 114: дубль ID у MEXC при повторной продаже). Длина и алфавит —
   по документации.
7. Итог ордера — проверка факта (количество, средняя цена, комиссия и в какой монете) по документации; все сроки и
   лимиты запроса истории — настройки, проверяются ДО отправки ордера (после — поздно).

## 3. Справочники и монеты
8. Сопоставление монеты — по адресу контракта в сети BSC (не по тикеру): разные тикеры у одного адреса бывают
   (`core.ticker_split`: DARKHORSE на BingX = 黑马 на MEXC). Название сети BSC у биржи своё («BSC», «BEP20»,
   «BSC_BNB»…) — только из справочника биржи, настройкой `venue.bsc_network`.
9. Полный справочник монет биржи огромен (MEXC — 9620 монет, 5,6 МБ). Разбор — вне рабочих потоков tokio
   (`spawn_blocking`), кэш за `Arc`, без глубоких копий; запрос одной монеты, если биржа умеет (решение 113).
   Не толкать пересборку ядра, если ничего не изменилось (решение 131).
10. Ввод/вывод по сети: статус ввода и вывода, комиссия и минимум вывода, точность, memo/tag (если сеть требует —
    адрес депозита с memo, Я-15), подтверждения. Деньги на депозите могут приходить не на спот, а на
    funding/main-счёт — тогда внутренний перевод на торговый счёт обязателен (как `venue.deposit_to_spot` у BingX).
11. Комиссия торговли — по паре/ключу из API (не числом), с учётом скидок; монета комиссии — по факту.

## 4. Поток данных и производительность
12. Стакан: WS канал по документации (снимок N уровней или снимок REST + изменения с проверкой номера — разрыв →
    пересинхронизация, не бесконечный цикл ресинков). Сколько подписок на соединение и сообщений в секунду —
    из документации, в настройки (`venue.ws_symbols_per_conn`, `venue.ws_subs_per_sec`). Пинг/понг по документации.
13. На каждый кадр — минимум выделений памяти (решения 130, 131: musl malloc + копии = процессор в потолке). Не
    клонировать уровни стакана по нескольку раз на кадр.
14. Пересподписка при том же наборе символов не должна перезапускать фоновые круги (комиссии и т.п.) — решение 131.
15. REST-лимиты: веса/корзины по документации, ответ «слишком часто» (429 и аналоги) — пауза по Retry-After, не
    слать дальше (бан IP). Никаких REST на горячем пути расчёта — только память; баланс для расчёта — из потока
    аккаунта, свежий REST — только в предпроверке перед ордером (решения 94, 113).
16. Баланс и ордера — через приватный WS (поток аккаунта), если есть; ключ/токен потока — по документации.

## 5. Готовая фича (CLAUDE.md)
17. Код + настройки (все числа/адреса/URL — в каталоге настроек, без значений по умолчанию) + UI (площадка на
    «Площадки», «Проверить подключение» → «Подключено» или точная причина) + комментарии + ARCHITECTURE.
18. Секреты (ключ, секрет, passphrase) — только в зашифрованном файле секретов (docs/SECURITY.md), в журнал/API — никогда.
19. Права ключа: только спот-торговля и вывод/ввод; без фьючерсов, без маржи. Белый список адресов вывода — описать.
20. Новый адаптер не меняет ядро и шлюз (кроме регистрации в main.rs и, если нужно, общих типов) — CLAUDE.md.
    Кошелёк DEX для биржи — строка на экране «Маппинг кошельков» (решение 132), не новые настройки.
