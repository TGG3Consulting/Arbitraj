# AGENTS — как несколько ИИ-агентов разрабатывают проект параллельно

> Обязательно для каждого агента, вместе с CLAUDE.md.
> Схема работы: Claude в чате — техлид (архитектура, задачи, промпты, приёмка), агенты Claude Code — исполнители, Тигран — владелец и финальное решение.

## Главный принцип

Параллельная работа возможна только поверх **зафиксированных стыков**: контракт адаптера, общие типы ядра, схема настроек, формат событий, единые коды ошибок.
Пока стыки не зафиксированы — работает **один** агент. После — несколько, каждый в своей зоне.

## Порядок

| Фаза | Сколько агентов | Что делается |
| --- | --- | --- |
| 1. Каркас (этап 0 ROADMAP) | 1 | Структура папок, `core/types.rs`, `gateway/contract.rs`, `gateway/events.rs`, `gateway/errors.rs`, `settings/schema.rs` и хранилище, пустой веб-сервер, сборка проекта. Результат утверждает Тигран — это и есть зафиксированные стыки |
| 2. Параллельная разработка | до 4 одновременно | Каждый агент — своя зона (таблица ниже), работает только через зафиксированные стыки |
| 3. Сборка этапа | 1 (агент-проверяющий) | Сквозная проверка этапа целиком, затем следующий этап ROADMAP |

## Зоны агентов (после фазы 1)

| Агент | Зона: папки, которые он меняет | Не трогает |
| --- | --- | --- |
| BingX | `src/venues/bingx/` | всё остальное |
| DEX | `src/venues/bsc_dex/` | всё остальное |
| Ядро | `src/core/` | venues, ui |
| Интерфейс | `src/api/`, `ui/` | core, venues |
| Сервисы | `src/settings/`, `src/notify/`, `src/storage/` | core, venues, ui |
| Проверяющий | ничего не пишет — только проверяет и пишет замечания | — |

Общие файлы (`core/types.rs`, `gateway/*`, `settings/schema.rs`, `CLAUDE.md`, `ARCHITECTURE.md`, `docs/*`) — **никто из агентов не меняет напрямую**. Нужен новый тип, поле, функция контракта или настройка → агент пишет **запрос на изменение стыка** в своей задаче; техлид вносит изменение отдельной задачей, Тигран утверждает, все агенты подтягивают.

Исключение: строку в таблице «Готовые фичи» в `ARCHITECTURE.md` и строку в `docs/SETTINGS.md` для своих новых настроек агент добавляет сам — это часть готовой фичи.

## Синхронизация

- **Задачи — GitHub Issues** репозитория. В каждой задаче: зона, что сделать, какие файлы, критерии готовности (пять частей готовой фичи), ссылки на разделы ТЗ.
- **Одна задача = одна ветка = один Pull Request.** Ветка: `<зона>/<номер задачи>-<коротко>`, например `bingx/12-orderbook-ws`.
- **Каждый агент работает в своей копии репозитория** (git worktree), чтобы агенты не мешали друг другу в одной папке.
- **Перед началом и перед PR** агент подтягивает свежий `main` и перебазирует ветку.
- **PR маленькие:** одна фича или часть фичи. Большие изменения дробятся на несколько задач.
- В `main` попадает только то, что прошло проверку.

## Проверка перед слиянием (каждый PR)

1. Проект собирается, проходят форматирование, линтер и тесты (тесты — только на записанных реальных данных).
2. Агент-проверяющий сверяет PR с CLAUDE.md:
   - нет хардкодов и моков;
   - файлы не больше ~200 строк, шапки и комментарии на месте;
   - ядро не импортирует адаптеры;
   - готовая фича — все пять частей, включая интерфейс;
   - события фичи — в уведомлениях Telegram, новые подключения — с кнопкой «Проверить подключение».
3. Агент не меняет файлы вне своей зоны.
4. Сливает PR в `main` Тигран (или техлид по его решению).

## Что получает агент при старте задачи

- Весь репозиторий: CLAUDE.md, ARCHITECTURE.md, все docs/.
- Ссылку на задачу (Issue) с зоной и критериями готовности.
- Ссылку на ТЗ.
- Правило: что-то непонятно или не хватает стыка — остановиться и написать вопрос в задаче. Не додумывать.

## Отчёт агента по задаче

В комментарии к задаче и в описании PR:
- что сделано и какие файлы изменены;
- какие настройки добавлены (имена из docs/SETTINGS.md);
- что появилось в интерфейсе;
- какие события уходят в Telegram;
- что не сделано и почему; какие запросы на изменение стыков.
