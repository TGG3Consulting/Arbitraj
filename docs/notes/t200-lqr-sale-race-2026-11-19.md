# t200 — гонка продаж LQR 19.11.2026 (решение 415)

Живой случай (данные бота, хронологии сделок): кошелёк DEX w1, монета LQR, BingX → bsc_dex, одна группа докупки
(exec.top_up = да). A 20261119085840767LQR: зачислено 7316.64153 в 08:58:56.2, продано по
0.1183486421559381922735799249. B 20261119085843064LQR: план правильно учёл A (sell_avg 0.1174601510946614606572066079),
зачислено 5371.95816 в 08:58:56.3; «Котировка продажи на bsc_dex: средняя 0.1184877284330296105213894667» → «продажа не
ушла в сеть: [свой сборщик: умный] Цена в пуле сейчас 0.1174479740659173351024386981 хуже допустимой 0.117895» →
«Своих монет на счёте не видно … на DEX (кошелёк w1) сейчас 5372 LQR, но по учёту 7317 LQR из них принадлежат другим
сделкам: сделка A …» → алерт, 67 минут, продано кнопкой −3.93 USDT вместо плана +2.29.

Строки — по коду ветки feat/own-bsc-node, коммит e1c687cd (до правок t200).

## 1. Котировка B не видела продажу A

- Продажа сделки берёт котировку один раз на входе и с ней идёт в ордер: `src/core/sell.rs:97` (sell_or_stuck_guarded) и
  `:144` (market_guarded) — `trade_ops::deal_quote(core, &deal)`; ордер — `sell.rs:205–224` (trade_seen под
  credit_lock::selling) со средней этой котировки.
- `trade_ops::deal_quote` (`src/core/trade_ops.rs:343–351`) → `sell_quote_of` (`:391–465`): у DEX — `x.quote(&on,
  Side::Sell, qty)` (`:421`), котировка на `deal.qty` по состоянию пулов адаптера. Ничего о других сделках той же монеты
  на той же площадке здесь нет.
- Учёт идущих сделок группы есть только на ВХОДЕ: `ride_quote.rs` (sell_ahead / sell_after / buy_fresh, вызывает
  costs_source.rs Live) и `precheck_dex_sell.rs` (sell_ahead). Поэтому план B (0.11746015…) верен, а продажа B
  котировала пул заново — как будто A нет.
- Замок продажи `credit_lock::selling` (`src/core/credit_lock.rs:100–120`) — общий доступ (read): продажи сделок одного
  счёта идут одновременно, котировки друг друга не ждут.
- Время в хронологии: строка «Котировка продажи …» пишется ПОСЛЕ ордера (`sell.rs:228`, quote_note), поэтому у A и B
  она в одну миллисекунду 08:58:57.6; сама котировка B взята раньше, на входе в продажу.

## 2. Откуда минимальная цена 0.117895

- Худшая цена ордера DEX — `worst::worst_price` (`src/core/worst.rs:125–160`): `avg × (1 − exec.dex_slippage_pct/100)`
  (`:158`), avg — средняя котировки B 0.1184877284330296105213894667. 0.117895 / 0.11848772843 = 0.99499755… — сходится с
  exec.dex_slippage_pct = 0,5 (0.11848772843 × 0.995 = 0.117895289…; в тексте случая число округлено). Значение настройки
  на боте я не видел — это вывод по числам.
- Адаптер перед отправкой: `venues/bsc_dex/exec/order.rs:52` — у продажи `price < req.worst_price` → ошибка
  «Цена в пуле сейчас {price} хуже допустимой {worst}» (`:60`), price — по живому состоянию для количества B. После A
  пул дал 0.11744797… (≈ план B 0.11746015…) < 0.11789529… — отказ до отправки.
- Почему проверка B увидела пул уже после A: обмен кошелька ждёт конца обмена с тем же выходным токеном —
  `exec/trade_smart.rs:74` `env.inflows.swap(...)` → `wallet/inflows.rs:81` (`!t.swapping`; отметка держится до занятия
  nonce в блоке — шапка inflows.rs). Доли и цена считаются после этого (`trade_smart.rs:85` prepare по живому
  состоянию). То есть B стояла за A внутри адаптера, но котировку и худшую цену взяла до A.

## 3. Вторая половина — «Своих монет на счёте не видно»

- Ошибка B — QuoteMismatch, не отправлена: `OpError::retry_safe` (`src/core/op_error.rs:64–78`) → `sell_unsent::decide`
  (`src/core/sell_unsent.rs:73`, пауза 0) → Retry::Go → `sell_next::unsent_retry` (`src/core/sell_next.rs:37`) →
  `sell_unsent::retry` («продажа не ушла в сеть … повтор через режим застрявшей монеты», `:144–147`) → stuck::handle →
  `remain_fact::reconcile` → `remain_read::read` (факт кошелька и учёт других) → `remain_apply::apply_with`
  (`src/core/remain_apply.rs:34–37`) → `remain_others::own_qty` Human → `remain_alert::all_foreign`
  (`src/core/remain_alert.rs:37–44` — текст случая).
- Учёт других — `remain_others::on_account` (`src/core/remain_others.rs:78–83`): сделка с `qty > 0` и не закрытая
  вычитается. «по учёту 7317 LQR … сделка A» значит, что в момент чтения у A в учёте памяти ещё было 7316.64153.

### Закрывает ли t198 (credit_lock sync, sell_fact::before) — по текущему коду

- `credit_lock::selling` (`credit_lock.rs:100–120`): после ордера, ДО снятия охраны, учёт продающей сделки в памяти
  уменьшается на проданное (`:109` `d.qty = deal.qty - x.filled_qty`) — у A это 0.
- Чтение факта для сверки — под исключительным доступом: `remain_read.rs:93` (read_with) `credit_lock::fact` (write) —
  ждёт конца всех продаж ключа (bsc_dex, LQR); учёт других снимается под тем же замком (`:101`).
- `remain_others.rs:79`: сделка с количеством 0 (у DEX `credit` нет — `credit_fact.rs:88–90`, остатка «не присвоено» нет)
  не вычитается.
- Итог: в текущем коде сверка B идёт после конца продажи A и видит у A 0 → own_qty = min(5371.95816, 5372 − 0) — алерта
  нет. Вторую половину t198 закрывает. `sell_fact::before` здесь ни при чём: он только для биржи (`sell_fact.rs:42–46`,
  need: VenueKind::Cex), продажа на DEX факт перед ордером не читает.
- Был ли t198 в сборке бота 19.11 08:58 — по коду не установить (credit_lock.rs появился в 738e8961, релиз 19.11 (2) —
  4cf8312e). Без него чтение факта не ждало конца продажи A — ровно текст случая.
- Первую половину t198 не закрывает: замок продажи общий, котировки не упорядочены. Её закрывает решение 415.

## 4. Решение 415 — очередь продажи счёта

- `src/core/sell_turn.rs` — ход очереди (tokio Mutex) по ключу credit_lock (площадка + CoinKey); след прошлой
  исполненной продажи (конец, блок, пулы маршрута) хранится в замке. Порядок замков — в шапке файла.
- `src/core/sell_turn_fresh.rs` — котировка под ходом: биржа — стакан новее конца прошлой продажи; DEX — пулы её маршрута
  в памяти ядра уже с блоком ≥ её блока (адаптер шлёт пул ядру после записи в реестр — `pools/emit_pool.rs`) или маршрут
  котировки через её пулы по блоку ≥ её блока (тот же признак, что ride_trail.rs check / ride_quote.rs buy_fresh;
  DexRoute.block = наименьший блок пулов маршрута — `quote/costs.rs:62`; блок пула — блок события, `pools/events.rs:139`).
  Не свежо — ждём тика монеты (Ticks) не дольше feed.stale_after_ms площадки; срок вышел — по последней котировке, как
  раньше, строка Warn core.sell_turn.
- Пути: sell.rs (sell_or_stuck_guarded, market_guarded → sell: ход до итога ордера, `turn.done` сразу после
  credit_lock::selling), sell_range_run.rs (branch — свой ход на котировку и рыночный ордер), котировки-решения —
  stuck.rs (Ожидание, Порог убытка), relay.rs (продать здесь), relay_here.rs — ход только на время котировки.

## 5. Что не закрыто (риски)

- Ход держится всё время trade_seen: повторы по правилу шлюза, ожидание паузы площадки (patience_scope, решение 201),
  ожидание поступления USDT в кошелёк (inflows), поиск исхода «неизвестен» (outcome_resolve) — столько же, сколько
  держится credit_lock::selling. Другие сделки этой монеты на этой площадке ждут.
- Ключ DEX — без кошелька: продажи одной монеты с разных кошельков тоже по одной (пул общий — так и нужно для котировки).
- Продажи вне сделок («Продать» в «Балансах», balance_sell.rs) и циклы DEX ↔ DEX в очередь не входят.
- Ревью t200 (С-2): исход «неизвестен» оставляет след без блока — свежесть по времени получения пулов / первому блоку
  после конца продажи (не доказывает, что транзакция уже в блоке — она может попасть позже), иначе до срока.
- Ревью t200 (С-3): при exec.via_kyber = да маршрут обмена строит KyberSwap (kyberswap/trade_prep.rs), итог несёт наш
  запрос (kyberswap/trade_fact.rs) — след «маршрут неизвестен»: котировка B только по маршруту с блоком ≥ блока A
  (без общих пулов); у маршрута с давно не менявшимся пулом — ожидание до feed.stale_after_ms.
- Блок неизвестен — «первый блок после конца» берётся по времени получения пулов в памяти ядра: опоздавшее событие
  старого блока может дать блок раньше нашего.
- Использование feed.stale_after_ms как предела ожидания — решение агента, без новой настройки; вопрос Тиграну в TASKS.
